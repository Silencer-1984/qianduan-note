# 部署、缓存与数据库

## 一、Docker 与部署

### Q1 为什么用 Docker？

解决「我本地能跑，服务器不行」：把代码、依赖、系统环境打包成一致的镜像，开发/测试/生产跑的是同一个东西，部署动作简化成「拉镜像、启动」。

- **镜像**是只读模板，**容器**是镜像跑起来的实例；同一个镜像可以在任何装了 Docker 的机器上起多个容器。
- 多服务（app + db + redis）用 `docker compose` 一份 YAML 编排，网络、卷、启动顺序都写在里面。
- 镜像带版本标签，天然支持回滚（见 Q8）。

### Q2 给 FastAPI 写一个 Dockerfile，并解释每一行

```dockerfile
FROM python:3.12-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8000"]
```

三个关键点：

- **顺序**：先 `COPY requirements.txt` 装依赖、最后才 `COPY . .`。Docker 按层缓存，只要依赖文件没变，改代码不会重新 pip install，构建快很多。AI 常写成一上来 `COPY . .`，每次都重装。
- **`--host 0.0.0.0`**：容器里监听 `127.0.0.1` 只有容器自己能访问，端口映射再对也进不来。这是最高频的新手坑。
- **镜像与标签**：`slim` 体积小、攻击面小；`python:3.12-slim` 固定了版本，`latest` 会让构建不可复现，也没法回滚。

补充：`--no-cache-dir` 不让 pip 缓存留在镜像层；生产镜像建议加非 root 用户运行；`CMD` 用 JSON 数组形式（exec form），信号才能正确传给 uvicorn 实现优雅关闭。

### Q3 容器里的 localhost 指向谁？

指向**容器自己**，不是你的电脑，也不是旁边的数据库容器。连不上数据库的头号原因就在这里。

- compose 里容器之间用**服务名**互访：`postgresql://user:pwd@db:5432/app`，`db` 是 compose 里定义的服务名，由 Docker 内置 DNS 解析。
- `-p 8000:8000` 是「宿主机端口:容器端口」，只负责外部流量进来，不影响容器间通信；容器间直接用服务名 + 容器内部端口。
- 想从容器访问宿主机上的服务，用 `host.docker.internal`（Docker Desktop 提供），不是 localhost。

### Q4 容器删除后，数据库的数据还在吗？

默认**不在**。容器的可写层是临时的，`docker compose down` 之后数据就没了。数据库必须挂 **volume**：

```yaml
services:
  db:
    image: postgres:16
    volumes:
      - pgdata:/var/lib/postgresql/data
volumes:
  pgdata:
```

`pgdata` 是命名卷，独立于容器生命周期，由 Docker 管理。`docker compose down -v` 会把卷一起删掉 —— 生产环境别随手敲。

bind mount（挂宿主机目录）适合本地开发看文件，生产更常用命名卷。

### Q5 密钥怎么处理？

不写进 Dockerfile、不 `COPY` 进镜像，运行时通过环境变量或 `.env` 注入；`.env` 加进 `.gitignore`，**同时**写 `.dockerignore` 排除 `.env`、`.git`、`venv`、`__pycache__`。

原因：Docker 构建时把上下文目录里的文件发给 daemon，`COPY . .` 会把 `.env` 打进镜像层；**镜像层是累积的，后面再删掉文件，密钥仍留在历史层里**，镜像一推到仓库就泄露。

应用侧用 Pydantic `BaseSettings` 读环境变量，启动时缺关键配置就快速失败，别等第一次请求才发现。

### Q6 depends_on 能保证数据库已经就绪吗？

不能。它只保证**启动顺序**，不保证数据库已经能接受连接；应用先起来就会报连接失败。

```yaml
services:
  db:
    image: postgres:16
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U app"]
      interval: 5s
      retries: 10
  app:
    depends_on:
      db:
        condition: service_healthy
```

或者应用里做带退避的重连重试。两者都做最稳：健康检查管启动阶段，重连管运行中数据库短暂重启。

### Q7 容器起不来 / 服务异常，怎么排查？

按顺序走：

1. `docker ps -a` —— 在运行还是已退出，看退出码（`137` 通常是 OOM 被杀，`1` 多为应用报错）。
2. `docker logs -f <容器>` —— 大部分答案在这里。
3. `docker exec -it <容器> sh` —— 进容器内部查环境变量、DNS/网络、文件是否齐全。
4. `docker stats` —— CPU/内存是否被打满；配合 `docker inspect` 看挂载和端口。

常用命令：`build` / `run` / `ps` / `logs` / `exec` / `stop` / `images` / `docker compose up -d` / `down`。

### Q8 怎么上线一个新版本？出问题怎么回滚？

构建镜像并打**版本标签**（`app:1.2.0`）→ 推到镜像仓库 → 服务器拉取 → `docker compose up -d` 重建 → 看健康检查与日志。

回滚就是切回上一个版本标签的镜像再 `up -d`。这也是不用 `latest` 的原因：用了它根本不知道「上一版」是什么。

数据库迁移要单独跑（见 Q15），并且保持向后兼容：先加字段/加表，确认没问题再改代码，否则回滚代码时旧版本读不了新表结构。

## 二、PostgreSQL

### Q9 为什么选 PostgreSQL？

开源、成熟稳定、事务与约束完善、支持 `JSONB` 存半结构化数据、扩展生态丰富。

对 AI 应用尤其方便的是：**pgvector** 扩展可以直接在 PG 里存向量并做相似度检索。中小规模 RAG 不必再单独搭一套向量库，业务数据和向量一套库搞定，少一个组件、少一份运维和一致性问题。

`JSONB` 支持 GIN 索引和字段内查询，适合存模型输出这类结构不固定的内容；但频繁更新、需要外键和强约束的字段仍然应该建正规表。

### Q10 什么是事务？为什么需要？

事务是「要么全部成功、要么全部失败」的一组操作，满足 ACID（原子性、一致性、隔离性、持久性）：

```sql
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;   -- 中途出错 ROLLBACK，不会出现「钱扣了没到账」
```

默认隔离级别是 **Read Committed**（每条语句看最新已提交快照）；需要整个事务看到一致快照用 Repeatable Read。

AI 应用里典型的一组：创建订单 + 扣减额度 + 写调用日志，必须在同一个事务里。审查多步写操作时看两件事：有没有包在事务里、出错时有没有 rollback。

### Q11 什么是索引？什么时候建？有什么代价？

索引像书的目录，用额外的数据结构加速查找，默认 B-tree 适合等值、范围、排序。

- **该建**：经常出现在 `WHERE` / `JOIN` / `ORDER BY` 的列（`user_id`、外键、时间戳）。复合索引注意**最左前缀**。
- **代价**：占磁盘、拖慢写入（每次 INSERT/UPDATE 都要维护索引），所以别乱建；区分度低的列建了也没用。
- **验证**：`EXPLAIN (ANALYZE, BUFFERS)` 看是 `Index Scan` 还是 `Seq Scan`，以及估算行数和实际行数差多少。
- **常见失效**：`LIKE '%关键字'` 前导通配符、对列用函数或类型转换、类型不匹配、统计信息过期（需要 `ANALYZE`）。

### Q12 什么是 N+1 查询？

先查 1 次拿到 N 个对象，再在循环里对每个对象各查 1 次，总共 N+1 次：

```python
for user in users:        # 1 次
    print(user.orders)     # 每个 user 一次，共 N 次（ORM 惰性加载触发）
```

SQLAlchemy 这类 ORM 很容易写出来，数据量小时毫无感觉，上线就慢。

修复：用 `joinedload` / `selectinload` 预加载，或 `JOIN` / `where id in (...)` 一次取完。发现方法：开 SQL echo 或看慢查询日志里有没有大量重复的相似语句 —— **看到循环体里有查询就先警惕**。

### Q13 SQL 注入是什么？怎么防？

把用户输入直接拼进 SQL，攻击者可以改变语句含义：

```python
# 错
conn.execute(f"INSERT INTO logs VALUES ('{user_id}', '{message}')")
# 对：值单独传，由驱动处理转义
conn.execute("INSERT INTO logs VALUES (?, ?)", (user_id, message))
```

参数化查询把**语句结构和数据分开**传给数据库，输入永远被当成值而不是 SQL 片段。ORM 同理，但别在 ORM 里用 `text()` 拼原生字符串。其他注入面同理：命令拼接、路径拼接、模板渲染。这条在 FastAPI 那份代码审查清单里也出现过。

### Q14 为什么需要数据库连接池？

创建连接开销大（TCP + 认证 + 服务端进程），而且 PG 的连接数有上限（默认约 100）。每个请求新建连接，并发一高就报 `too many connections`。连接池复用已建立的连接。

- FastAPI 里 `async def` 接口要配**异步驱动**（`asyncpg` 等），同步驱动会阻塞事件循环。
- 多个实例时 **总连接数 = 实例数 × 池大小**，扩容前先算，必要时用 PgBouncer 这类外部连接池。
- 池耗尽的表现是「接口卡在等连接」而不是报 SQL 错，排查时容易误判成慢查询。

### Q15 数据库表结构要改了，怎么办？

用迁移工具 **Alembic**：每次改动生成版本化迁移脚本，进 Git、可追踪、可回滚、团队一致。绝不手动连线上库 `ALTER TABLE`。

`Base.metadata.create_all()` 只适合 demo —— 它只建不存在的表，**不处理字段变更、不记录版本、不会回滚**，AI 生成的项目里很常见。

上线顺序：先跑迁移（且保持向后兼容），再更新应用；回滚代码时确认旧版本还能读新表结构。

### Q16 几个「选对类型」的小常识

| 场景 | 正确做法 | 错误做法 |
|---|---|---|
| 金额 | `NUMERIC` | `FLOAT`（二进制浮点精度丢失） |
| 时间 | `TIMESTAMPTZ`（带时区） | 存字符串 / 不带时区 |
| 唯一性（邮箱等） | 数据库加 `UNIQUE` 约束 | 只在代码里判断（并发下会重复） |
| 大表分页 | 游标/条件分页 `where id > last_id` | 深翻页 `OFFSET 100000`（越往后越慢） |
| 查询字段 | 只查需要的列 | 无脑 `SELECT *` |

原则：**能在数据库层用约束保证的，不要只靠应用代码**。代码会有 bug、会有并发窗口，约束不会。

### Q17 数据怎么备份？

`pg_dump` 做逻辑备份，定时执行，备份文件存到**另一台机器或对象存储**，不要和数据库同机。

```bash
pg_dump -Fc -U app -d appdb > backup_$(date +%F).dump
pg_restore -d appdb backup_2026-11-11.dump
```

真正重要的是**定期演练恢复** —— 没验证过能恢复的备份等于没有备份。要求更高时再上 WAL 归档做时间点恢复（PITR）。

## 三、Redis

### Q18 Redis 是什么？为什么快？

基于内存的键值数据库。快在三点：数据在内存里、命令执行是单线程（没有锁竞争和线程切换开销）、用 I/O 多路复用处理大量连接。

单线程的好处：**单个命令天然原子**，`INCR` 做计数和限流不会竞态。注意「单线程」指命令执行，网络 IO 在新版本里已有多线程优化；真正的性能杀手是 `KEYS *`、大 key、慢命令这类阻塞操作。

### Q19 常用数据类型和场景？

| 类型 | 典型场景 |
|---|---|
| String | 缓存 JSON、计数器、验证码 |
| Hash | 存对象字段（用户信息） |
| List | 简单队列、最近记录 |
| Set | 去重、标签 |
| Sorted Set | 排行榜、延迟队列（按 score） |
| Stream | 消息流、轻量任务队列 |

### Q20 Redis 在 AI 应用里干什么？

- **缓存**：相同问题的 LLM 回答、embedding 结果，省钱省时间。
- **限流**：`INCR` + `EXPIRE`，限制每用户每分钟调用次数，防止 token 费用被刷爆。
- **短期上下文**：最近几轮对话、登录态。
- **任务队列中间件**：Celery 的 broker。

边界要讲清：**长期对话历史和重要数据的权威来源是 PostgreSQL**，Redis 只是加速层，丢了可以重建。

### Q21 什么是缓存旁路（Cache-Aside）？写出流程

读：先查缓存 → 命中直接返回 → 未命中查库 → 写回缓存再返回。写：先更新数据库，再删除缓存。

```python
async def get_user(uid):
    key = f"user:{uid}"
    cached = await redis.get(key)
    if cached:
        return json.loads(cached)
    user = await db.fetch_user(uid)
    await redis.set(key, json.dumps(user, default=str), ex=3600)
    return user
```

这段代码里常见的五个疏漏：

- 用户不存在时每次都查库 → **缓存穿透**，应缓存空值并设短过期；
- 所有 key 都 3600 秒 → 同时过期引发**雪崩**，过期时间加随机偏移；
- 更新用户时没删缓存 → 读到脏数据；
- `json.dumps` 遇到 `datetime` 会报错，要传 `default=str` 或先序列化；
- 要用异步客户端（`redis.asyncio`），别在 `async def` 里用同步 Redis。

### Q22 缓存穿透、击穿、雪崩分别是什么？怎么应对？

| 问题 | 含义 | 应对 |
|---|---|---|
| 穿透 | 大量请求查**根本不存在**的数据，缓存挡不住，全打到库 | 缓存空值（短 TTL）、参数校验、布隆过滤器 |
| 击穿 | 某个**热点 key** 过期瞬间，大量请求同时打到库 | 互斥锁只让一个请求重建、热点数据逻辑过期不删 |
| 雪崩 | 大量 key 同时过期，或 Redis 宕机 | 过期时间加随机抖动、多级缓存、熔断降级、Redis 高可用 |

### Q23 缓存和数据库怎么保证一致？

做不到绝对强一致。工程上的做法是：**先更新数据库，再删缓存，并给缓存设 TTL 兜底**，接受极短时间窗内的不一致。

- 为什么是「删」不是「更新」缓存：并发写时两次更新缓存可能乱序，删掉让下次读重建更安全。
- 为什么不是「先删缓存再更新库」：删完到写库之间如果有读请求，会把旧值重新塞回缓存，脏得更久。
- 要求更高时用延迟双删，或订阅 binlog 异步失效；跨服务强一致要引入分布式事务，代价大，一般不做。

### Q24 Redis 数据会丢吗？

会。数据在内存里，重启可能丢。两种持久化：

- **RDB**：定时快照，文件小、恢复快，但两次快照之间的数据会丢；
- **AOF**：记录写命令，丢得少（可配每秒刷盘），文件大、恢复慢。

生产常两者都开。但不建议把 Redis 当唯一数据存储 —— 重要数据以 PostgreSQL 为准，Redis 里的内容应该都能重建。

### Q25 Redis 的几个审查点

- 没设 TTL：内存无限增长，最终撑爆或触发淘汰策略把别的数据清掉；
- key 没有命名规范：用 `业务:类型:id`，如 `user:123:profile`；
- 生产环境用 `KEYS *`：会阻塞整个 Redis，用 `SCAN` 分批；
- 没设密码还暴露公网：真实世界里的高频入侵原因，应只监听内网 + `requirepass`；
- 缓存了敏感信息或超大对象：前者有合规风险，后者一次读写就能拖慢整条链路；
- 配了 `maxmemory` 却没想清楚 `maxmemory-policy`：默认策略可能把还想留的 key 淘汰掉。

## 四、实操题

### S1 设计一个 AI 聊天应用的数据存储，各放什么？

| 存储 | 放什么 |
|---|---|
| PostgreSQL | `users`（账号）、`sessions`（会话元数据）、`messages`（长期历史，权威数据）；做 RAG 时向量放 `pgvector` |
| Redis | 限流计数、登录态、热点回答缓存、最近几轮上下文 |

分界原则：**持久、需要查询和事务的放 PG；高频读写、可丢失、可重建的放 Redis**。

表结构示意：`sessions(id, user_id, title, created_at)`、`messages(id, session_id, role, content, token_count, created_at)`，`messages.session_id` 建索引并按时间排序；向量表 `embeddings(doc_id, chunk, embedding vector(1536))`。消息只追加不回改，分页用游标而不是 `OFFSET`。

### S2 接口突然变慢，怎么排查？

按层次定位：

1. **先量化**：加耗时埋点/链路追踪，看是全部接口慢还是个别慢、慢在哪一段。
2. **外部调用**：LLM API 是不是本身变慢（最常见）。看首 token 时间和总耗时，区分「模型慢」和「我们自己排队」。
3. **数据库**：`EXPLAIN ANALYZE` 查慢查询、是否缺索引、有没有 N+1。
4. **连接池**：是不是请求卡在等连接（池耗尽时表现为等，不是报错）。
5. **缓存**：命中率是不是掉了，导致流量全回源到 DB 或 LLM。
6. **容器资源**：`docker stats` 看 CPU/内存，OOM 被杀或 CPU 限额被打满都会让延迟飙升。

### S3 怎么防止用户把你的 LLM 额度刷爆？

- Redis 限流：`INCR` + `EXPIRE`，按用户每分钟 N 次；更平滑可以用滑动窗口或令牌桶。
- 请求体限制长度（`max_length`），超长直接 422，避免一次调用吃掉大量 token。
- 接口必须认证，匿名调用不能触发 LLM。
- 设每日/每月额度，额度计数**落库**（Redis 可能被淘汰或重启清空，不能只靠它）。
- 监控异常用量并告警：按用户、按模型的调用次数和 token 消耗，突增要能发现。

### S4 相同问题要不要缓存 LLM 的回答？

可以，但要说清前提和限制。

- key 要对**所有影响结果的因素**做哈希：模型名与版本、prompt、温度等参数、以及会影响答案的上下文摘要；只按问题文本做 key 会串答案。
- 设 TTL，并监控命中率；命中率高才说明真省到了钱。
- **不能缓存**的：带个性化信息（用户资料、权限相关）、实时性要求高、上下文不同答案就不同的请求；含敏感信息的回答也别进共享缓存。
- 流式输出和缓存要分开处理，别把流式片段直接塞进缓存。

### S5 描述一次完整的上线流程

本地构建镜像 → 打版本标签（`app:1.2.0`）→ 推镜像仓库 → 服务器拉取 → **执行数据库迁移**（Alembic，且保持向后兼容）→ `docker compose up -d` → 健康检查 + 看日志 → 出问题切回上一个镜像标签。

两个容易漏的点：迁移要在新代码对外提供服务前跑完；回滚代码时要确认旧版本还读得了新表结构（这也是 Q15 强调迁移向后兼容的原因）。
