# 04 网络与安全

## 同源策略

协议、域名、端口三者全一样才算同源。

- 限制的是**跨源读取响应**：`fetch` 请求发得出去，但 JS 拿不到响应内容。
- 顺带限制跨源访问 DOM、跨源读 cookie。
- **它防不住 CSRF**：CSRF 压根不需要读响应，只需要借你的登录态发个请求。防 CSRF 靠 `SameSite` + CSRF Token。
- `<script>`、`<img>`、`<link>` 不受限制——能加载，但读不到内容。这正是 JSONP 的立足点。

## CORS

三行说完：

1. **简单请求**（`GET` / `POST` / `HEAD`，`Content-Type` 只限那三种，没有自定义头）直接发出去，浏览器看响应里的 `Access-Control-Allow-Origin` 决定 JS 能不能读。
2. **其余都是预检**：先发 `OPTIONS`，服务端回 `Allow-Methods` / `Allow-Headers` / `Allow-Origin`，通过了才发真正的请求——预检不过，真请求根本不会发。
3. **带 cookie**：前端 `credentials: 'include'`，服务端 `Access-Control-Allow-Credentials: true`，且 `Allow-Origin` **不能写 `*`**，必须写具体域名。

开发环境更省事的做法是 dev server 代理：同源请求本地，本地服务端再转发，同源策略管不到服务端之间的请求。

## JSONP

利用 `<script>` 不受同源限制：拼一个 `<script src="...?callback=fn">`，后端返回 `fn({...})`，直接当 JS 执行。**只能 GET**，现在基本不用，但“`<script>` 为什么能跨域”是常问的引子。

## postMessage

跨源窗口通信，iframe 父子页最常用。

- 发送：`iframe.contentWindow.postMessage(data, targetOrigin)`
- 接收：监听 `message` 事件，**必须校验 `event.origin`**，否则等于给自己开后门。

## HTTP 缓存
![图片描述](https://github.com/user-attachments/assets/b7ed9ab2-edcd-4539-a912-a0aa59ef8160)
两级，都靠响应头控制。

### 强缓存

- `Cache-Control: max-age=秒数`：有效期内**不发请求**，直接读本地，状态码 200（from cache）。
- 老写法 `Expires` 是个时间点，受客户端时间影响，已经被 `Cache-Control` 取代。
- 三个常用指令别混：`no-store` 完全不存；`no-cache` **照存，但每次用之前都要验证**（不是“不缓存”）；`must-revalidate` 过期后必须找服务端。

### 协商缓存

浏览器照常发请求，带上缓存标识让服务端判断变没变：

- `Last-Modified` / `If-Modified-Since`：按时间，只精确到秒。
- `ETag` / `If-None-Match`：按内容 hash，更准。
- 没变 → `304 Not Modified`，用本地那份；变了 → `200` 加新资源。

`ETag` 更准的原因：内容没变但文件修改时间变了会误判；时间只到秒；多机部署时各机器时间还不一致。

### 实际怎么配

- **HTML**：`no-cache` 或协商缓存，每次都验证，保证拿到最新入口。
- **JS / CSS**：打包时文件名带 contenthash（`main.a1b2c3.js`），内容一变文件名就变，所以能放心 `max-age=31536000` 缓存一年。
- **图片 / 字体**：同样带 hash，长期强缓存。
- **用户上传的图片**：走 CDN，策略由 CDN 决定。

### 三种加载行为不一样

- 地址栏回车：强缓存有效就直接用本地。
- `F5`：**跳过强缓存**，带 `Cache-Control: no-cache` 去走协商缓存。
- `Ctrl+F5`：连协商都不走，整份重新下载。

## 从输入 URL 到页面呈现

一条链，面试常整题问：

1. **URL 解析 + 查缓存**：先看强缓存有没有效，有效就直接用本地，不发请求。
2. **DNS 解析**：浏览器缓存 → 系统 hosts → 路由器/局域网 DNS → ISP DNS。客户端到本地 DNS 是**递归**，本地 DNS 到根/顶级/权威是**迭代**，别搞混。
3. **TCP 三次握手**。
4. **HTTPS 再加 TLS 握手**：协商算法、验证书、生成会话密钥。
5. **发 HTTP 请求**：请求行（方法 + 路径 + 版本）、请求头、请求体。端口 HTTP 80、HTTPS 443。
6. **服务端响应**：状态行 + 响应头（缓存头就在这）+ 响应体。
7. **浏览器渲染**：见渲染那一节的六步。
8. **断开**：四次挥手。但 HTTP/1.1 默认 keep-alive，实际访问很少立刻断开，连接会复用。

能加分的两句：DNS 预解析（`dns-prefetch`）、TLS 1.3 只需 1-RTT，都是这条链上最省时间的地方。

## TCP 与 UDP

| | TCP | UDP |
|---|---|---|
| 连接 | 面向连接，先三次握手 | 无连接，直接发 |
| 可靠性 | 不丢、不重、按序（确认 + 超时重传 + 序号排序） | 尽力而为，可能丢、可能乱序 |
| 传输方式 | 字节流 | 一个包一个报文 |
| 典型场景 | HTTP、文件传输 | 直播、视频会议、游戏、DNS |

**三次握手**：确认双方的收发能力都正常，同时同步各自的初始序列号。

**为什么不是两次**：网络延迟的旧 SYN 晚到了，服务端一收到就分配资源、认为连接已建立，但客户端不认这个连接，服务端就白占着资源干等。第三次让客户端回一句“我收到你的确认了”，服务端才敢落实。

**为什么挥手要四次**：服务端收到 FIN 只能先回 ACK（“知道你要关了”），但它自己可能还有数据没发完，等发完再发 FIN，所以拆成两次。

**TIME_WAIT**：主动关闭方等 2MSL，保证最后那个 ACK 丢了还能重发，同时让这条连接的残留报文在网络里自然消失。

## HTTP 状态码

| 段 | 记这几个 |
|---|---|
| 2XX | `200` 成功、`204` 成功但没有响应体、`206` 范围请求（断点续传） |
| 3XX | `301` 永久重定向（会被缓存）、`302` 临时重定向、`304` 协商缓存命中、`307` 临时但要求保持原方法 |
| 4XX | `400` 报文有错、`401` 没认证、`403` 认证了但没权限、`404` 资源不存在 |
| 5XX | `500` 服务端异常、`502` 网关拿到无效响应（后端挂了）、`503` 过载或维护、`504` 网关超时 |

两个最实用的判断：**4XX 是客户端的问题，5XX 是服务端的问题；502 是后端没起来或崩了，504 是后端太慢。**

## GET 与 POST

| | GET | POST |
|---|---|---|
| 参数位置 | URL 的 query | 请求体 |
| 缓存 | 默认可缓存 | 默认不缓存（显式设置也能缓存） |
| 幂等 | 幂等 | 不幂等 |
| 典型用途 | 查询 | 提交、修改 |

结论：**两者本质没有区别**，都是 HTTP 请求、都走 TCP，只是报文格式和语义约定不同。URL 长度限制是浏览器和服务器的实现限制，协议里没有规定。

## HTTPS 与 TLS

- HTTP 明文传输；HTTPS = HTTP + TLS，端口 443，需要 CA 证书。
- **不能只用对称加密**：密钥没法安全地送到对面，网络上送就等于公开。
- **不能只用非对称加密**：太慢，整段会话都这么加，性能扛不住。
- 所以是**混合**：先用非对称（现在多是 ECDHE）协商出一个**会话密钥**，之后所有数据都用这个密钥做对称加密。
- **证书**解决中间人：CA 的签名证明“这个公钥确实属于这个域名”。
- 一句话：**非对称负责安全地商量，对称负责高效地传输**。TLS 1.3 一轮往返就能建好连接。

## HTTP 版本演进

- **1.0**：每个请求开一个 TCP 连接，用完就关。
- **1.1**：默认长连接（keep-alive），支持管道化，但有**队头阻塞**。
- **2**：同一个 TCP 上多路复用、二进制分帧、头部压缩（HPACK）；服务端推送已被废弃。
- **3**：换到 UDP 上的 QUIC，绕开 TCP 层的队头阻塞，建连 0-RTT。

## WebSocket

- 持久连接、双向通信，握手时用 HTTP 的 `Upgrade` 升级协议。
- 不受同源策略限制，但**服务端仍然要校验 `Origin`**，否则等于开了任意跨站连接。
- 场景：聊天、协同编辑、实时推送。只需要单向推送的话，SSE 更省事。

## 会话方案

- **cookie**：HTTP 规范里的东西，浏览器自动存、自动带，能设 `HttpOnly`。
- **token（JWT）**：自己存储、自己塞进请求头。无状态的代价是**没法主动吊销，只能等过期**；payload 只是 base64 编码，不是加密，别往里放敏感信息。
- **session**：数据放服务端，占内存，多实例部署要拿 Redis 共享。

## 前端安全

### XSS

三种：**存储型**（恶意内容进了数据库）、**反射型**（藏在 URL 里）、**DOM 型**（前端自己把不可信内容塞进 `innerHTML`）。

React 的默认防御：JSX 里渲染的字符串会被转义，`<script>` 只会当文本显示。但三个地方会失效：

- **`dangerouslySetInnerHTML`**：名字里的 dangerous 不是白叫的，必须先用 DOMPurify 之类清洗。
- **危险的 `href` / `src`**：`javascript:alert(1)` 在 `<a>` 上照样执行，要校验协议白名单（`http` / `https` / `mailto`）。
- **SSR 脱水注入**：`window.__DATA__ = ${JSON.stringify(data)}` 遇到 `</script>` 会提前闭合标签，要用 `serialize-javascript` 转义 `<` 这类字符。

兜底手段：CSP 限制内联脚本和外部域；cookie 加 `HttpOnly`，让 XSS 偷不到 token。

### CSRF

攻击者不读响应，只借你的登录态发请求。防御：

- cookie 设 `SameSite`（`Lax` 起步）；
- CSRF Token，表单或请求头带上服务端下发的随机值；
- 校验 `Origin` / `Referer`；
- 敏感操作二次验证。
