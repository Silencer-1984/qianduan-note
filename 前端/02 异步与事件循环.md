# 02 异步与事件循环

## 为什么要有 Promise

回调写法三个硬伤：

- **耦合**：层层嵌套，改一个回调要动一片。
- **错误处理**：`try/catch` 抓不到回调里异步抛出的错，只能在每一层手动传 `err`。
- **可读性**：一眼看过去全是 `})`，逻辑被拆碎。

Promise 干的事就是把“成功/失败”变成一个**可以传递的值**，让流程能串起来。

## Generator

用 `yield` 暂停、`next()` 恢复。它本身不是异步方案，价值是把异步流程写成“同步的样子”，是 `async/await` 的雏形。

## Promise 的特性

- **executor 立即执行**：`new Promise(fn)` 里 `fn` 是同步跑掉的。
- **状态只变一次**：`pending → fulfilled / rejected`，之后不可逆。
- **`then` 返回新 Promise**，不是 `this`，所以能链式；`then` 里 `return` 的值会被 `Promise.resolve` 包一层。
- **无法取消**。
- **未捕获的 rejection 不会中断脚本**，只触发 `unhandledrejection` 警告。

## 四个分支

| 方法 | 什么时候成功 | 什么时候失败 |
|---|---|---|
| `all` | 全部成功 | 有一个失败就立刻失败（结果顺序仍按传入顺序） |
| `race` | 第一个**落定**的，成功或失败直接返回 | 同上 |
| `allSettled` | 全部落定，返回 `[{status, value/reason}]`，它本身不会失败 | — |
| `any` | 第一个成功 | 全部失败，抛 `AggregateError` |

## async / await

- `async` 函数返回值会被 `Promise.resolve` 包成 Promise。
- `await` 等价于 `then`：右边不是 Promise 会先被包成 Promise。
- `await` 之后的代码进微任务，所以它后面的逻辑总是让位给当前同步代码。
- **没有依赖的异步别串行 `await`**，那是白等，用 `Promise.all` 并发。
- 错误只能用 `try/catch` 抓（`await` 本身不走 `.catch`）。
- 跟 Promise 一样无法取消。

## 求值顺序题

```js
let a = 0
const b = async () => {
  a = a + await 10
  console.log('2', a)
}
b()
a++
console.log('1', a)
```

输出 `1 1`，再输出 `2 10`。

原因：等号右边**从左往右求值**——先读 `a`（此时是 0），再遇到 `await` 挂起；同步代码继续跑 `a++`，打印 `1 1`；微任务恢复后算 `0 + 10` 赋给 `a`，打印 `2 10`。

## 定时器

- `setTimeout` / `setInterval` **不保证准时**：主线程被占住，任务只能往后排。
- `setInterval` 的回调**可能堆积**：上一次没跑完，下一次已经到点。
- `requestAnimationFrame` 跟屏幕刷新走（60Hz 约 16.6ms），自带节流，适合动画，可以替代 `setInterval`。

## 手写 Promise 的思路

考点就五点，能说清楚就不用写：

1. **状态机**：`pending / fulfilled / rejected`，只能迁移一次，迁移后锁定。
2. **发布订阅**：`then` 时如果还没结果，回调先存进数组；`resolve` / `reject` 时统一拿出来执行。
3. **返回新实例**：`then` 必须返回一个新的 Promise，不能返回 `this`，否则状态不可逆就冲突了。
4. **值穿透**：`then` 不传函数时给个默认函数，保证链不断。
5. **错误捕获**：`executor` 和 `then` 的回调都要包 `try/catch`，出错就走 `reject`。

## 事件循环

一轮循环四步：

1. 跑完当前同步代码（整个 `script` 本身算一个任务）。
2. 调用栈空了，**清空微任务队列**——一直清到空，清的过程中新产生的微任务也要跑。
3. 浏览器按需决定要不要渲染一次。
4. 取下一个宏任务，回到第 1 步。

**微任务**：Promise 的 `then` / `catch` / `finally`、`queueMicrotask`、`MutationObserver`、`await` 之后的代码。

**宏任务**：`script` 本身、`setTimeout` / `setInterval`、I/O、事件回调、ajax 回调。Node 里还有 `setImmediate`，以及独立队列的 `process.nextTick`（比微任务还早）。

两个要说准的点：

- **微任务队列由 HTML 规范定义**（`queueMicrotask` 就是宿主 API），不是 ES 规范。ES 只定义了 Promise 的 job，由宿主排进微任务队列。
- **`await` 之后的代码和 `.then` 回调在同一个队列里，没有优先级**，谁先入队谁先执行。

## 什么时候渲染

- 微任务清空后，浏览器看帧率、页面有没有变化，决定要不要走一次渲染。
- 渲染内部顺序：`requestAnimationFrame` 回调 → 样式计算 → 布局（回流）→ 绘制（重绘）→ 合成。
- 渲染完如果还有空闲时间，才跑 `requestIdleCallback`。
- 所以同步代码改完 DOM 不会立刻上屏；要读到刚改完的布局，得放进 `requestAnimationFrame` 里读。

## 题目一

```js
async function async1() {
  console.log('async1 start')
  await async2()
  console.log('async1 end')
}
async function async2() {
  console.log('async2')
}
console.log('script start')
setTimeout(() => console.log('setTimeout'), 0)
async1()
new Promise((resolve) => {
  console.log('promise1')
  resolve()
}).then(() => console.log('promise2'))
console.log('script end')
```

输出：

```
script start
async1 start
async2
promise1
script end
async1 end
promise2
setTimeout
```

解释：`async1 start`、`async2`、`promise1`、`script end` 都是同步的。`async1` 先调用，所以它的续体先入微任务队列；`async1 end` 排在 `promise2` 前面，只是**入队顺序**，不是 await 有什么更高优先级。宏任务最后跑。

## 题目二

```js
async function async1() {
  console.log('async1 start')
  await async2()
  console.log('async1 end')
}
async function async2() {
  await async3()
  console.log('async2')
}
async function async3() {
  console.log('async3')
}
console.log('script start')
setTimeout(() => console.log('setTimeout'), 0)
async1()
new Promise((resolve) => {
  console.log('promise1')
  resolve()
}).then(() => console.log('promise2'))
  .then(() => console.log('promise3'))
console.log('script end')
```

输出：

```
script start
async1 start
async3
promise1
script end
async2
promise2
async1 end
promise3
setTimeout
```

解释：`async1` 挂起在 `await async2()`，`async2` 挂起在 `await async3()`，这时队列里只有 `async2` 的续体和 `promise2`。`async2` 的续体跑完，async2 这个 Promise 才兑现，`async1` 的续体这时才入队——所以 `async1 end` 被挤到 `promise2` 后面。

一句话记住：**`await` 一个返回 Promise 的函数，比 `await` 一个普通值多排一个微任务**。
