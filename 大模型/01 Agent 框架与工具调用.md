## 一、Agent 基础概念

### Agent 与普通 LLM 调用、Workflow（固定流程编排）的本质区别是什么？什么场景该用 Agent，什么场景不该用？

**一句话结论：区别不在「用不用大模型」，而在「下一步由谁决定」** —— 调用是模型答一次，Workflow 是代码定死路径，Agent 是模型自己决定下一步做什么、做几步。

| 维度 | 普通 LLM 调用 | Workflow | Agent |
| --- | --- | --- | --- |
| 控制流 | 一次性输入 → 输出 | 开发者写死的 DAG / 步骤 | 模型根据观察结果动态决定 |
| 步数 | 1 | 固定 | 不固定，可能循环 |
| 工具 | 通常无 | 按预设节点调用 | 模型自主选择、可重试换工具 |
| 可预测性 | 高 | 最高 | 最低 |
| 单次成本 / 延迟 | 低 | 中 | 高且波动大 |

判断是否该上 Agent，按这三条过一遍：

1. **路径能否预先写死**：能写清楚「先查 A，再算 B，然后返回 C」的，用 Workflow，别用 Agent。
2. **是否需要看结果才知下一步**：例如「先搜一下，搜不到就换个关键词、再不行去查数据库」—— 这种分支依赖环境反馈，才是 Agent 的用武之地。
3. **错误代价是否可承受**：Agent 会多花几倍 token、可能走偏甚至重复执行有副作用的操作，代价高的场景要加人工关卡。

**明确不该用 Agent 的场景**：

- 固定格式转换、分类、抽取、摘要 —— 一次调用 + 结构化输出就够。
- 高确定性批处理、报表生成 —— 需要可复现，不能容忍「这次和上次不一样」。
- 延迟敏感的接口（如搜索框联想）—— Agent 的多步循环扛不住。
- 高并发低成本场景 —— 成本会随步数线性放大。

> 面试加分的一句：现实中更多是**混合结构** —— 主干用 Workflow 保证确定性，只在「需要判断」的局部节点嵌一个 Agent。**先写成 Workflow，把不确定的那一两个节点换成 Agent**，比一上来全自主更稳。

### 解释 ReAct 范式；它和 Plan-and-Execute、Reflection、Multi-Agent 模式各自适用什么场景？

**一句话结论：它们都是「如何组织多步推理」的策略，差别在「什么时候做计划」和「依据什么改进行动」**。

| 范式 | 核心循环 | 适用场景 | 主要代价 |
| --- | --- | --- | --- |
| **ReAct** | Thought → Action → Observation 交替，边做边想 | 工具型任务、需要边查边调整（客服查询、检索问答） | 每步都要调模型，步数一多成本高、容易跑偏 |
| **Plan-and-Execute** | 先一次性拆出完整计划，再逐步执行，必要时 replan | 步骤可预估、且希望少调用大模型的长任务 | 初始计划错就全盘错，环境变化时要能重规划 |
| **Reflection** | 执行 → 自评/外部校验 → 修订 → 再执行 | 质量比速度重要的产出（代码、文案、SQL） | 轮数翻倍，且「自己评自己」不一定可靠 |
| **Multi-Agent** | 多角色分工 + 消息传递 / 移交（handoff） | 需要不同专长或相互制衡（审查 + 执行、研究 + 写作） | 通信开销、状态一致性、调试复杂度陡增 |

选择时的三个判断点：

- **任务步数能不能提前估**：能 → Plan-and-Execute；不能 → ReAct。
- **有没有客观校验器**：有（单测、编译、规则校验）→ Reflection 才有效；只靠模型自评 → 收益很小。
- **是不是真的需要多角色**：多 Agent 最常见的翻车原因是「本来一个 Agent 就能做完，却拆成三个互相传话」。链式成功率是乘法衰减的：单步 90%，十步只剩约 35%。

> 一个实用组合：ReAct 做执行循环，Reflection 只在关键节点做一次校验，Plan 只用于给用户展示进度。三层全开通常不划算。

### Agent 的核心组成部分有哪些（模型、工具、记忆、规划、环境反馈）？

**一句话结论：Agent = 一个能拿反馈、能改状态、能反复调用的模型循环**，五个部件各自对应一段工程实现。

| 部件 | 职责 | 工程上对应什么 |
| --- | --- | --- |
| **模型** | 推理与决策，选下一步动作 | 主模型 / 小模型路由、temperature 设置、结构化输出约束 |
| **工具** | 让模型能对外界产生影响或获取信息 | Tool schema、权限、超时、幂等性、错误处理 |
| **记忆** | 跨步骤、跨会话保留状态 | 短期：State / Checkpointer / Redis；长期：向量库 + 结构化库 / Store |
| **规划** | 把目标拆成步骤、决定顺序 | Prompt 里的计划指令、Plan 节点、todo 状态字段 |
| **环境反馈** | 告诉模型「上一步做成了没有」 | 工具返回值、执行报错、检索结果、校验器结论、用户回复 |

最容易忽略的是**环境反馈的质量**：

- 工具只返回 `success` 不够，要返回**足够模型判断下一步的信息**（例如「未找到该订单，库里有 3 个相近 ID」）。
- 报错要变成**可行动的提示**，不能把一整页 traceback 塞回上下文（既贵又干扰）。
- 没有反馈的 Agent 就退化成「盲猜多轮」，这是很多 demo 效果差、上生产就崩的根因。

> 讲这一题时把「循环」画出来：拼上下文 → 调模型 → 解析动作 → 执行工具 → **把结果写回状态** → 判断是否结束。最后那一步「写回状态」就是记忆与反馈的交界。

### 什么是 Function Calling / Tool Calling？底层是模型输出结构化 JSON，还是框架做了解析？

**一句话结论：模型输出的是「要调用哪个函数、参数是什么」的结构化内容；框架负责声明、解析、执行和回填，模型自己不执行任何代码**。

一次完整调用链路：

1. **声明**：开发者把工具名、用途、参数 JSON Schema 随请求发给模型。
2. **决策**：模型经过专门训练，输出一个结构化的 `tool_call`（函数名 + 参数），而不是普通自然语言。
3. **解析**：框架/SDK 校验参数、反序列化成本地对象 —— 这一步是框架做的。
4. **执行**：**你的代码**真正去跑函数、查数据库、发 HTTP 请求。
5. **回填**：把结果作为 `tool` 角色消息追加进上下文，再次调用模型，让它决定结束还是继续调下一个工具。

需要澄清的三点：

- 「输出 JSON」不是靠提示词求出来的，是模型在训练阶段学会的一种**受约束的生成模式**；参数仍可能不合法，所以第 3 步的校验不能省。
- **模型永远不执行函数**，所谓「模型调用了工具」是简写。安全边界全在你的执行层。
- 参数来自模型输出，等同于**不可信输入**：路径、SQL、命令都要按用户输入的标准做校验和权限检查。

> 追问常见陷阱：模型一次返回多个 tool_call 时，执行顺序、失败后的重试、以及「并行调用之间有依赖」怎么处理 —— 这属于下一章工具设计的内容。

### Function Calling 和 MCP（Model Context Protocol）是什么关系？MCP 解决了什么问题？

**一句话结论：两者不在同一层 —— Function Calling 是「模型怎么表达我要调工具」，MCP 是「工具怎么被找到、连接和复用」，是互补而非替代**。

MCP 解决的是 **N×M 集成问题**：以前每个 AI 应用（N）接每个数据源/工具（M）都要写一套专用适配；MCP 定义统一协议后，工具方实现一次 server，任何支持 MCP 的客户端都能用（常被比作「AI 应用的 USB-C」）。

| 对比 | Function Calling | MCP |
| --- | --- | --- |
| 层次 | 模型能力 / API 特性 | 开放协议（工具与应用的连接标准） |
| 关注点 | 单次调用的意图表达与参数格式 | 工具发现、能力协商、鉴权、传输 |
| 谁实现 | 模型厂商 + 你的调用代码 | Server 提供方 + Client/Host 应用 |
| 能否互相替代 | 不能 | 不能（MCP 工具最终仍要转成一次 tool call） |

**MCP 的架构与能力**：

- 三个角色：**Host**（用户使用的 AI 应用）、**Client**（Host 内的连接器）、**Server**（暴露能力的一方）。
- Server 暴露三类能力：**Tools**（可执行函数）、**Resources**（可读数据）、**Prompts**（可复用模板）。
- 消息基于 **JSON-RPC 2.0**；本地走 stdio，远程走 **Streamable HTTP**。
- 生态时间线：2024 年 11 月由 Anthropic 开源；**2025 年 12 月捐给 Linux 基金会旗下的 Agentic AI Foundation（AAIF）**成为创始项目；官方 Registry 用于发现公开 server。2026-07-28 规范修订进一步转向**无状态**（移除 initialize 握手和协议级 session），方便用普通负载均衡横向扩容。

> 面试可以顺带说风险：接第三方 MCP server 等于把外部工具接进你的 Agent，恶意或含注入内容工具的 server 会扩大攻击面；权限、来源审查和调用审计不能因为「是标准协议」就省掉。

### Agent 的自主性越高越好吗？如何权衡可控性与自主性？

**一句话结论：不是。自主性应该按「动作的错误代价 × 是否可撤销」逐档授予，而不是给整个 Agent 一个全局开关**。

实践里的分级授权：

1. **只读、无副作用**（检索、查询、计算）—— 可以完全自主，出错最多是答错。
2. **写入内部系统、可回滚**（建草稿、写工单备注、生成 PR）—— 可自主执行，但留审计日志和撤销入口。
3. **对外或有资金/数据影响**（发邮件、改线上配置、退款、删数据）—— 必须人工确认或走审批流。
4. **不可逆高险动作**（转账、批量删除、生产发布）—— 原则上不给 Agent 直接权限，由人执行。

把可控性落到工程上的手段：

- **白名单 + 最小权限**：Agent 用的凭证只有完成本任务所需的最小范围。
- **步数与预算上限**：`recursion_limit` / 最大工具调用次数 / token 预算，防止失控循环烧钱。
- **中断与人工关卡**：高风险节点前 `interrupt`，人批准后才继续（LangGraph 的 HITL 就是干这个）。
- **结构化输出 + 校验器**：动作参数先过 schema 和业务规则，不合法直接拒绝而不是让模型重试碰运气。
- **可观测 + 可回滚**：每一步留 trace，出事能定位、能撤销。

> 一句话能收尾：自主性不是能力指标，是**风险决策**。行业里落地成功的 Agent 几乎都是「窄任务 + 明确成功标准 + 关键动作留人工关卡」，而不是全自主助手。

## 二、LLM 基础

### Token、上下文窗口、temperature、top_p 分别是什么？Agent 场景下 temperature 怎么设？

**一句话结论：前两个是「容量」，后两个是「采样随机性」；Agent 里默认把随机性压到最低，因为多步循环会放大任何一点不稳定**。

| 概念 | 含义 | 工程影响 |
| --- | --- | --- |
| **Token** | 模型处理的最小文本单位（中文大致 1 字 ≈ 1~2 token） | 直接决定费用与延迟；输入和输出都要计费，输出更贵 |
| **上下文窗口** | 单次请求能容纳的 token 上限（含系统提示、历史、工具结果、输出预留） | Agent 每步都重发上下文，长任务会「挤爆」窗口 |
| **temperature** | 缩放 logits，越大分布越平、越随机 | 高值让输出发散，工具参数容易不合法 |
| **top_p** | 只从累计概率达 p 的候选里采样（核采样） | 与 temperature 同属随机性旋钮 |

**Agent 场景的建议**：

- 工具选择、参数生成、路由判断、结构化抽取：设 **`temperature=0`（或 0~0.2）**，追求可复现。
- 需要创意文案、多方案发散时，才单独在某个节点调高，不要全局调高。
- **不要同时调 temperature 和 top_p**，两个旋钮叠加后行为难预测，调一个即可（多数团队只动 temperature）。
- 即使设为 0 也不保证严格确定（模型版本更新、并行计算、供应商侧变化都会带来差异），所以**别把「可复现」寄托在参数上**，要靠结构化输出 + 校验 + 评估集。

> 容易被追问的点：窗口大不等于可以全塞满。长上下文存在「迷失在中间」和准确率随长度衰减的现象，塞得越满越容易忽略关键指令 —— 这正是第六章上下文工程要解决的问题。

### 什么是幻觉？在 Agent 中有哪些缓解手段？

**一句话结论：幻觉是模型生成了看似合理但与事实/上下文不符的内容；在 Agent 里更危险，因为它会直接变成一次错误的工具调用**。

按四层来防，从内到外：

- **模型与解码层**：降低 temperature；要求结构化输出；给明确的「不知道就说不知道 / 不允许编造」指令。
- **上下文层**：用 RAG 提供可引用的证据；**要求答案附来源片段**；把工具真实返回值写回上下文，不让模型凭记忆续写。
- **工具与校验层**：参数过 schema 校验；关键事实由**确定性系统**核对（查库、算数、跑代码），不让模型自己算；工具返回「未找到」时明确告知模型而不是空字符串。
- **流程层**：关键结论做一次独立复核（第二个模型或规则校验器）；高风险动作加人工确认；全程留 trace 便于事后定位。

两个容易踩的坑：

- 「加一句『不要幻觉』」几乎无效，**必须有外部事实源和校验器**。
- 检索结果为空时，模型最容易开始编。工程上要把「无结果」当成一种明确状态处理，直接走兜底回答或追问用户。

> 讲这题时把因果说清：普通聊天里幻觉是「答案不好」，Agent 里幻觉会**被工具放大成副作用**（改错数据、发错邮件），所以缓解重点放在执行层而不是提示词层。

### 如何让模型稳定输出结构化 JSON？（JSON mode、Structured Output、Pydantic 校验、重试修复）

**一句话结论：可靠性来自「层层加固」，优先级是 严格 Structured Output > JSON mode > 提示词约束 + 校验重试**，只靠提示词求 JSON 一定会在边缘情况翻车。

四道防线，按顺序上：

1. **约束解码（首选）**：用厂商的 Structured Output / 严格模式，传入 JSON Schema，服务端保证输出符合 schema。这是目前最稳的一层，`response_format` 里带 `strict: true` 一类开关。
2. **JSON mode**：只保证「是合法 JSON」，**不保证符合你的字段结构**。比纯提示词好，但仍需校验。
3. **本地校验**：用 Pydantic（Python）/ Zod（TS）定义模型，解析失败就抛错。校验器是兜底，不是可选项。
4. **错误回填重试**：把校验错误信息作为新一轮输入，让模型**只修错误的那部分**；设最多 2~3 次，超限走降级（默认值 / 人工 / 报错）。

```python
from pydantic import BaseModel, Field, ValidationError

class Intent(BaseModel):
    action: str = Field(description="create_order | query_order | other")
    order_id: str | None = None
    confidence: float = Field(ge=0, le=1)

def parse_intent(raw: str) -> Intent:
    try:
        return Intent.model_validate_json(raw)
    except ValidationError as e:
        # 把 e 的具体字段错误回填给模型，限定重试 2 次
        raise
```

配套的几个细节：

- **字段尽量用枚举和必填**，少用自由文本；可选字段显式给 `null`，别让模型省略。
- 数值、日期、ID 用字符串还是数字要在 schema 里定死，否则模型会来回变。
- **别在提示词里塞一整段 JSON 示例就以为万事大吉** —— 示例（few-shot）能提升格式稳定性，但替代不了约束解码。
- 校验失败率要监控：突然升高通常意味着上游 prompt 或模型版本变了，是个很好的回归信号。

### Prompt 工程常用技巧有哪些（Few-shot、CoT、角色设定、分隔符、输出约束）？

**一句话结论：这些技巧本质都在做同一件事 —— 缩小模型的解空间，让它更容易收敛到你要的格式与内容**。

| 技巧 | 做什么 | 什么时候用 | 注意 |
| --- | --- | --- | --- |
| **Few-shot** | 给 2~5 个输入→输出示例 | 格式难描述、边界情况多 | 示例会占 token，且模型可能照抄示例里的具体值 |
| **CoT / 逐步推理** | 要求先写推理再给结论 | 多步判断、需要拆解 | 让「推理」暴露在最终输出里会浪费 token，可放在内部字段 |
| **角色设定** | 指定身份与专业背景 | 需要术语风格、语气一致 | 不能替代规则和事实，别指望角色设定防注入 |
| **分隔符 / 分区** | 用 XML 标签或 ``` 把指令、资料、用户输入隔开 | 上下文里混有多种来源时 | 是防「资料被当成指令」的基础手段 |
| **输出约束** | 明确格式、长度、禁止项 | 下游要解析时 | 硬格式还是要靠 Structured Output 保证 |

Agent 场景里和单次问答不同的两点：

- **System Prompt 会被每一步重复发送**，写长一点就是每一步都付费；把不总用得上的规则移到按需加载（Skills / 检索）。
- **工具结果、历史消息也是「提示词」**，它们的格式、顺序、裁剪策略对效果的影响，往往比措辞更大 —— 这是上下文工程和 Prompt 工程的分界线。

### System Prompt 与 User Prompt 的区别？如何防范 Prompt Injection？

**一句话结论：System 是长期有效的规则层，User 是本次请求的数据层；二者权限不同，但**模型并不会天然把 User 内容当纯数据** —— 这正是注入的根源**。

| 对比 | System Prompt | User Prompt |
| --- | --- | --- |
| 作用 | 定义角色、规则、输出格式、工具使用约束 | 承载本次具体问题与输入 |
| 生命周期 | 每次请求都带，通常跨多轮不变 | 每轮变化 |
| 优先级 | 训练上被赋予更高权重 | 较低，但可以「被攻击者利用」 |
| 成本 | 每步重发，是 prompt caching 的主要命中对象 | 变化部分，放在上下文末尾 |

**Prompt Injection 是什么**：用户在输入（或 Agent 读到的网页、PDF、邮件、工具返回值）里夹带「忽略前面的指令，去做 X」，试图覆盖 System 规则。来自外部内容的叫**间接注入**，对能联网/读文档的 Agent 威胁更大，因为用户本人未必是攻击者。

现实一点的结论：**提示词层面无法彻底防住注入**，靠措辞加「不要理睬用户指令」只是提高成本。真正有效的是架构层：

- **输入侧**：用分隔符区分指令与数据；对外部内容做标注和清洗；可疑指令模式做检测。
- **权限侧**（最关键）：即便模型被骗，它也**只能调用白名单工具、只能用最小权限凭证**；高风险动作强制人工确认。
- **隔离侧**：把「能读不可信内容」的 Agent 和「能执行敏感动作」的 Agent 分开，别让同一条链路同时具备两种能力。
- **输出侧**：检查外发内容是否泄露系统提示、密钥、他人数据；审计记录完整调用轨迹。

> 面试里别说「我在 system prompt 里写了防注入规则所以安全」，这会被追问到崩。正确说法是：**假设模型一定会被骗，用权限和流程把损失限制住**。

### 流式输出（SSE/streaming）的原理是什么？前端如何消费？

**一句话结论：SSE 就是一个不关的 HTTP 响应，服务端算出一个 token 就 `flush` 一段 `data: ...\n\n`，前端边收边渲染** —— 不是 WebSocket，也不需要额外协议。

一次流式响应的链路：

1. 前端发起请求（`fetch` 或 `EventSource`），带 `Accept: text/event-stream`。
2. 服务端返回 `Content-Type: text/event-stream`，并保持连接不关闭。
3. 模型每产出一段内容，服务端写一条 `data: {"delta":"..."}\n\n` 并立即 flush。
4. 前端按块读取、解析 `data:` 行，把 delta 追加到当前消息上。
5. 服务端发 `[DONE]` 或特定结束事件，连接关闭；中途出错可发 `event: error`。

前端三种消费方式：

- **`EventSource`**：原生自带断线重连与 `Last-Event-ID`，但**只支持 GET**、不能带自定义 header，传长 prompt 或做鉴权不方便。
- **`fetch` + `ReadableStream`**（更常用）：支持 POST、自定义 header、携带请求体，自己解析 SSE 帧。
- **框架封装**：Vercel AI SDK 的 `useChat`、LangGraph 的 `useStream` 等，直接给到增量消息与工具调用事件。

```ts
const res = await fetch('/api/chat', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ message })
})
const reader = res.body!.getReader()
const decoder = new TextDecoder()
while (true) {
  const { done, value } = await reader.read()
  if (done) break
  const chunk = decoder.decode(value, { stream: true })
  // 注意：一个 chunk 可能含半条 / 多条 SSE 帧，要按 \n\n 缓冲切分
  appendToUI(chunk)
}
```

几个上线必踩的坑：

- **Nginx / 反向代理会缓冲流式响应**，要设 `X-Accel-Buffering: no`（或 `proxy_buffering off`），否则前端看到的是「等很久一次性出现」。
- **chunk 不等于一帧**，可能截断半条 JSON，必须先按 `\n\n` 拼缓冲再解析。
- Agent 场景流的不只是正文，还有**思考过程、工具调用开始/结束、状态事件**，建议自定义事件类型（`event: tool_call`）而不是全塞进 `data:` 文本。
- 断线重连要有幂等设计：靠 `Last-Event-ID` 或服务端保存的增量游标续传，别让用户刷新后从头重跑一遍昂贵的 Agent 任务。

## 三、LangChain

### LCEL（LangChain Expression Language）的设计思想是什么？Runnable 接口有哪些核心方法（invoke/stream/batch）？

**一句话结论：LCEL 把「提示词 → 模型 → 解析器」这条链统一成可组合的 `Runnable`，用管道符 `|` 拼起来，从而免费获得流式、批量、异步和并发能力**。

设计思想拆成三点：

- **统一抽象**：PromptTemplate、ChatModel、OutputParser、Retriever、甚至普通函数都实现同一套 `Runnable` 接口，因此能任意拼接。
- **声明式组合**：`chain = prompt | model | parser`，框架负责把上一环输出喂给下一环，不用手写中间变量。
- **能力自动透传**：只要每一环都支持流式，整条链就支持流式；同理批量、异步、fallback、重试都由框架统一处理。

`Runnable` 的核心方法：

| 方法 | 作用 | 典型用法 |
| --- | --- | --- |
| `invoke` | 单输入 → 单输出，最常用 | 一次请求拿到完整结果 |
| `stream` | 逐块产出输出 | 前端打字机效果 |
| `batch` | 多输入并行处理 | 离线批量评测、批量抽取 |
| `ainvoke` / `astream` / `abatch` | 对应的异步版本 | FastAPI 的 `async def` 里必须用异步版，否则阻塞事件循环 |

配套但同样常问的：`with_config`（注入 tags / callbacks / run_name，是 Tracing 打标的基础）、`with_fallbacks`（模型降级）、`with_retry`（重试）。

> 讲清价值的一句话：**不用 LCEL 也能写链，但要自己实现流式透传、并发、错误处理和可观测埋点**；LCEL 卖的是这些横切能力的统一，不是语法糖。

### 如何自定义一个 Tool？Tool 的描述（description）为什么对效果影响很大？

**一句话结论：工具描述就是模型选工具时唯一能看到的「文档」** —— 参数 schema 告诉模型怎么填，description 决定它**会不会选、什么时候选**。

自定义一个 Tool 的三要素：

1. **名称**：动宾结构、语义唯一（`search_order_by_id`，不要 `tool1` / `handle`）。
2. **参数 schema**：字段类型、必填、取值范围、单位、格式都写清；用 Pydantic / Zod 定义最稳。
3. **description**：说清「能干什么、不能干什么、什么时候该用、返回什么」，最好附 1~2 个示例。

```python
from langchain_core.tools import tool
from pydantic import BaseModel, Field

class OrderArgs(BaseModel):
    order_id: str = Field(description="订单号，格式 ORD- 加 8 位数字")

@tool(args_schema=OrderArgs)
def query_order(order_id: str) -> str:
    """按订单号查询订单状态与金额。
    仅用于用户已提供订单号的场景；不要用于按用户名或时间范围搜索，
    后者请用 search_orders。查不到时返回 'NOT_FOUND'。"""
    ...
```

**描述差会具体导致什么**：

- 太短或太泛（「查询数据」）→ 模型在多个相似工具间乱选，或该用时不用。
- 没写边界 → 把「按订单号查」误用于「按用户名查」，参数编造，工具报错。
- 没写返回值形态 → 模型不知道 `NOT_FOUND` 该怎么处理，可能编一个结果出来。
- 多个工具描述高度重叠 → 选择准确率明显下降（下一章「工具太多」会展开）。

> 一个很实用的验证法：把工具列表单独给一个模型，用十几条真实用户问法测「它会选哪个」，这就是最小版的**工具选择评估集**。改描述要像改代码一样跑回归。

### OutputParser、PromptTemplate、ChatModel 各自的职责？

**一句话结论：这三者是 LCEL 链上最经典的三个环节 —— 组装输入、产生输出、把输出变成程序能用的对象**。

| 组件 | 输入 → 输出 | 职责 | 常见坑 |
| --- | --- | --- | --- |
| **PromptTemplate** | 变量 dict → 消息/字符串 | 拼模板、填变量、分区与占位 | 变量没填会报错；把用户输入直接拼进模板容易引入注入 |
| **ChatModel** | 消息列表 → `AIMessage` | 调模型推理 | 返回的是消息对象不是纯文本；同步方法用在异步接口里会阻塞 |
| **OutputParser** | 模型输出 → 结构化对象 | 解析、校验、格式化 | 只解析不校验；解析失败没有重试/降级 |

补充两点：

- 现代写法里 OutputParser 的角色**正在被 Structured Output 取代**：与其「让模型吐 JSON 再解析」，不如直接传 schema 让服务端约束输出（`with_structured_output`），解析失败率大幅下降。
- 三者之间的边界其实就是**数据形态转换**：dict → messages → AIMessage → 业务对象。排查链上问题时，逐环打印输入输出是最快的定位方式。

### LangChain 的 Memory 有哪些实现？各自的优缺点（Buffer、Window、Summary 等）？

**一句话结论：Memory 的本质是「每轮调用前，往上下文里塞哪些历史」，不同实现只是在「保留多少」和「花多少 token」之间取舍**。

| 实现 | 保留策略 | 优点 | 缺点 |
| --- | --- | --- | --- |
| **Buffer**（全量） | 全部历史原样带 | 信息无损、实现最简单 | token 随轮数线性增长，长会话必爆窗口、必变贵 |
| **Window**（最近 k 轮） | 只留最近 k 条 | 成本可控、实现简单 | 早期关键信息会「突然失忆」，且可能把一轮对话从中间截断 |
| **Summary**（摘要） | 用模型把旧历史压成摘要 | 长会话成本平稳，能保留要点 | 摘要本身要额外调模型；细节会丢失，且摘要可能累积失真 |
| **Summary + Buffer 混合** | 近期原文 + 远期摘要 | 兼顾细节与成本 | 实现复杂，切换时机要调 |
| **检索式 / 实体记忆** | 按需召回相关片段或事实 | 适合超长、跨会话场景 | 需要向量库与召回策略，可能召回到无关内容 |

**但在 Agent / 多轮生产系统里，更该说的答案是**：

- 传统 `ConversationBufferMemory` 这类老式 Memory 类已属**旧范式**，2025 年之后主流做法是**把状态交给 LangGraph 的 Checkpointer 管理**（按 `thread_id` 持久化），长期事实交给 `Store`。
- 区分清楚两条线：**会话状态**（这一轮对话的消息、中间产物）与**长期记忆**（跨会话的用户偏好、事实），前者不该塞进 Memory 类，后者不是「多留几轮历史」能解决的。

> 面试讲这题别停在背四个类名，落到一句工程判断：**窗口是有限预算，Memory 策略就是在预算内决定保留什么、丢弃什么、压缩什么**。

### 你觉得 LangChain 有哪些缺点？为什么有人说它「过度封装」？什么时候不该用它？

**一句话结论：批评集中在「抽象层太厚」—— 简单的模型调用被包了好几层，出问题时很难看清究竟发了什么给模型**；但要分清被诟病的老版本和 1.0 之后的收敛。

常见的具体吐槽：

- **调试困难**：层层封装 + 默认回调，栈很深，想看「最终请求体」往往要开 verbose / Tracing 才看得清。
- **抽象泄漏**：真要定制行为时，得先理解 Chain / Runnable / Callback / Memory 一整套概念，学习成本高于直接写几十行代码。
- **版本变动快**：早期 API 频繁更名弃用，升级成本高；`AgentExecutor`、各类 `Memory` 类都属被淘汰的一代。
- **隐性行为**：默认重试、默认解析、默认提示模板都会改你的输入，线上出现「我明明没这么写」的效果。

**客观一点的补充**：LangChain **1.0**（2025 年 10 月）已经明显收敛 —— 包体裁剪到核心抽象，旧功能移到 `langchain-classic`，`create_agent` 直接构建在 LangGraph 之上，文档也统一到 `docs.langchain.com`。所以「过度封装」的批评有相当一部分是**针对 0.x 时代**的，面试时点出这一层会比单纯吐槽更显判断力。

**什么时候不该用**：

- 只有一两次模型调用、格式固定 —— 直接调 SDK，二十行搞定。
- 需要精确控制每一字节的请求、超时、重试、计费归因 —— 框架默认值反而是干扰。
- 团队不做复杂编排、也不打算用它的可观测生态 —— 引入依赖却只用 5% 的能力，不划算。
- 已有自研编排 / 强合规要求必须完全掌握调用链。

**什么时候值得用**：需要快速拼出标准 Agent、需要统一的流式/批量/异步、要接 LangSmith 做 Tracing、或者工作流确实复杂到需要 LangGraph 的状态与断点能力。

> 一句稳妥的收尾：**框架该不该用，取决于你是否需要它替你管理复杂性；如果业务本身的复杂度低于框架本身的复杂度，就是净负担**。

## 四、LangGraph

### LangGraph 与 LangChain 的 AgentExecutor 相比解决了什么问题？为什么要用「图」来建模 Agent？

**一句话结论：AgentExecutor 是一个写死的黑盒 while 循环，LangGraph 把循环拆成显式的节点和边，于是状态可查、可暂停、可恢复、可回溯**。

AgentExecutor 的具体局限：

- 循环逻辑内建，想插入「执行前先审批」「失败后走另一个分支」「某个节点并行」都要绕开框架改写。
- 状态是框架内部的，难以查看、持久化、修改或重放。
- 没有一等公民的**持久化 / 中断 / 回溯**，长任务崩了就得从头跑。

用图建模换来的四件东西：

1. **显式控制流**：条件边写清楚「什么情况走哪条路」，代码即流程图，评审和排错都容易。
2. **可持久化状态**：每个 super-step 存一次 checkpoint，进程重启、部署、崩溃后能从断点继续。
3. **一等公民的人工介入**：任意节点可以 `interrupt` 暂停，人批准后再 `Command(resume=...)` 继续。
4. **确定性 + 自主性可混编**：固定步骤用普通函数节点，需要判断的节点才放模型，两者画在同一张图里。

**版本现状**（2026 年 11 月）：

- **LangGraph 1.0 于 2025-10-22 GA**，定位是「durable agent runtime」，核心能力就是持久化执行、流式、HITL。
- 旧的 `AgentExecutor`、`langgraph.prebuilt.create_react_agent` **均已弃用**；官方推荐用 LangChain 的 `langchain.agents.create_agent`，它本身就跑在 LangGraph 上。
- 因此现在更准确的说法不是「LangChain vs LangGraph 二选一」，而是**高层用 `create_agent` 起步，需要精细控制时下潜到 LangGraph 写图**，两者可组合。

> 面试里的高信号回答：从 AgentExecutor 到 LangGraph，本质是把 Agent 从「一段会跑的脚本」变成「一个可运维的状态机」—— 生产环境真正缺的从来不是更聪明的模型，而是崩溃可恢复、动作可审计。

### State、Node、Edge、Conditional Edge 分别是什么？如何设计一个 State Schema？

**一句话结论：State 是全局共享的数据对象，Node 是读写它的函数，Edge 决定下一个跑谁，Conditional Edge 用函数返回值做动态路由**。

| 概念 | 是什么 | 关键点 |
| --- | --- | --- |
| **State** | 一张图共用的状态（TypedDict / Pydantic / dataclass） | 节点不直接互相传参，只通过 State 交互；字段要声明 reducer |
| **Node** | `fn(state) -> 部分状态更新` | 可以是模型调用、工具执行、纯函数；返回的是**增量**，不是完整 State |
| **Edge** | 固定的 `A → B` | 用 `add_edge`，适合确定性顺序 |
| **Conditional Edge** | `A → (B 或 C 或 END)` | `add_conditional_edges`，路由函数读 State 返回下一个节点名 |
| **START / END** | 入口与终止 | 条件边最常见的返回值就是 `END` |

设计一个 State Schema 的实操顺序：

1. **先列「决策需要的信息」**：`messages`、`user_id`、当前计划、检索结果、待执行的动作、重试次数。
2. **再列「只做输出的信息」**：最终答案、审计字段、耗时统计 —— 这些可以不参与路由判断。
3. **给每个字段定 reducer**：累加型（消息列表）用 `add_messages`；覆盖型（当前计划）默认直接替换；别混用。
4. **控制体积**：不要把整份文档、原始 HTML、大段 traceback 塞进 State —— 它每个 checkpoint 都会被序列化存一遍。
5. **敏感字段单独考虑**：凭证、PII 不要进 State（会被持久化到数据库）。

```python
from typing import Annotated, TypedDict
from langgraph.graph.message import add_messages

class AgentState(TypedDict):
    messages: Annotated[list, add_messages]   # 累加
    user_id: str                              # 覆盖
    plan: list[str]                           # 覆盖
    retries: int                              # 覆盖，用于终止判断
    needs_approval: bool                      # 覆盖，用于条件边路由
```

> 常见翻车点：State 里塞了一个不可序列化的对象（数据库连接、client），Checkpointer 保存时直接报错。**连接、客户端这类资源放全局或运行时注入，不要放 State**。

### Reducer 是什么？为什么 messages 字段要用 add_messages？不写 Reducer 会发生什么？

**一句话结论：Reducer 决定「节点返回的更新如何合并进 State」；不写就默认覆盖，多轮对话会被最后一次输出冲掉**。

两种语义对比：

- **默认（无 reducer）**：新值**直接替换**旧值。适合 `plan`、`retries`、`current_step` 这类「当前状态」字段。
- **`add_messages`**：把新消息**追加**到列表，并按消息 ID 做去重/更新（同一 ID 的新内容会替换旧的，而不是无限追加）。

**为什么 messages 必须用 `add_messages`**：Agent 每一轮都会产生新的 `AIMessage` / `ToolMessage`，如果默认覆盖，下一轮模型就只能看到最后一条消息，等于**每步都失忆**，循环推理直接失效。

不写 reducer 的具体后果：

1. 节点返回 `{"messages": [new_ai_message]}`，State 里的历史被整体替换成只有这一条。
2. 下一轮拼给模型的上下文里没有用户原始问题、没有之前的工具结果。
3. 模型开始重复提问、重复调同一个工具，或因为缺少工具结果而编造答案。
4. 如果节点还返回了异常，`messages` 甚至可能被写成不完整结构，后续解析报错。

其他要注意的：

- 自定义 reducer 必须**满足结合律且无副作用**，因为 checkpoint 重放、并行节点合并都会重复调用它。
- 并行节点同时写同一字段时，若没有合适的 reducer 会抛冲突错误 —— 这正是并行设计时必须先想清楚「谁写什么」的原因。
- 想主动删除/裁剪历史，用 `RemoveMessage` 配合 `add_messages`，而不是绕过 reducer 直接赋值。

### Checkpointer 的作用是什么？如何实现多轮对话的持久化与按 thread_id 区分会话？

**一句话结论：Checkpointer 在每个 super-step 把 State 存成一个 checkpoint，用 `thread_id` 把一串 checkpoint 归到同一个会话，从而实现「记住上下文」和「崩了能续跑」**。

它支撑的四个能力：

- **多轮记忆**：新一轮 invoke 时自动加载该 thread 的最新状态，不用自己维护历史表。
- **崩溃恢复 / 持久执行**：进程重启、部署、长任务中断后，从最后一个 checkpoint 继续，不丢已完成步骤。
- **人工介入**：`interrupt` 暂停时状态已落盘，人可能几小时后才批准，照样能恢复。
- **Time Travel**：能读取历史 checkpoint、从任意一步分叉重跑。

按 `thread_id` 区分会话的做法：

```python
from langgraph.checkpoint.postgres import PostgresSaver

checkpointer = PostgresSaver.from_conn_string(DB_URI)
graph = builder.compile(checkpointer=checkpointer)

config = {"configurable": {"thread_id": "user_42:session_7"}}
graph.invoke({"messages": [...]}, config=config)   # 第一次
graph.invoke({"messages": [...]}, config=config)   # 同一会话，接着上次
```

关键点：

1. **`thread_id` 就是会话主键**，通常用 `用户ID + 会话ID` 组合；不同用户的 thread 绝不能混，否则会串话。
2. 编译图时传入 checkpointer，**调用时通过 config 传 thread_id**；漏传或传错等于开了一个新会话（表现为「上一轮说的话全忘了」）。
3. `InMemorySaver` 只适合本地开发 —— **进程重启就没了**，生产要用 Postgres / Redis 等持久化后端。
4. checkpoint 会随轮数增长，要有**保留策略**（只留最近 N 个 / 定期归档），别让表无限膨胀。

> 面试里很容易被追问「那长期记忆呢」：Checkpointer 管的是**单个 thread 内的短期状态**；跨会话的用户偏好、历史结论属于长期记忆，要用 `Store`，下一题会展开。

### 如何实现 Human-in-the-Loop？interrupt 和断点机制的原理是什么？

**一句话结论：`interrupt()` 在节点里主动暂停，把当前状态存进 checkpoint 并返回一个待决事件；外部拿到人的输入后用 `Command(resume=...)` 从同一节点继续，而不是从头重跑**。

完整流程：

1. 图**必须带 Checkpointer 编译** —— 暂停状态要落盘，否则无处恢复。
2. 在需要人工确认的节点里调用 `interrupt(payload)`，`payload` 里放待审批的动作、参数、风险说明。
3. 执行到此暂停，`graph.invoke` 返回带 `__interrupt__` 的结果，进程可以**直接结束**（人可能几小时后才处理）。
4. 后端把待办推给前端/审批系统；前端展示「要执行什么、影响什么」。
5. 人批准后，用**同一个 `thread_id`** 调用 `graph.invoke(Command(resume=approved_value), config)`。
6. `interrupt()` 的返回值就是这次 resume 传进去的值，节点继续往下走。

```python
from langgraph.types import interrupt, Command

def risky_action(state):
    decision = interrupt({
        "question": "确认发送这封邮件？",
        "to": state["draft"]["to"],
        "preview": state["draft"]["body"][:200],
    })
    if not decision.get("approved"):
        return {"status": "cancelled"}
    send_mail(state["draft"])
    return {"status": "sent"}
```

几个必须知道的限制：

- **`interrupt` 所在节点在恢复时会重新执行一遍函数体**，因此 `interrupt()` **之前**的代码不能有副作用（否则会发两次邮件）。把副作用放在 interrupt 之后，或拆成独立节点。
- 节点内的 `interrupt()` 不能包在 `try/except` 里吞掉，它是靠抛特殊异常实现暂停的。
- 同一步多个 `interrupt` 要按固定顺序、用索引匹配 resume 值。
- 1.0 起支持 **typed interrupts**（在 `StateGraph` 构造时声明中断类型），让待决数据结构可被类型约束，适合多审批点的复杂流程。

> 这题的高分点是**幂等意识**：暂停/恢复天然带来重放，凡是会对外产生影响的操作，都要按「可能被执行两次」来设计。

### 什么是 Time Travel（回溯/分叉状态）？适用于什么场景？

**一句话结论：因为每个 super-step 都存了 checkpoint，所以可以读取任意历史状态，从那一步改一点数据后重新往后跑，形成一条分叉**。

两个动作要分清：

- **回溯（查看）**：`get_state(config)` 读当前或指定 checkpoint 的状态；`get_state_history(config)` 列出该 thread 的所有 checkpoint（含 `checkpoint_id`、`next` 节点、来源）。
- **分叉（重跑）**：取某个历史 `checkpoint_id`，`update_state` 修改其中字段，再以该 checkpoint 为起点 `invoke(None, config)` 继续执行，得到一条新分支，原分支不受影响。

典型适用场景：

- **复现线上 bug**：拿出错那次运行的 checkpoint，改一个参数重放，验证是不是这里导致的。
- **人工纠错**：Agent 在第 3 步理解错了用户意图，人工修正 State 里的 `plan`，从第 3 步重新跑，不必让用户重述整段。
- **A/B 对比**：从同一分叉点，换 Prompt / 换模型 / 换工具描述各跑一次，比较轨迹和结果。
- **调试与演示**：给评审逐步展示「每一步 State 长什么样」。

限制与注意：

- **分叉不会撤销已经发生的外部副作用** —— 邮件发了就是发了。Time Travel 只回滚**内部状态**，不改外部世界。
- 需要 Checkpointer；`InMemorySaver` 重启后历史就没了。
- 历史 checkpoint 会占存储，生产要设保留窗口。

> 一句话区分：Checkpointer 让 Agent「能从断点继续」，Time Travel 让开发者「能挑任意断点重来」。前者是可靠性，后者是可调试性。

### 如何在 LangGraph 中实现并行节点执行（fan-out/fan-in）？

**一句话结论：fan-out 用「一个节点连多条普通边」实现，fan-in 靠「多个节点都指向同一个下游节点」+ 正确的 reducer 合并结果**。

实现方式：

- **静态 fan-out**：`add_edge("split", "worker_a")` 和 `add_edge("split", "worker_b")` 写两条边，同一 super-step 内 A、B 并行执行。
- **动态 fan-out**：节点返回 `Send("worker", arg)` 列表（map-reduce 模式），按数据条数动态生成并行任务，适合「对每个检索结果各跑一次评估」。
- **fan-in**：把 A、B 都连到 `join` 节点。LangGraph 会等**同一步的所有分支都完成**才进入 join，因此不会发生「只合并了一半」的竞态。

设计时必须先想清楚三件事：

1. **谁写哪个字段**：并行节点写同一个 State 字段，必须有能合并的 reducer（例如 `operator.add` 或自定义列表合并），否则报 `INVALID_CONCURRENT_GRAPH_UPDATE`。
2. **不要写不可合并的对象**：两个分支各写 `final_answer` 这种覆盖型字段必然冲突；改成各写 `results_a` / `results_b`，在 join 节点统一裁决。
3. **副作用隔离**：两个并行节点都去发同一条通知 = 发两次。要么收拢到 join 后统一执行，要么用幂等键。

```python
from operator import add
from typing import Annotated, TypedDict

class S(TypedDict):
    partials: Annotated[list[str], add]   # 并行分支往同一个列表追加

builder.add_edge("split", "worker_a")
builder.add_edge("split", "worker_b")
builder.add_edge("worker_a", "join")
builder.add_edge("worker_b", "join")
```

> 一个现实提醒：并行能降延迟，但**会同时放大 token 消耗和上游限流压力**。并行调用同一模型时先确认并发配额，并给每个分支设独立超时与失败降级。

### Subgraph 与 Multi-Agent（Supervisor / Swarm / Hierarchical）如何设计？

**一句话结论：Subgraph 解决「把一段复杂逻辑封装成一个节点」，Multi-Agent 解决「谁来主导下一步」；两者常一起用，但关注点不同**。

**Subgraph**：一个编译好的图被当作节点挂进父图。

- 适用场景：某段流程自成体系（检索子系统、审批子系统）、需要独立 State Schema、要被多处复用。
- 两种接法：**共享 State 字段**（父图直接读写，简单）或 **不同 Schema**（父节点里显式做输入映射 / 输出映射，隔离更好）。
- 价值：边界清晰、可单测、可复用；代价是调试时要跨两层 trace。

**三种主流 Multi-Agent 拓扑**：

| 拓扑 | 结构 | 适合 | 风险 |
| --- | --- | --- | --- |
| **Supervisor** | 一个中心 Agent 分派任务给专家 Agent，结果回收 | 任务类型可分类、需要统一把关 | 中心节点成为瓶颈和单点故障 |
| **Swarm / Handoff** | Agent 之间直接移交控制权，谁接手谁继续对话 | 客服分流、按意图转接 | 控制权来回踢皮球，容易绕圈 |
| **Hierarchical** | 多层 Supervisor，逐层下派 | 大型复杂任务、组织级流程 | 层数一多，延迟与成本急剧上升 |

设计要点：

- **先问是不是真的需要多 Agent**：很多「多 Agent」其实只是多个 Prompt 节点，用一张图 + 条件边就能做完，成本低得多。
- **每个 Agent 的工具集要收窄**：专家 Agent 只拿自己需要的工具，既提升选择准确率，也符合最小权限。
- **明确终止条件与最大移交次数**，防止互相推诿形成死循环。
- **通信用结构化消息**，别让 Agent 之间用自由文本互相转述需求（信息会在转述中失真）。
- 链式成功率是乘法：每增加一次移交，端到端成功率就乘一次该环节的可靠性。

> 一句实话：多 Agent 在生产里最大的成本不是 token，是**调试复杂度**。没有完整 Tracing 之前，别急着拆多个 Agent。

### LangGraph 中如何处理循环与终止条件？如何防止 Agent 陷入死循环（recursion_limit）？

**一句话结论：循环是「条件边指回前面的节点」，终止是「条件边返回 END」；防死循环靠硬上限 + 软件条件双保险**。

让循环可控的四层设置：

1. **路由函数显式返回 `END`**：例如「工具结果已足够回答」「已拿到最终答案」就结束，这是主路径。
2. **State 里放计数器**：`retries` / `steps` 每轮 +1，超过阈值就走降级分支（转人工 / 返回兜底答案）。
3. **`recursion_limit`**：图执行时的 super-step 硬上限（默认通常 25），超出抛 `GraphRecursionError`。这是最后一道保险，通过 `config={"recursion_limit": 50}` 调整。
4. **业务级预算**：最大工具调用次数、最大 token、最长挂钟时间，防止「步数没超但钱烧光了」。

死循环的典型成因，排查时按这个顺序看：

- 条件边的判断条件写反或永远为真（例如只判断「有没有 messages」，而每轮都会新增消息）。
- 工具一直返回失败，模型一直用**相同参数**重试 —— 要把错误明确写回上下文，并限制同参数重试次数。
- 两个 Agent 互相 handoff 来回踢。
- `recursion_limit` 设得过大，掩盖了本该发现的逻辑问题。

> 关键认知：**`recursion_limit` 是保险丝，不是终止逻辑**。只靠它兜底意味着每次失控都要白跑几十步、烧一堆 token 才停下；正经做法是让 State 里的业务条件先收敛。

### LangGraph 的 Short-term memory 与 Long-term memory（Store）有什么区别？

**一句话结论：Short-term 是「这一个 thread 的执行状态」，由 Checkpointer 管；Long-term 是「跨 thread、跨会话 persists 的事实」，由 Store 管** —— 两者存储介质、作用域、写入方式都不同。

| 维度 | Short-term memory | Long-term memory（Store） |
| --- | --- | --- |
| 作用域 | 单个 `thread_id` 会话 | 跨会话，按 `user_id` / namespace 隔离 |
| 内容 | messages、当前计划、中间产物、待审批动作 | 用户偏好、项目约定、历史结论、领域事实 |
| 实现 | Checkpointer 自动在每步落盘 | 显式 `store.put` / `store.get` / `store.search` |
| 生命周期 | 随会话结束可归档/清理 | 长期保留，需要更新与遗忘策略 |
| 读取方式 | 自动加载，节点直接读 State | 节点里主动检索，按相关性召回 |
| 后端 | Postgres / Redis | 支持向量检索的 Store（如 Postgres + pgvector） |

长期记忆真正的难点不在「存」，而在三个决策：

- **写入决策**：不是每轮对话都值得记。要抽取、去重、判断置信度，否则库里很快堆满互相矛盾的垃圾。
- **检索决策**：按语义相关性召回，还要叠加时间衰减、权限过滤（多租户绝不能串）。
- **遗忘决策**：偏好会变（「我改用深色主题了」），要有覆盖、过期、冲突消解机制。

> 记忆这题的收尾金句：**短期记忆保证这一次不断线，长期记忆保证下一次不用重新认识你**。前者是工程状态管理，后者是「写入决策 + 检索 + 遗忘」的信息系统。

### 流式输出模式有哪些（values / updates / messages / custom）？区别是什么？

**一句话结论：`stream_mode` 决定「每次 yield 给你的到底是什么」—— 全量状态、节点增量、模型 token、还是自定义事件**，可以同时传多个模式。

| 模式 | 每次产出 | 适用 |
| --- | --- | --- |
| **`values`** | 每一步之后的**完整 State** | 想看状态演变、调试；数据量大、重复多 |
| **`updates`** | 每个节点返回的**增量更新** | 想知道「刚才是哪个节点做了什么」，做进度条 |
| **`messages`** | 模型逐 token 产出的消息片段 + 元数据 | 前端打字机效果；能区分是哪个节点在输出 |
| **`custom`** | 节点里用 `StreamWriter` 主动发的自定义事件 | 工具执行进度、检索命中数、外部任务百分比 |
| **`debug`** | 最详细的执行事件 | 排查图执行问题 |

实践建议：

- **前端聊天**用 `messages`（正文）+ `custom`（工具状态/进度）组合，不要只用一个模式硬凑。
- `values` 每步都发全量 State，**长会话会很费带宽**，别拿它做 UI 渲染。
- `messages` 模式下要处理元数据（哪个节点、是否工具调用），否则子图/多 Agent 的输出会混在一起。
- 多模式同时用时，事件是 `(mode, chunk)` 元组形式，消费端要按 mode 分流。

> 和第二章 SSE 那题连起来看：`stream_mode` 是**框架内部**的事件语义，SSE 是**传输给前端**的协议；中间需要一层把它们映射成前端能消费的事件类型。

### 如何把 LangGraph 应用部署成服务（LangGraph Platform / FastAPI 封装）？

**一句话结论：两条路线 —— 用官方平台托管，或自己用 FastAPI 把编译好的图包一层；无论哪条，Checkpointer 都必须换成持久化后端**。

**路线 A：LangGraph Platform（托管）**

- 官方提供的部署与运行环境，自带持久执行、任务队列、水平扩展、可观测与 Studio 调试界面。
- 适合不想自建运维、任务长且需要断点恢复的团队。
- 代价是平台绑定、部署方式与自研基础设施不同、成本模型要评估。

**路线 B：FastAPI 自己封装（更常见）**

1. 用 `PostgresSaver` 编译图（`InMemorySaver` 不能上生产）。
2. 定义清晰的接口：`POST /runs`（起任务）、`GET /runs/{id}/stream`（SSE 流）、`POST /runs/{id}/resume`（HITL 恢复）、`GET /runs/{id}/state`（查状态）。
3. 每个请求把 `thread_id` 从鉴权后的用户上下文里取，**绝不信任客户端传的 user_id**。
4. 长耗时任务走后台任务/队列，HTTP 只返回 `run_id`，前端用 SSE 或轮询跟踪。
5. 加上超时、限流、并发上限、取消（用户关页面要能停掉在跑的 Agent）。

上线前必查清单：

- [ ] Checkpointer 是持久化后端，且连接池/总连接数按实例数算过。
- [ ] `thread_id` 带用户隔离，防止跨用户串话。
- [ ] 流式响应关掉了反向代理缓冲（`X-Accel-Buffering: no`）。
- [ ] 有 Trace（LangSmith / Langfuse / OpenTelemetry）与每次运行的 token 成本记录。
- [ ] 有 `recursion_limit`、工具超时、总超时、以及任务取消后的清理。
- [ ] 密钥走环境变量，日志不打印完整 Prompt 与工具返回值（可能含 PII）。

> 一句实话：LangGraph 应用上线后最常出事的不是图逻辑，而是**有状态服务的运维** —— checkpoint 表膨胀、thread 串话、流被缓冲、任务取消不掉。

## 五、RAG

### 完整 RAG 流程是什么？每一步可能出什么问题？

**一句话结论：RAG = 把问题相关的资料找出来，连同问题一起交给模型，让它基于资料回答**；难点几乎都不在「生成」，而在「找得准不准」。

分两条链路看：**离线建索引**与**在线查询**。

离线：文档采集 → 解析/清洗 → 切分 → 生成 embedding → 连同元数据写入向量库（+ 关键词索引）。
在线：用户提问 → 查询改写/向量化 → 召回 → 重排 → 组装上下文 → 生成 → 引用与校验。

| 步骤 | 做什么 | 最常见的故障 |
| --- | --- | --- |
| **解析清洗** | PDF/网页/表格转纯文本 | 表格错位、页眉页脚噪声、扫描件没 OCR、代码块被压平 |
| **切分** | 按语义或长度切 chunk | 切碎了丢上下文、切太大混进无关内容、跨章节的语义被切断 |
| **Embedding** | 文本转向量 | 模型与语料语言/领域不匹配；中英文混排效果差 |
| **召回** | 相似度检索 top-k | 只按语义导致专有名词/编号命中差；k 太小漏、太大引入噪声 |
| **重排** | 精排候选 | 省略这步，top-k 里前几条往往是「看起来像但不相关」 |
| **组装上下文** | 拼进 prompt | 文档顺序混乱、没有来源标注、超出窗口被截断 |
| **生成** | 模型据资料作答 | 没约束「只依据资料」→ 自由发挥；无引用 → 无法核查 |
| **评估** | 回收反馈 | 没有评估集，只能靠感觉调，改一处坏一处 |

两个高频的整体性判断：

- **答不准先别急着换模型**，按「召回 → 重排 → 上下文 → 生成」逐层排查，多数问题出在前两层。
- **答案里带引用**（段落 ID、原文片段）既是可信度需要，也是最低成本的调试手段 —— 一看引了哪段就知道是哪一步错了。

### 文档切分（Chunking）策略有哪些？chunk size 和 overlap 如何选？

**一句话结论：切分的目标不是「长度均匀」，而是「每个 chunk 单独看都语义自洽、能回答一类问题」**。

常见策略：

| 策略 | 做法 | 适合 |
| --- | --- | --- |
| **固定长度** | 按字符/token 切 | 兜底基线，实现最快，但容易切断句子 |
| **递归字符切分** | 依次按段落 → 句子 → 字符降级切 | 通用默认，LangChain 的 `RecursiveCharacterTextSplitter` 属这类 |
| **按结构切** | 按 Markdown 标题 / HTML 标签 / 章节 | 文档本身结构清晰时效果最好 |
| **语义切分** | 相邻句子 embedding 差异大处断开 | 长叙述型文本，成本较高 |
| **父子 / Small-to-Big** | 用小 chunk 检索、命中后返回它所在的大 chunk | 兼顾检索精度与生成上下文完整度 |
| **加上下文前缀** | 每个 chunk 前自动补「所属章节 / 文档标题」 | 解决「这段里的『它』指谁」这类指代丢失 |

`chunk size` 与 `overlap` 怎么定：

1. **先按问题的粒度反推**：用户问的是术语定义 → 200~400 token 够；问的是方案对比/流程 → 需要 500~1000 token 或父子切分。
2. **overlap 取 chunk 的 10%~20%** 即可，目的是不让跨边界的句子被腰斩；开太大只是重复计费。
3. **以评估集为准，不要凭直觉**：拿几十条真实问题测召回率，对比 256 / 512 / 1024 三档比拍脑袋可靠。
4. **务必保留元数据**：`doc_id`、`section`、`version`、`updated_at`、`权限标签` —— 后续做过滤、增量更新、引用全靠它。

> 一个常被忽略的坑：**切分单位和检索单位可以不相等**。小 chunk 检索 + 返回父段落，往往比纠结「到底 512 还是 1024」更有效。

### Embedding 模型如何选择？向量检索与关键词检索（BM25）的区别？什么是混合检索？

**一句话结论：向量检索擅长「意思相近」，BM25 擅长「字面精确」，生产里两者融合（混合检索）几乎总是优于单用一种**。

| 对比 | 向量检索（稠密） | BM25（稀疏/关键词） |
| --- | --- | --- |
| 匹配依据 | 语义相似度（余弦/内积） | 词频、逆文档频率、字段长度归一 |
| 强项 | 同义改写、口语化提问、跨语言 | 产品型号、错误码、人名、专有名词、精确短语 |
| 弱项 | 编号/缩写/生僻专名容易「差不多但不对」 | 用户换个说法就召回不到 |
| 成本 | 需要 embedding 模型 + 向量索引 | 索引轻量，可即时建 |

**Embedding 模型选型看四件事**：

- **语言与领域**：中文语料别默认用英文模型；医疗、法律、代码等垂类优先看该领域评测。
- **维度与向量库兼容**：维度影响存储与检索速度，不是越大越好。
- **输入长度上限**：超过会被截断，长 chunk 可能白切。
- **可否自托管 / 数据合规**：内部文档不能出网的场景要能本地部署。

**混合检索**的做法与关键细节：

1. 两路各自召回候选（向量 top-k + BM25 top-k）。
2. 用 **RRF（倒数排名融合）** 或加权分数合并 —— RRF 只用名次不看分数，省去两路分数尺度不统一的麻烦。
3. 合并后再送 Rerank 精排。
4. **换 embedding 模型必须全量重建索引**：不同模型的向量空间不通用，混用等于索引失效，这也是下一章要做版本管理的原因。

> 面试里可以举一个直观例子：用户搜 `ERR_CONN_502`，BM25 一击命中，向量检索可能返回一堆「网络错误排查」的泛泛文档。反过来问「服务老连不上怎么办」，BM25 就抓瞎了。

### 什么是 Rerank？为什么需要两阶段检索？

**一句话结论：召回阶段用便宜的方法「广撒网」，重排阶段用更贵但更准的模型「精挑」，是精度与成本的折中**。

为什么必须两阶段：

- 双塔/向量检索为了快，把文档和查询**分别**编码成向量，两者在编码时没有交互，细粒度相关性判断天然受限。
- Rerank 用 **Cross-Encoder**：把「查询 + 候选文档」拼在一起过一次模型，直接打分，能看到两者间的交互，精度高得多。
- 但 Cross-Encoder 无法预先算好，**对每对候选都要实时推理**，拿它扫全库不可行。

典型流程：

1. 混合检索召回 **50~100** 条候选（召回优先，宁可多召回）。
2. Rerank 逐条打分，取 **top 5~10**。
3. 只把这 5~10 条拼进上下文交给生成模型。

收益与代价：

- 收益：真正相关的文档被顶到前面，**减少「上下文里塞了一堆噪声」**，答案忠实度常明显提升。
- 代价：多一次模型调用、增加几十到几百毫秒延迟；要评估是否值得。
- 注意 Rerank 模型也有语言/领域适配问题，且**它只能重排召回到的东西** —— 第一步漏掉的文档，后面救不回来。

> 排查 RAG 时的判断法：**如果相关文档根本不在 top-50 里，是召回问题（改切分/混合检索/Query 改写）；如果它排在 30 名，是重排问题**。这两类问题的解法完全不同。

### 常见向量数据库有哪些（Milvus、Chroma、pgvector、Qdrant）？如何选型？

**一句话结论：选型看的不是「谁的 benchmark 最快」，而是数据规模、是否已有 PostgreSQL、运维能力和是否需要混合检索/多租户隔离**。

| 方案 | 定位 | 适合 | 主要取舍 |
| --- | --- | --- | --- |
| **pgvector** | PostgreSQL 扩展 | **已有 PG、中小规模、业务表与向量要同库** | 免去多一套组件、能直接用 SQL 做元数据过滤和事务；超大规模与高 QPS 能力不如专用库 |
| **Chroma** | 轻量嵌入式 / 本地库 | 原型、demo、单机小项目 | 上手最快；生产级分布式、权限、运维能力弱 |
| **Qdrant** | 专用向量库，Rust 实现 | 中等规模、要过滤与混合检索、自建服务 | 功能均衡、部署相对轻；仍需单独运维一套服务 |
| **Milvus** | 分布式专用向量库 | 亿级向量、高并发、需要横向扩展 | 能力最强；组件多（依赖 etcd / 对象存储等），运维成本最高 |

选型的四个实际问题：

1. **规模量级**：十万级以下且已有 PG → `pgvector` 基本够，别为了「看起来专业」多引入一个分布式系统。
2. **AI 应用的特殊性**：RAG 常需要「业务数据 + 向量」一起过滤、一起事务，还要存会话与消息 —— **pgvector 让这些都在一个库里**，中小规模运维成本最低。
3. **过滤与多租户**：按部门/权限/时间过滤是刚需，要确认索引在带过滤条件时仍有效。
4. **索引类型**：HNSW（查询快、内存占用高）vs IVF（省内存、需训练）；别只看「支持哪些索引」的宣传，要看在你数据分布下的召回率。

> 一个务实的回答：多数团队的第一版 RAG **用 pgvector 就对了**；等 QPS 或向量量级真的逼到瓶颈再迁移，比一上来搭 Milvus 集群更省时间。

### 如何评估 RAG 效果？（召回率、忠实度、答案相关性；RAGAS 等工具）

**一句话结论：必须把「检索」和「生成」分开评，否则答错了根本不知道该改哪一层**。

两层指标：

| 层 | 指标 | 含义 | 不达标说明什么 |
| --- | --- | --- | --- |
| **检索** | Recall@k / Context Precision / Context Recall | 相关文档有没有被召回、排在前面 | 切分、embedding、混合检索、Query 改写的问题 |
| **生成** | **Faithfulness（忠实度）** | 答案里的每条陈述能否被给定上下文支撑 | 模型在编造 / 上下文里有噪声 |
| **生成** | **Answer Relevancy** | 答案是否切题 | 上下文找对了但答偏了，或 Prompt 约束不够 |
| **整体** | 正确率、拒绝率、引用准确率、延迟、成本 | 端到端表现 | 用于上线门槛与回归对比 |

**RAGAS** 是常用的自动化评估框架，核心就是用模型来算上面几个指标（忠实度、答案相关性、上下文精度/召回），适合在评估集上批量跑。类似的还有 TruLens、DeepEval、Arize Phoenix。

怎么落地：

1. **先建评估集**：从真实用户问题里挑 50~200 条，标注「标准答案 + 应命中的文档 ID」，覆盖常见问法、边界情况、以及**应该拒答的问题**。
2. **分层归因**：检索指标差就别调 Prompt，先修召回；忠实度低而检索正常，才去改生成约束。
3. **每次改动跑全量回归**：换 embedding、改 chunk、换模型、改 Prompt 都跑一遍，看指标有没有退步。
4. **保留人工抽检**：LLM 打分本身有偏差，定期人工复核一小批，防止「指标涨了体验差了」。

> 特别提醒：**「答不上来」也要能评**。把「资料里没有就说不知道」纳入评估集，否则优化会一路把系统推向「什么都敢答」。

### 检索结果不准有哪些优化手段？（Query Rewrite、HyDE、多路召回、元数据过滤）

**一句话结论：先判断是「用户问法的问题」还是「索引/召回的问题」，再选对应手段，别一次全上**。

| 手段 | 解决什么 | 怎么做 |
| --- | --- | --- |
| **Query Rewrite** | 口语化、含代词、省略上下文的追问（「那它多少钱？」） | 用模型结合历史把问题改写成完整独立查询 |
| **Multi-Query / 多路召回** | 一个问法覆盖不全 | 生成 2~4 个不同角度的查询并行检索，合并去重 |
| **HyDE** | 短查询与文档表述差异大 | 先让模型生成一段「假想答案」，用它的向量去检索（注意会引入偏差） |
| **Step-back Prompting** | 问题太具体、缺上位概念 | 先抽象成一个更泛的问题，再一起检索 |
| **元数据过滤** | 结果跨版本、跨部门、越权 | 按 `tenant / doc_type / version / updated_at / 权限` 先过滤再检索 |
| **混合检索 + Rerank** | 语义/字面各漏一半 | BM25 + 向量融合，再精排（见前面两题） |
| **父子切分** | 命中片段缺上下文 | 小 chunk 检索，返回所属大段落 |

排查顺序（很实用，面试常问）：

1. 把出错的问题**人工检索一次**，看相关文档到底在不在库里 —— 不在就是**索引/更新问题**，不是检索算法问题。
2. 在库里但没进 top-50 → **召回问题**：Query Rewrite、混合检索、换 embedding、调切分。
3. 进了 top-50 但排名靠后 → **重排问题**：加 Rerank。
4. 排第一但答案仍错 → **生成问题**：上下文组装、引用约束、Prompt、模型能力。

> 别忽略一个「非算法」手段：**让用户能看到引用来源并点「没帮上忙」**，这些反馈是构建评估集最好的原料。

### Agentic RAG 与传统 RAG 的区别是什么？

**一句话结论：传统 RAG 是「检索一次 → 生成一次」的固定管道，Agentic RAG 把检索变成一个由模型自主决定「要不要搜、搜什么、搜几次、够不够」的循环**。

| 维度 | 传统 RAG | Agentic RAG |
| --- | --- | --- |
| 流程 | 固定：改写 → 召回 → 生成 | 动态：模型可多轮检索、换策略、换工具 |
| 检索决策 | 由代码写死（一定检索 top-k） | 模型判断是否需要检索、检索几次 |
| 工具 | 通常只有向量库 | 可同时用向量库、SQL、Web 搜索、计算器等 |
| 自我校验 | 无 | 可评估「找到的资料够不够回答」，不够就再查 |
| 适用 | 问答型、资料确定 | 需要多跳推理、跨源比对、资料不确定的任务 |
| 代价 | 低延迟、成本可预测 | 步数不定的延迟与 token 消耗，且更依赖评估与终止条件 |

典型循环：拆问题 → 决定先查哪个源 → 检索 → **判断证据是否充分** → 不充分则改写再查或换数据源 → 够了才生成 → 可选地自检引用。

必须配套的三件事，否则很容易失控：

- **终止条件**：最大检索轮数、证据充分度判定、`recursion_limit`。
- **成本上限**：一轮 Agentic RAG 可能是普通 RAG 的 5~10 倍 token，要有预算。
- **可观测**：每一步检索了什么、为什么继续查，都要进 Trace，否则没法排查。

> 判断该不该上 Agentic RAG 的一句话：**如果「一次检索就够」能解决 80% 的问题，就用传统 RAG；只有剩下那 20% 需要多跳时，才把 Agent 作为一条可选分支接上去**，别把它当默认路径。

### 知识库内容更新后，如何做增量索引与版本管理？

**一句话结论：靠「稳定 doc_id + 内容哈希 + 版本号」做到「只重算变化的部分」，并且任何时刻都能回答「这个答案依据的是哪一版文档」**。

增量索引的流程：

1. **文档标识稳定**：给每篇文档一个不变 `doc_id`（不要用文件名/路径当主键，改名就全乱）。
2. **变更检测**：解析后算内容哈希（或比对 `updated_at` / 版本号），哈希没变就跳过，不重复 embedding。
3. **按 doc_id 删旧 chunk**：先删除该文档的所有旧 chunk 与旧关键词索引条目，再写入新 chunk —— **顺序错了会残留孤立片段**。
4. **原子切换**：大批量更新时用新版本别名/指针切换，避免更新中途出现「一半旧一半新」。
5. **失败可重放**：记录每篇文档的处理状态与水位，中断后从断点续跑。

版本管理要覆盖四处：

| 对象 | 为什么要版本化 |
| --- | --- |
| **文档内容** | 答案要能引用当时的原文；政策/价格类问题事后可追溯 |
| **chunk 切分规则** | 规则一变，chunk 边界全变，需要重建并标注规则版本 |
| **Embedding 模型** | 换模型必须**全量重建**，新旧向量不能共库查询 |
| **评估集与指标** | 每次索引/模型变更后跑回归，留一份基线对比 |

还有两个工程细节：

- **删除要真删**：文档下线时同步删向量、关键词索引、以及缓存里的相关问答；否则会继续被召回（这是「幽灵答案」的常见来源）。
- **缓存失效**：知识库更新后，基于旧文档生成的语义缓存必须按 `doc_id` 或版本键失效，否则用户拿到的是几天前的答案。

> 一句能体现工程意识的话：**索引不是一次性构建的产物，是一条需要持续运行、可回滚、可观测的数据管道**。

## 六、记忆与上下文工程

### 短期记忆与长期记忆在 Agent 中分别怎么实现？

**一句话结论：分界不在「存在哪」，而在「生命周期」和「写入门槛」** —— 短期是本次任务的工作集，长期是跨会话要保留的事实。

**短期记忆**：本次任务的工作集 —— 消息历史、当前计划、已调工具的结果、中间产物。

- 放会话状态 / Checkpointer / Redis，要求低延迟、可序列化、支持检查点。
- 随任务结束清空或转存；**不需要「判断该不该记」**，流式写入即可。
- 常见三层：会话缓冲（原始消息）→ 情景摘要（每次任务结束生成的结构化小结）→ 需要时才抽取成长期条目。

**长期记忆**：跨会话要保留的东西 —— 用户偏好、项目约定、历史结论、领域事实。

- 存向量库 + 结构化库，下次会话按相关性召回。
- **必须经过抽取、去重、置信度判断才写入**，否则很快堆满互相矛盾的噪声。
- 要有更新、冲突消解和遗忘策略（「我改用 X 了」应覆盖旧偏好，而不是并存）。

| 维度 | 短期 | 长期 |
| --- | --- | --- |
| 作用域 | 单个任务 / thread | 跨会话、按用户/项目隔离 |
| 写入 | 自动、无门槛 | 抽取 + 去重 + 置信度判断 |
| 读取 | 全量加载进上下文 | 按相关性检索少量条目 |
| 失效 | 任务结束 | 需显式更新/过期/覆盖 |
| 权限 | 随会话 | **必须做多租户隔离**，串了就是数据事故 |

> 收尾金句：**短期记忆保证这一次不断线，长期记忆保证下一次不用重新认识你**；短期靠工程状态管理，长期靠「写入决策 + 检索 + 遗忘」的信息系统。

### 上下文窗口快满了怎么办？（截断、摘要、滑动窗口、检索式记忆）

**一句话结论：别等塞满才处理，把上下文当**有限预算**主动管理；四种手段按「丢什么、留什么」的代价递增排序**。

| 手段 | 做法 | 优点 | 代价 |
| --- | --- | --- | --- |
| **滑动窗口 / 截断** | 只留最近 k 轮 | 最简单、零额外成本 | 早期关键约束会突然消失；可能把一轮对话从中间切断 |
| **摘要压缩** | 把旧历史用模型压成结构化小结 | 成本平稳、保留要点 | 要额外调模型；细节丢失，多次摘要会累积失真 |
| **检索式记忆** | 历史存外部，按当前问题只召回相关片段 | 适合超长/跨会话 | 需要索引与召回策略，召回不准等于没带 |
| **隔离 / 卸载** | 大段工具结果不进主上下文，存文件/State，需要时按需取 | 从源头减少占用 | 工程实现最复杂 |

实操中更好用的几条：

- **工具结果是最主要的膨胀源**：一次网页抓取、一整页日志可以轻松吃掉上万 token。先在工具层做裁剪/摘要，只回传模型决策真正需要的字段。
- **给输出预留空间**：窗口不是全给输入的，要扣掉 `max_output_tokens`，否则生成会被截断。
- **关键约束重复放在首尾**：受「迷失在中间」影响，模型对开头（系统提示）和结尾（最新输入）注意力最高；重要规则别只写在中间。
- **压缩要留锚点**：摘要里保留订单号、时间、已确认的决策等不可丢失的事实，不要只留「用户讨论了订单问题」。
- **触发点提前**：到 70%~80% 用量就压缩，别等到逼近上限才手忙脚乱。

> 一句话点破本质：**上下文窗口变大只是提高了预算上限，没有降低「每多一个 token 都在稀释注意力并重复计费」这个事实**。上下文工程做的是选对要放进去的东西。

### 什么是 Context Engineering？它和 Prompt Engineering 有什么不同？

**一句话结论：Prompt Engineering 是「把这句话写好」，Context Engineering 是「决定模型这一刻能看见什么、按什么顺序、以及看不到什么」** —— 后者在 Agent 里更重要，因为多步任务里大部分上下文不是你写的。

Anthropic 在 2025 年 9 月的《Effective context engineering for AI agents》里给的定义被广泛引用：**在每次推理时，策划并维护最优 token 集合的一组策略**，包括那些并非来自提示词、却会落进窗口的信息（工具结果、文件内容、历史对话、检索片段）。目标是「找到能达成预期结果的**最小高信噪 token 集合**」。

| 维度 | Prompt Engineering | Context Engineering |
| --- | --- | --- |
| 作用对象 | 指令的措辞、结构、示例 | 整个窗口：系统提示、工具定义、检索结果、历史、工具返回 |
| 时机 | 写这一条指令时 | 会话前（规则/技能）、会话中（每步组装）、跨会话（记忆） |
| 优化目标 | 这一次答得好 | 整个任务/仓库里**每一轮都稳定** |
| 典型失败 | 某一个答案差 | 结果忽好忽坏、不可复现 |

工程上常按四类操作来组织：

1. **Write（写出状态）**：把可复用的结论落成结构化状态 —— 任务计划、决策记录、未解决问题清单。**存事实和决策，不是存逐字逐句的流水账**。
2. **Select（选出信息）**：检索、过滤、排序，只把少量证据放进窗口。相关性之外还要看时效性、权限、来源质量。
3. **Compress（压缩）**：把旧对话、重复的工具输出、已完成的调查压成摘要。
4. **Isolate（隔离）**：把高风险或大体积内容放到子 Agent / 外部文件，主上下文只拿结论。

为什么这是个真问题（两个物理约束）：

- **Context rot / 迷失在中间**：窗口变长时模型对其中任一信息的召回准确率下降，开头的指令和最近的内容注意力最高，中段最容易被忽略。
- **预算是重复计费的**：Agent 每一步都重发上下文，一个不必要的 token 会被付很多次；同时它挤占本可用于推理和工具结果的席位。

> 一个很实用的判据：**如果你的改动是「把一句话写得更好」，那是 Prompt 工程；如果是「决定某个东西要不要进入窗口」，那是 Context 工程**。写 `CLAUDE.md` / `AGENTS.md`、按需加载 Skills、裁剪工具输出、设计记忆召回，都属于后者。

### 如何设计用户画像/偏好的长期存储与召回？

**一句话结论：难点不是存储，是「写什么、什么时候覆盖、召回时怎么保证不串人和不过时」**。

整体分四层设计：

**1. 数据模型**：分成两类，别混成一张表。

- **显式事实**：用户主动声明的偏好（语言、技术栈、回复长度、时区）—— 高置信、可直接覆盖。
- **推断画像**：从行为里归纳的倾向（「偏好先看结论」「常问部署问题」）—— 要带**置信度、来源、证据时间**，且可被人纠正。

每条记忆至少带：`user_id`、`key`、`value`、置信度、来源（显式/推断）、`created_at`、`updated_at`、过期时间。

**2. 写入决策**（最容易做错的一环）：

1. 每轮结束后用模型抽取候选事实，而不是把整段对话存进去。
2. **去重**：与已有条目比对，相同或更弱的直接丢弃。
3. **冲突消解**：新偏好与旧偏好矛盾时**覆盖并留变更记录**（「改用 X」不是新增一条），而不是两条并存。
4. **设门槛**：低置信、一次性、纯任务上下文的不写；能明确回答「下次还会用到吗」才写。

**3. 召回**：

- 按 `user_id` **硬过滤优先**，再做语义检索 —— 权限过滤必须在检索前/检索条件内，不能「召回后再筛」，否则会泄露他人数据。
- 相关性叠加**时间衰减**和置信度权重。
- 控制注入条数（通常 3~8 条），并把它们放在系统提示的固定区块，格式统一，别和检索文档混在一起。

**4. 治理**：

- 提供**查看 / 修改 / 删除**入口（合规要求，也是纠错手段）。
- 定期清理过期条目；记录每次召回用到了哪条记忆，方便排查「它为什么这么答」。
- 多租户场景把 `user_id` / `tenant_id` 作为所有读写路径的必带参数，测试里要有跨用户用例。

> 面试收尾可以点一句：**长期记忆系统本质是一个带写入门槛的小型信息检索系统**，把它当「多存几轮聊天记录」来做，一定会在冲突、过时和权限上翻车。

## 七、工具设计与调用

### 设计一个好 Tool 的原则是什么？（命名、参数描述、粒度、幂等性、错误信息）

**一句话结论：工具是给模型用的「API」，不是给人用的函数 —— 它的接口设计要按「模型只能看到 schema 和 description」这个前提来做**。

逐项原则：

| 维度 | 怎么做 | 反例 |
| --- | --- | --- |
| **命名** | 动宾结构、语义唯一、能看出作用域 | `handle`、`tool1`、`query` |
| **参数描述** | 类型、单位、格式、必填、取值范围、示例都写全 | 只写 `id: str` |
| **边界说明** | 写清「什么时候用、什么时候**不要**用」 | 三个工具描述都是「查询信息」 |
| **粒度** | 一个工具做一件语义完整的事 | 把「查订单 + 算折扣 + 发通知」塞进一个工具 |
| **幂等性** | 写操作带幂等键，重复调用结果一致 | 重试一次就重复发一封邮件 |
| **返回值** | 结构化、简短、含「无结果/失败」的明确状态 | 返回空字符串或一整页 HTML |
| **错误信息** | 变成**可行动**的提示，让模型知道下一步 | 直接把 traceback 甩回上下文 |

几个容易被追问的细节：

- **参数越少越好**：能由服务端推导出来的（如 `user_id`）不要让模型填，既减少出错又防越权 —— 从鉴权上下文里取。
- **枚举优于自由文本**：`status` 用固定枚举，别让模型自由发挥。
- **返回值要「够判断」但不「撑爆窗口」**：查不到时告诉模型「库里有 3 个相近 ID，是否需要换个条件」，比 `NOT_FOUND` 有用得多；但一整张表不能原样返回。
- **错误信息分两类**：可重试（超时、限流）→ 明确告诉模型可稍后重试；不可重试（参数非法、权限不足）→ 明确告诉模型别再用同样参数重试。这个区分直接决定会不会陷入死循环。

> 一个很好的自检法：**把工具列表给一个没看过业务的人（或一个模型），让他判断「用户说 XXX 该调哪个」** —— 判断不出来就是描述没写好。

### 工具数量很多（几十上百个）时，模型选错工具怎么办？

**一句话结论：先做减法，再做分层 —— 不要指望把上百个工具的完整 schema 全塞进上下文还能选对**。

按顺序上的手段：

1. **按任务/阶段动态挂载**：进入「订单处理」分支时只给订单相关 5~8 个工具，而不是全程挂 100 个。这是收益最大的一招。
2. **检索式工具选择（Tool RAG）**：把工具描述建索引，先按用户意图召回 top-k 个候选，只把这些 schema 传给模型。
3. **分层路由**：先用一个轻量模型/分类器判断任务类型，再交给对应专家 Agent（它自带窄工具集）—— 也就是 Supervisor 模式。
4. **合并与去重**：把高度重叠的工具合并，用参数区分而不是用工具名区分；删掉长期零调用的工具。
5. **改描述与命名**：把「什么时候不要用」写清楚，冲突命名改掉；用真实问法做工具选择评估集跑回归。
6. **失败兜底**：选错导致参数校验失败时，把错误和最相似的 3 个工具描述一起回填，给一次纠正机会；仍失败就转人工/兜底回答。

为什么工具一多就崩（可以讲清原理）：

- 每个 schema 都占 token，**上百个工具可能吃掉大半个窗口**，还把关键指令挤到注意力最弱的中段。
- 候选项越多，语义越容易重叠，模型做的是一个高混淆度的多分类。
- 工具定义通常放在上下文前部，**这部分变动会让 Prompt Caching 失效**，成本随之上升。

> 经验判断：单个 Agent 的工具数控制在 **10~20 个以内**比较稳；真需要更多能力时，优先走分组路由，而不是继续往一个列表里加。

### 工具调用失败、超时、返回超长内容时如何处理？

**一句话结论：三类问题要分开处理 —— 失败要「可行动 + 可重试」，超时要「有上限 + 有降级」，超长要「在工具层裁剪」，不要让任何一种原样进入上下文**。

**调用失败**：

- 把错误分类：**可重试**（网络抖动、429、5xx）/ **不可重试**（参数非法、鉴权失败、业务校验不通过）。
- 返回结构化错误给模型，包含「错在哪、建议怎么改」，而不是异常堆栈。
- 可重试的用**指数退避 + 抖动**，限制次数（2~3 次）；**同一参数重试有上限**，否则就是死循环的起点。
- 失败信息里带上工具名和参数，方便 Trace 里定位。

**超时**：

- 每个工具设独立超时，且**必须小于整体请求超时**；Agent 总挂钟时间也要设上限。
- 超时后明确告知模型「该数据源暂不可用」，让它换源或降级回答，**不要静默重试**。
- 有副作用的操作超时最危险：**不知道到底执行成功没有** —— 要靠幂等键 + 事后查询状态确认，不能盲目重发。

**返回超长**：

- 在工具层做**截断 / 摘要 / 分页 / 只返回字段子集**，这是最有效的一层。
- 大内容存到外部（对象存储、State 文件），只把路径/摘要给模型，需要细节再按需取（对应第六章的 Isolate）。
- 设一个硬上限（如 4~8k token），超出直接截断并标注「结果已截断」，避免模型误以为看到了全部。

一个统一的工程原则：

> **模型看到的每一条工具结果，都是你「处理过」的产物，不是原始返回值**。这一层做不好，上下文膨胀、幻觉、死循环会一起出现。

### 并行工具调用（Parallel Tool Calls）是什么？有什么风险？

**一句话结论：模型一次返回多个互不依赖的 tool_call，执行层并发跑完再一起回填 —— 能显著降延迟，但前提是这些调用真的互相独立**。

适合并行的典型场景：

- 同时查 3 个不同数据源（订单库、用户库、日志库）。
- 对多份文档各自做一次抽取/评分（fan-out）。
- 多个只读校验同时跑。

四类主要风险：

1. **隐式依赖**：模型把「先创建订单、再用订单号查详情」也一起并行发出，第二个调用拿到空 ID 直接失败。**有依赖必须串行**。
2. **副作用重复/竞态**：两个调用同时写同一条记录、同时扣减库存、同时发通知 —— 需要幂等键、乐观锁或事务边界。
3. **限流与配额**：并发打向同一上游会瞬间触发 429，反而变慢；要设并发上限和信号量。
4. **失败处理复杂**：部分成功时，回填给模型的是「一半结果 + 一半错误」，模型容易基于不完整信息下结论；要明确标注哪些失败、是否可重试。

实践建议：

- 默认**串行**，只对明确的只读、无依赖调用开并行。
- 执行层自己校验依赖（检查参数里是否引用了同批尚未产出的 ID），不完全信任模型判断。
- 并发数设上限、每个调用独立超时、整体设总超时。
- 回填时按调用 ID 对齐结果，别把顺序搞乱。

> 和 LangGraph 的 fan-out 对比着讲：**图里的并行是开发者显式声明的、可控的；模型自发的并行调用是不可信输入，需要执行层兜底校验**。

### 有副作用的工具（发邮件、删数据、转账）如何做权限控制与二次确认？

**一句话结论：假设模型一定会被诱导或出错，把安全放在执行层和流程层，而不是放在提示词里**。

分层控制（从外到内）：

1. **身份与授权**：工具用**服务端鉴权后的用户身份**，绝不接受模型传来的 `user_id` / 角色；每个工具单独校验权限。
2. **最小权限**：Agent 用的凭证只覆盖本任务所需资源；只读任务就只发只读凭证。
3. **动作分级**：按错误代价把工具标成「只读 / 可回滚写入 / 对外不可逆」三级，不同级别走不同流程。
4. **二次确认**：高风险动作前 `interrupt` 暂停，把「要做什么、影响哪些对象、参数预览」展示给人，批准后才执行（LangGraph 的 HITL）。
5. **参数校验与业务规则**：金额上限、白名单收件人、禁止批量删除、单日次数上限 —— 这些是**确定性代码**，不交给模型判断。
6. **幂等 + 审计**：写操作带幂等键，记录 who / when / what / 依据哪次运行，全程可追溯。
7. **回滚路径**：能撤销的给撤销入口；不能撤销的原则上不开放给 Agent 直接调用。

几个真实坑：

- 「在 system prompt 里写『未经确认不要发邮件』」**不是控制**，模型被注入或理解偏差就会执行。
- 确认界面只显示「确定执行吗」不够，要显示**具体参数预览**（发给谁、金额多少），否则人无法判断。
- 中断/恢复会让节点重跑，`interrupt()` 之前不能有副作用（前面 HITL 那题已强调）。

> 一句能收尾的话：**权限控制的目标不是「让 Agent 不犯错」，而是「Agent 犯错时造成的损失有上界」**。

### 如何让 Agent 安全地执行代码（沙箱）？

**一句话结论：代码执行是最高风险的工具，必须默认「这段代码是恶意的」来设计 —— 隔离、限资源、断网、无凭证、可丢弃**，而不是 `exec` 一下就完事。

必须有的六层约束：

1. **进程/内核级隔离**：独立容器或 microVM（gVisor、Firecracker 类），**不要在执行 Agent 的宿主进程里跑**；容器共享宿主内核，严格场景要用更强隔离。
2. **资源限制**：CPU 时间、内存、磁盘、进程数、输出大小全部设上限，硬性超时后强杀。
3. **网络**：默认**完全禁用**；确需访问时走白名单代理，防止 SSRF 打内网元数据服务、也防数据外传。
4. **文件系统**：只读根文件系统 + 一次性临时目录，任务结束即销毁；不挂载宿主目录、不注入任何密钥/环境变量。
5. **权限**：非 root 运行、无特权、禁用能力集（capabilities drop）、seccomp 过滤系统调用。
6. **输出处理**：stdout/stderr 截断、脱敏，再作为工具结果回填；避免一整个 traceback 污染上下文。

工程上的额外考虑：

- **冷启动**：每个任务新建容器有秒级开销，用预热池或轻量运行时（WebAssembly / 受限解释器）折中。
- **依赖**：预装固定依赖、不让它现场 `pip install`（既是网络口子也是供应链风险）。
- **审计**：记录提交的代码、退出码、资源用量、被拒绝的系统调用，便于事后复盘。
- **分级**：纯计算类任务可以给受限解释器；需要调外部库/文件系统的，走完整沙箱。

> 容易被追问的一句：**Docker 容器 ≠ 安全沙箱**。它主要做环境隔离，共享内核、默认配置偏宽松；跑不可信代码要显式收紧上面六层，而不是 `docker run` 就当完事。

## 八、调试、可观测性与评估

### Agent 效果不好时，你的排查思路是什么？如何定位是 Prompt、工具、检索还是模型的问题？

**一句话结论：先拿一条失败案例的完整 Trace，从后往前定位「第一次偏离预期发生在哪一步」，再归因到对应层 —— 不要一上来就改 Prompt**。

推荐的排查顺序：

1. **复现并固定输入**：拿到 `run_id`、模型版本、Prompt 版本、工具 schema 版本、检索索引版本，先用同一输入重放。
2. **看完整轨迹**：逐步列出「模型看到了什么 → 决定做什么 → 工具返回了什么 → 状态怎么变」。
3. **找第一个偏离点**：是没理解意图？选错工具？参数填错？检索没命中？还是工具结果被误读？
4. **按层归因**：

| 现象 | 大概率归属 | 该改什么 |
| --- | --- | --- |
| 每一步都答非所问、格式乱 | **Prompt / 上下文** | 指令分区、示例、输出约束、裁剪噪声 |
| 该调 A 却调了 B，或参数编造 | **工具设计** | 命名、description、schema、动态挂载 |
| 相关文档根本没被召回 | **检索** | 切分、混合检索、Query 改写、embedding |
| 文档召回对了但答案仍错 | **生成 / 上下文组装** | 引用约束、排序、Rerank、忠实度校验 |
| 召回和工具都对，但推理链断 | **模型能力** | 换更强模型、拆步骤、加中间校验 |
| 偶发、同样输入两次结果不同 | **稳定性** | 降 temperature、结构化输出、回归评估集 |

5. **一次只改一处，跑评估集对比**，避免叠加多个改动后无法归因。
6. **把这条案例加进评估集**，做成回归用例，防止修好又坏。

> 一个高信号的习惯：**先测「组件」再测「整体」** —— 单独跑一次检索看召回、单独跑一次工具看返回、单独把标准上下文喂给模型看答案。三层各自正常而整体失败，问题几乎都在状态流转或上下文组装。

### 如何使用 LangSmith 或类似工具做 Tracing？一条 Trace 里你会重点看什么？

**一句话结论：Trace 把一次 Agent 运行展开成一棵调用树（每个 Run 是一个 span），重点看「输入上下文、模型决策、工具输入输出、以及每一步的耗时与 token」**。

接入方式：

- LangChain / LangGraph 生态：配置环境变量 + project 名即可自动埋点，无需改业务代码。
- 其他框架或自研：**OpenTelemetry** 语义约定是更通用的选择，可对接 Langfuse、Arize Phoenix、Jaeger 等；自研循环用装饰器/上下文管理器手动建 span。

一条 Trace 里重点看这六项：

1. **Run 树结构**：哪些节点被走了、有没有意外的循环、并行分支是否都完成。
2. **每一步的实际输入**：真正发给模型的完整 messages（包括被框架拼进去的系统提示、工具结果）—— 多数「莫名奇妙」的问题一看这里就明白。
3. **模型输出与 tool_call**：选了哪个工具、参数是什么、有没有被解析成结构化对象。
4. **工具返回值**：状态码、耗时、是否被截断、错误信息是否可行动。
5. **延迟与 token 分布**：哪一步最慢、哪一步最贵、缓存命中率、重复调用次数。
6. **元数据标签**：`run_id`、`thread_id`、`user_id`、Prompt 版本、模型版本、环境 —— 没有这些就无法跨运行对比和复现线上问题。

让 Trace 真正有用的几个做法：

- **自定义 tag / metadata** 打上业务维度（tenant、任务类型、实验分组），便于按维度聚合成功率与成本。
- **给每条 run 关联一次用户反馈**（点赞/点踩/「没帮上忙」），这是评估集和回归用例的来源。
- **采样与脱敏**：高流量下全量存很贵；日志里的 PII、密钥、完整 Prompt 要按合规要求处理。
- 把 Tracing 当**基础设施**而不是调试开关：线上默认开，出事才有得查。

> 同类工具选型一句话：LangSmith 与 LangChain/LangGraph 集成最顺；要自建或跨框架用 **Langfuse / OpenTelemetry**；只关注 RAG 指标可加 RAGAS / Phoenix。

### 如何构建 Agent 的评估集（Eval Dataset）？有哪些评估维度（任务成功率、工具调用准确率、轨迹质量、成本、延迟）？

**一句话结论：评估集要覆盖「结果 + 过程 + 成本」三层，并且必须来自真实流量，不能只靠自己编的十道理想题**。

**怎么建**：

1. **从真实日志抽样**：按任务类型、难度、失败反馈分层抽样，别只抽成功案例。
2. **覆盖四类用例**：典型 happy path、边界/模糊输入、**应当拒答或转人工**的用例、以及已知历史 bug 的回归用例。
3. **标什么**：输入、期望最终结果、期望的关键工具调用（或允许的等价路径）、必须出现的上下文证据、以及明确的失败条件。
4. **量级**：起步 50~100 条就能驱动迭代；成熟系统按任务类型分多个数据集。
5. **持续维护**：每条线上事故 + 每次用户负反馈都转成一条用例；评估集不更新，指标很快失去意义。

**评估维度**：

| 层 | 指标 | 说明 |
| --- | --- | --- |
| **结果** | 任务成功率、答案正确率、拒答准确率 | 最终有没有解决问题 |
| **过程** | 工具选择准确率、参数合法率、**轨迹质量**（有没有走弯路/重复调用） | 结果对但过程糟糕，仍然不可上线 |
| **鲁棒性** | 多次运行一致性、故障恢复率、注入/越权用例通过率 | 生产最常出事的一层 |
| **效率** | 总 token、成本/任务、端到端延迟、P95、步数 | 直接决定能不能规模化 |
| **体验** | 首 token 延迟、流式中断率、引用可核查性 | 用户实际感知 |

两个容易被忽略的实践点：

- **过程指标要和结果指标一起看**：Agent 可能「碰巧答对」但走了 12 步、重试 5 次，这种成功不可复制。
- **固定随机性做相对比较**：同配置跑多次取通过率分布，而不是只跑一次比大小；上线门槛应写成「评估集通过率 ≥ X% 且 P95 延迟 ≤ Y」。

> 一个能体现成熟度的说法：**评估不是上线前跑一次的报告，而是每次 Prompt / 模型 / 工具 / 索引变更后自动跑的回归门禁**。

### LLM-as-a-Judge 是什么？有哪些偏差和局限？

**一句话结论：用另一个模型按评分标准给输出打分，适合做大规模、低成本的相对评估；但它本身是有偏差的测量工具，不能当标准答案**。

适用场景：开放式回答的相关性/语气/忠实度、A/B 对比、大规模回归；不适合精确事实判断、数值计算、合规判定（这些用确定性校验器）。

主要偏差与局限：

| 偏差 | 表现 |
| --- | --- |
| **位置偏差** | A/B 对比时倾向选先出现或后出现的一个 |
| **长度偏差** | 更长的答案容易得高分，哪怕更啰嗦或含错误 |
| **自我偏好** | 评判模型倾向给同家族模型/自己风格的输出高分 |
| **权威/格式偏差** | 带引用、排版漂亮的答案容易虚高 |
| **标准漂移** | 同一 rubric 不同次打分不一致，模型版本一换基线就变 |
| **无法判事实** | 编造得很流畅的内容它也可能判「忠实」 |

怎么用才相对可靠：

1. **rubric 写得具体可判**：拆成几条二选一或 1~5 分的明确标准，别用「请评价好坏」。
2. **给参考答案/证据**：把标准答案、检索片段一起给 judge，减少它靠自身知识猜。
3. **消除位置偏差**：A/B 双向各评一次，或随机化顺序取一致结果。
4. **用强模型、固定版本与 temperature=0**，把 judge 的模型版本也纳入实验记录。
5. **定期用人工标注校准**：抽一小批人工打分，测 judge 与人的一致率；一致率跌了就换 rubric。
6. **混合评估**：能写规则的（JSON 合法性、是否调用了禁用的工具、是否包含 PII）一律用代码判，judge 只负责主观维度。

> 收尾一句：**LLM-as-a-Judge 是「可扩展的近似」，不是「客观真值」**；把它和确定性校验、人工抽检三者搭配，才敢拿来做上线门禁。

### 如何做 Prompt 的版本管理与回归测试？

**一句话结论：把 Prompt 当代码对待 —— 进 Git、有版本号、改动走评审、上线前自动跑评估集**。

具体做法：

1. **外置与版本化**：Prompt 不硬编码在代码里，放独立文件/配置或 Prompt 管理平台，带 `name + version`；运行时记录本次用的是哪一版。
2. **结构化组织**：把系统指令、工具使用规则、输出格式、few-shot 示例拆成可组合的片段，改一处不影响其他。
3. **改动可追溯**：每次修改写清「改了什么、为什么、针对哪条失败用例」，和 commit 关联。
4. **回归门禁**（关键）：

| 步骤 | 内容 |
| --- | --- |
| 1 | 在固定评估集上跑基线，记录成功率、忠实度、成本、P95 延迟 |
| 2 | 只改一处，跑同一评估集，逐条 diff 哪些用例变好/变坏 |
| 3 | 重点检查**原失败用例是否修好、原成功用例是否退化** |
| 4 | 设置门槛（整体不退步 + 关键用例全过），不达标不合并 |

5. **灰度和回滚**：先小流量灰度，指标异常切回上一版；Trace 里带上 Prompt 版本，才能按版本聚合对比。
6. **变量隔离**：评估时固定模型版本、temperature、检索索引、工具 schema，一次只变一个变量，否则结论不可信。

还有两个现实细节：

- **Prompt 改动会影响 Prompt Caching**：系统提示变了，缓存前缀失效，成本会突然上升 —— 回归报告里要一起看 token/成本指标。
- **别只测「平均分」**：某类任务从 95% 掉到 70%、整体平均只掉 2 分的情况很常见，要按任务类型分组看。

> 一句话：**无法回滚、无法归因、无法回归的 Prompt 改动，本质上就是在线上直接改生产代码**。

### Agent 输出不稳定、同样输入结果不同，怎么办？

**一句话结论：先接受「不可能完全确定」，把目标从「每次一模一样」改成「结果分布收敛、关键动作受约束」**。

不稳定的来源先分清楚：

- **采样随机性**：temperature / top_p 非 0。
- **平台侧变化**：模型版本更新、供应商路由、并行计算带来的浮点差异 —— 设 0 也不能保证严格一致。
- **上下文漂移**：历史消息、检索结果、工具返回、时间、并发状态每次略有不同。
- **上游不确定性**：外部 API 时快时慢、时成时败，导致 Agent 走了不同分支。

对策按性价比排序：

1. **降随机性**：工具选择/参数/路由节点设 `temperature=0`，只调一个采样旋钮。
2. **结构化输出 + 校验**：用 Strict Structured Output 约束格式，Pydantic/Zod 校验，失败重试（见第二章）—— 这一步收益最大。
3. **收敛动作空间**：动态挂载少量工具、参数用枚举、给明确的决策规则，减少「有多种 equally plausible 走法」。
4. **让关键判断确定化**：金额、权限、状态这类判断交给代码/规则，别让模型自由裁量。
5. **固定外部输入**：评估时用 mock 工具、固定检索快照；生产里把「上游波动」显式作为状态告诉模型。
6. **多次采样 + 裁决**：高价值任务跑 2~3 次取一致结果或让 judge 选；代价是成本翻倍，只用于关键节点。
7. **用分布而非单次结果衡量**：同一用例跑 5~10 次看通过率，上线门槛写「通过率 ≥ X%」，别用「跑了一次对了」下结论。

> 面试里别说「设 temperature=0 就稳定了」—— 那会被追问到崩。更准确的说法是：**随机性可以压低，稳定性主要靠约束、校验和确定性系统来保证**。

### 如何复现线上的一次 Agent 失败案例？

**一句话结论：能复现的前提是「当时的一切都被记录下来了」—— 输入、版本、外部依赖、随机状态，缺一样就只能靠猜**。

需要被记录的最小集合：

| 类别 | 具体字段 |
| --- | --- |
| **标识** | `run_id`、`thread_id`、租户、时间戳 |
| **输入** | 完整原始请求、当时拼好的完整 messages（含系统提示、历史、工具结果） |
| **版本** | 模型名与版本、Prompt 版本、工具 schema 版本、图结构版本、检索索引/文档版本 |
| **参数** | temperature / top_p / `recursion_limit` / 各超时配置 |
| **外部依赖** | 每次工具调用的请求与**原始返回**（或可回放的快照）、上游状态 |
| **过程** | 完整 Trace、每步 State、checkpoint ID |
| **结果** | 最终输出、错误、token 与耗时 |

复现步骤：

1. 用 `run_id` 拉出这次运行的完整 Trace 和输入快照。
2. **冻结所有版本号**，用同一配置重放；外部工具调用优先用录制回放（mock），排除上游变化干扰。
3. 若重放不复现，依次放开变量：先放开工具真实返回，再放开检索索引 —— 定位是内部逻辑还是外部数据变了。
4. 用 **Checkpointer / Time Travel** 从出错那一步的 checkpoint 直接重跑，省掉前面几十步。
5. 复现后把该用例连同期望结果**加入评估集**，修完跑回归确认不再复发。

落地上线前就该准备的两件事：

- **Trace 与输入快照默认开启**（含脱敏策略），不要等出事才补埋点 —— 没记录的事故无法复盘。
- **敏感数据处理**：完整 Prompt 常含 PII，存储要有权限控制与保留期限；既要够复现，也要合规。

> 一个诚实提醒：**100% 复现不总做得到**（模型版本下线、上游不可回放）。所以工程上还要准备「可解释」的兜底 —— 至少能从 Trace 说清当时为什么走了那一步。

### 常见的 Agent 失败模式有哪些？（死循环、工具参数错误、忽略指令、过早结束、上下文丢失）

**一句话结论：失败大多不是「模型不够聪明」，而是循环没有终止条件、状态没管好、或者错误信息没被正确反馈**。

| 失败模式 | 典型表现 | 根因 | 防线 |
| --- | --- | --- | --- |
| **死循环** | 反复调同一个工具 / 两个 Agent 互踢 | 条件边恒真、错误未被正确写回、无步数上限 | 计数器 + `recursion_limit` + 同参数重试上限 + 业务预算 |
| **工具参数错误** | 编造 ID、类型不符、必填缺失 | schema 太松、描述含糊、模型自由填了本该服务端给的值 | 严格 schema + 服务端注入身份 + 校验失败回填重试 |
| **忽略指令** | 不遵守格式、调用了禁用工具 | 规则埋在长上下文中段、工具结果把指令挤走、注入攻击 | 关键规则放首尾、确定性校验器、权限兜底 |
| **过早结束** | 只查了一次就下结论、没验证就返回 | 没有「证据是否充分」的判断节点、结束条件太宽 | 加自检节点 / 校验器，把「证据不足」作为显式状态 |
| **上下文丢失** | 长会话忘了用户最初的要求 | 无 reducer 覆盖、粗暴截断、State 里塞不下 | 正确 reducer、压缩留锚点、关键约束常驻 |
| **副作用重复** | 邮件发两次、重复下单 | 重试/中断恢复导致节点重放，没有幂等键 | 幂等设计、状态查询确认、`interrupt` 前不放副作用 |
| **成本/延迟失控** | 一次任务烧掉几十万 token | 并行 + 循环叠加、工具返回未裁剪 | 每任务预算、输出裁剪、最大步数、告警 |

一个统一的看法：

> 这些模式可以归成三类 —— **控制流失控**（循环/过早结束）、**状态失控**（丢失/重复）、**边界失控**（参数/权限/成本）。对应的三类防线分别是终止条件、Checkpointer + 幂等、以及校验器 + 预算上限。排查时先归类，再查具体层，比逐个现象硬猜快得多。

## 九、性能、成本与稳定性

### 如何降低 Agent 的延迟？（流式、并行、缓存、小模型路由、减少步骤）

**一句话结论：Agent 的延迟主要是「串行步数 × 每步模型调用」，所以第一优先级是**减少步数**，第二是让首字节更早出现，第三才是并行和缓存**。

按收益排序的手段：

1. **减少步骤**：合并能一次做完的工具调用、去掉不必要的「先规划再确认再执行」中间轮、把确定性判断从模型手里交给代码。**少一轮 LLM 调用通常比任何优化都有效**。
2. **流式输出**：先让首 token 尽快到达（TTFT），用户感知延迟大幅下降，虽然总时长没变。Agent 里还要流式推送「思考/工具状态」，避免长时间白屏。
3. **并行无依赖调用**：多个只读工具同时发（见第七章），把多次串行等待叠成一次；LangGraph 的 fan-out 同理。
4. **小模型路由**：分类、意图识别、格式抽取、简单改写用小模型/快模型，只有复杂推理才上大模型。
5. **Prompt Caching**：稳定的系统提示 + 工具定义作为前缀被复用，跳过最贵的 prefill，既降延迟又降成本（见下一题）。
6. **精简上下文**：工具结果裁剪、历史压缩 —— 输入 token 越少，prefill 越快。
7. **基础设施**：就近区域、连接复用、避免每次新建 HTTP client、 embedding / Rerank 模型批处理。

要分清楚的两个指标：

- **TTFT（首 token 延迟）**：用户「感觉快不快」，靠流式 + 缓存 + 精简上下文。
- **端到端总时长**：靠减少步数 + 并行。

> 一个反直觉的提醒：**并行能降总时长，但会同时提高瞬时 QPS，容易触发上游限流反而更慢**。上并行前先确认配额，并给每个分支独立超时。

### 如何控制 Token 成本？（Prompt Caching、模型分级、压缩上下文）

**一句话结论：Agent 每一步都重发几乎相同的上下文，所以成本优化的核心不是「换个便宜模型」，而是**别为重复的内容反复付钱**。

**1. Prompt Caching（最高性价比）**

- 原理：模型推理最贵的一步是给输入算 KV 缓存。服务商把**重复的 prompt 前缀**存起来，下次命中直接复用，跳过 prefill。
- **只匹配前缀**：稳定内容（系统提示、工具定义、输出 schema、few-shot、固定文档）必须放**最前面**，变化内容（用户输入、当前时间、本轮历史）放**最后**。
- 顺序错了就完全失效：哪怕只把 `user_id` 或时间戳插在系统提示前面，缓存也命中不了。
- 各家机制不同：有的**自动**做前缀匹配，有的要**显式标记缓存断点**；一般都有最小长度门槛（千 token 量级）和空闲 TTL（分钟级，持续命中会续期）。
- 两个诚实提醒：
  - **缓存写入通常有溢价**，读写次数太少反而更贵；低流量、每个请求都不同的场景收益很小。
  - **输出 token 不缓存**，而输出单价远高于输入 —— 所以「逼模型简洁」往往比缓存更直接。

**2. 模型分级 / 路由**

- 把任务按难度分层：意图分类、参数抽取、格式转换、摘要走小模型；复杂规划和多跳推理走大模型。
- 在 LangGraph 里这很自然 —— 不同节点绑不同模型。
- 配套要有「小模型搞不定就升级」的兜底路径，别为了省钱牺牲成功率。

**3. 压缩上下文**

- 工具结果在工具层裁剪/摘要，别原样回传（第七章）。
- 历史用滑动窗口 + 摘要 + 按需检索（第六章）。
- 系统提示只放**每条都适用**的规则，其余按需加载（Skills / 检索）。

**4. 减少输出与步数**

- 用结构化输出代替长篇解释；明确 `max_tokens`；禁止无用的开场白。
- 设每任务 token 预算与最大步数，超限降级或转人工。
- 不需要实时的批量任务（离线评估、文档处理、embedding 回填）走 **Batch API**，通常有明显折扣。

**5. 成本可观测**

- 每次运行记录 input/output/缓存命中 token，按 `run_id` / 任务类型 / 租户聚合。
- 监控「单任务成本」而不是只看总账单 —— 某个 Prompt 改动导致步数翻倍，总成本会悄悄涨上去。

> 收尾一句：**缓存、分级、压缩三者是相乘的**；但一切优化都要在评估集上验证质量没退化，否则省下的钱会以「答错」的形式还回去。

### 如何做模型降级与容灾（Fallback、重试、限流、超时）？

**一句话结论：把上游当不可靠依赖来设计 —— 每类错误有明确策略，且任何策略都不能无限重试**。

按错误类型给策略：

| 情况 | 策略 | 注意 |
| --- | --- | --- |
| **429 限流** | 指数退避 + 抖动重试；超限则切备用模型/供应商 | 尊重 `Retry-After`；并发过高时先降并发而不是猛重试 |
| **5xx / 超时** | 有限次重试 → fallback 到备用模型 → 再不行降级回答 | 每次请求独立超时，且小于整体超时 |
| **模型下线/版本变更** | 配置里维护可切换的模型别名 | 别把模型名硬编码散落在代码各处 |
| **成本/配额触顶** | 降到小模型或关闭非关键节点 | 要有明确的降级开关，不能靠人临时改代码 |
| **完全不可用** | 返回**明确的**兜底（缓存答案 / 转人工 / 稍后重试） | 不要伪装成正常答案 |

工程要点：

- **Fallback 链要预先验证**：备用模型的输出格式、工具调用能力、上下文长度可能不同，切换后要能跑通同样的 schema。
- **重试必须幂等**：重试一次 LLM 调用没事，重试一次「发邮件」就是事故。有副作用的动作不自动重试，先查状态。
- **限流分两层**：保护自己（每租户/每用户并发与配额）+ 保护上游（并发信号量）。
- **熔断**：连续失败达到阈值就暂时熔断，避免雪崩时所有请求一起排队烧钱。
- **可观测**：记录每次重试、fallback、熔断事件与原因，按模型统计成功率与 P95 —— 降级是不是真的生效，要靠数据说话。

> 和 LangGraph 结合讲更自然：`with_fallbacks` / `with_retry` 是节点级的降级，而上面这些是**服务级**的容灾，两层都要有。

### 语义缓存（Semantic Cache）是什么？有什么风险？

**一句话结论：把「意思相近的问题」直接复用之前的答案，跳过整次模型调用；省钱很猛，但也是最容易答错的一个优化**。

和 Prompt Caching 的区别（这题最容易被问混）：

| 对比 | Prompt Caching | 语义缓存 |
| --- | --- | --- |
| 谁实现 | **模型服务商**，服务端自动/显式 | **你的应用**，自己存 |
| 省什么 | 重复输入前缀的 prefill 费用 | 整次推理（连输出都省了） |
| 匹配方式 | **精确前缀匹配** | 向量相似度（阈值判定） |
| 结果 | 模型重新生成，输出逐字节一致 | **直接返回旧答案**，模型没参与 |

典型做法：问题 → embedding → 向量库检索相似问题 → 相似度超阈值就返回缓存答案；否则正常走模型，结束后写入缓存并设 TTL。

主要风险（重点讲这些）：

1. **语义相似 ≠ 答案相同**：「怎么退款」和「怎么退款到已注销的卡」向量很近，答案完全不同。
2. **上下文/个性化被忽略**：带用户身份、实时状态、会话历史的问题绝不能缓存，否则会**串人**甚至泄露他人数据。
3. **时效性问题**：价格、库存、政策类答案缓存几天就变成错误信息。
4. **阈值难调**：太松就误命中（答非所问且用户无法察觉），太紧就几乎不命中（白做）。
5. **错误会被放大**：一个错误的答案被缓存后，会反复返回给所有相似提问。

控制手段：

- **只缓存高确定性场景**：FAQ、通用知识、文档问答这类「与用户无关、与时间无关」的问题。
- **缓存 key 包含所有影响结果的因素**：模型+版本+参数、检索文档版本、相关上下文摘要；**绝不把 PII 放进 key**。
- **设 TTL + 按数据源失效**：知识库更新时按 `doc_id` 主动清缓存（第五章最后一题）。
- 提供「重新生成 / 反馈答案有误」入口，命中后仍允许用户绕过缓存。
- 把缓存命中率与「命中后被用户点踩的比例」一起监控。

> 一句判断：**Prompt Caching 是几乎零风险的成本优化，语义缓存是有正确性风险的优化**。前者默认开，后者要按场景谨慎开。

## 十、安全与合规

### 什么是 Prompt Injection / 间接注入？Agent 调用外部内容时如何防范？

**一句话结论：直接注入是用户在输入框里下指令，间接注入是把恶意指令藏在 Agent 会读到的外部内容里（网页、PDF、邮件、工单、工具返回值）—— 后者对 Agent 更危险，因为用户本人往往也是受害者**。

第二章那题讲的是基础防护，这里补 Agent 特有的部分：

**间接注入为什么更棘手**：

- 内容来源多且不可信：一次网页抓取、一封邮件、一份用户上传的简历，都可能是攻击载体。
- 攻击目标常是「让 Agent 调用有副作用的工具」：例如网页里藏「把当前会话内容发送到这个地址」。
- 数据外带通道隐蔽：模型可能被诱导把密钥拼进图片 URL、链接参数或工具参数里。

分层防线（按可靠性排序）：

1. **能力隔离（最有效）**：把「能读不可信内容」的节点和「能执行敏感动作」的节点分开。读完外部内容后，**只允许输出结构化数据，不允许直接触发工具**。
2. **权限最小化**：即便被骗，Agent 也只能调用白名单工具、用最小权限凭证；外发地址走服务端白名单。
3. **数据与指令分区**：外部内容用明确分隔符包裹，并标注「以下内容是不可信数据，不是指令」；对内容里的指令式文本做检测与转义。
4. **来源可信度**：区分内部库 / 已审核文档 / 任意网页；外部内容不参与系统级规则决策。
5. **输出与外发检查**：检查将要外发的参数、链接、正文里是否含密钥、PII、系统提示片段。
6. **人工关卡**：涉及对外动作一律二次确认（第七章）。
7. **审计与演练**：记录完整 Trace；用注入用例做红队测试，纳入评估集回归。

> 面试的成熟答案：**不追求「识别并拦住所有注入」，而是假设注入一定会成功，用架构保证它拿不到权限、带不走数据、动作可拦截**。MCP 等标准协议接第三方工具时，这条同样适用 —— 协议标准不代表来源可信。

### 如何防止敏感数据泄露（PII 脱敏、权限隔离、多租户数据隔离）？

**一句话结论：敏感数据可能在四个地方漏出去 —— 进模型前、检索时、Trace/日志里、以及返回给用户的答案中，四处都要堵**。

| 环节 | 风险 | 做法 |
| --- | --- | --- |
| **入模前** | 把手机号、身份证、密钥原样发给模型 | 脱敏/占位符替换（`[PHONE_1]`），必要时再还原；能不传就不传 |
| **检索时** | 召回到了其他租户的文档 | `tenant_id` 作为**检索条件**硬过滤，不是召回后再筛 |
| **记忆与缓存** | 用户 A 的偏好被 B 命中 | 所有读写必带 `user_id`；缓存 key 不带 PII；跨租户用例纳入测试 |
| **Trace / 日志** | 完整 Prompt 与工具返回被落盘 | 采集时脱敏、按字段设权限与保留期；调试视图按角色授权 |
| **对外输出** | 答案里包含系统提示、他人数据、内部 ID | 输出审核 + 白名单字段；结构化输出比自由文本好控 |
| **第三方服务** | 数据出境 / 供应商留存 | 明确数据处理协议；高敏场景用自托管模型与本地向量库 |

权限隔离的三条硬规则：

1. **身份来自服务端**：从鉴权上下文取 `user_id` / `tenant_id`，绝不采信模型或客户端传入的身份字段。
2. **每一层都校验**：API 层、工具层、检索层、数据库层各自按身份过滤，不依赖上游「应该已经校验过了」。
3. **默认拒绝**：没有明确授权的资源一律不可访问；新加的数据源默认不开放给 Agent。

还要有合规配套：

- 数据分类分级（公开 / 内部 / 敏感），不同级别决定能否入模、能否进日志、留存多久。
- 提供用户查看/删除自己数据的入口；日志与记忆有明确保留期和清理任务。
- 定期做越权测试：**用 A 的 token 尝试问出 B 的数据**，这是最有效的一类回归用例。

> 一句实话：多数泄露事故不是模型「主动泄密」，而是**检索没加租户过滤、日志原样打印、或者缓存 key 设计漏了用户维度**。

### 如何做输出内容审核与 Guardrails？

**一句话结论：Guardrails 是模型之外的确定性检查层，分「输入侧」和「输出侧」，能写代码判的一律别交给模型判**。

常见的三类护栏：

| 类型 | 检查什么 | 实现方式 |
| --- | --- | --- |
| **输入侧** | 注入模式、越权请求、超长输入、敏感词、PII | 规则/正则、分类器、长度限制、权限校验 |
| **输出侧** | 格式合法性、禁用内容、PII/密钥泄露、引用是否真实、事实是否忠于上下文 | Schema 校验、确定性规则、小模型分类器、忠实度检查 |
| **动作侧** | 工具是否白名单、参数是否越界、金额/次数上限 | **业务代码**，与模型判断解耦 |

设计原则：

- **并行或前置执行**：输入护栏在调模型前跑；输出护栏在返回用户/执行动作前跑。别等生成完了才发现该拒答。
- **分层而不是一坨**：便宜的规则先跑（正则、schema、枚举），贵的模型分类器只处理规则判不了的模糊情况。
- **明确失败策略**：拦下之后是「拒答 / 转人工 / 重试生成 / 降级到安全模板」，要提前定义，不能临时抛异常。
- **可配置**：不同租户、不同业务线的规则强度不同；规则要能灰度、能回滚、带版本。
- **可观测**：记录每次拦截的类型与原因，误拦率要监控 —— 护栏过严会毁掉体验。

一个必须承认的局限：

> Guardrails 降低风险但不提供保证。**真正的安全边界仍然是权限和动作控制**：即使一段违规文本溜过了输出审核，它也改不了数据库、发不了邮件，损失就有限。

### 如何限制 Agent 的权限范围（最小权限原则）？

**一句话结论：给 Agent 一套「只够完成本任务」的独立身份和凭证，而不是复用人的全权限账号**。

落地清单：

1. **独立服务身份**：Agent 拥有自己的服务账号/角色，不用开发者或管理员的密钥；凭证走环境变量或密钥管理服务，运行时按需签发的短期凭证更好。
2. **工具白名单**：按任务动态挂载工具（第七章），没挂的工具**在服务端也不接受调用**，不能只靠「不告诉模型」。
3. **资源级限制**：数据库只授权特定表/视图、只读优先；文件系统限定目录；网络出站走白名单。
4. **动作分级**：只读 → 可回滚写 → 对外不可逆，逐级加审批（第七章）。
5. **配额与边界**：金额上限、单日次数、批量条数上限、并发上限、总预算 —— 用确定性代码强制。
6. **身份不可伪造**：`user_id` / `tenant_id` / 角色一律从鉴权上下文注入，工具 schema 里干脆不暴露这些参数。
7. **审计与回收**：每次动作留 `who/what/when/依据哪次 run`；任务结束回收临时凭证；定期 review 权限是否越用越大。

> 面试收尾可以用这句：**最小权限不是一条配置，而是「身份 + 白名单 + 资源边界 + 配额 + 审批 + 审计」六件套**。少任何一件，模型的一次误判就可能变成一次真实事故。

## 十一、全栈与工程化

### 如何设计一个 Agent 后端服务？（API 设计、异步任务、会话管理、鉴权）

**一句话结论：按「有状态、长耗时、会中断」的服务来设计，而不是按普通 CRUD 接口** —— 这是它和一般 Web 后端最大的区别。

**API 设计**（一套够用的最小集合）：

| 接口 | 作用 |
| --- | --- |
| `POST /runs` | 创建一次运行，立即返回 `run_id`（不等待结果） |
| `GET /runs/{id}/events` | SSE / WebSocket 推送增量事件 |
| `GET /runs/{id}` | 查状态、结果、成本（轮询兜底） |
| `POST /runs/{id}/resume` | 人工审批后恢复（HITL） |
| `POST /runs/{id}/cancel` | 取消运行并清理资源 |
| `GET /threads/{id}` | 会话历史与 checkpoint 摘要 |

**四个关键设计点**：

1. **鉴权**：所有身份从 token 解析，`thread_id` 与 `user_id` 绑定；**绝不让客户端指定 user_id**，也要校验它访问的 thread 属于自己。
2. **异步任务**：HTTP 层只负责接单和推事件，真正的 Agent 循环在后台 worker / 任务队列里跑（Celery / ARQ / 自研队列），否则长任务会占满连接并被打超时。
3. **会话管理**：`thread_id` 作会话主键，Checkpointer 落 Postgres；保留策略与归档任务要有；跨用户隔离写进测试用例。
4. **状态与事件模型**：定义统一的事件类型（`token`、`tool_start`、`tool_end`、`plan_updated`、`needs_approval`、`error`、`done`），前端和后端共用同一套 schema（用 Pydantic 定义、TS 侧生成类型）。

配套细节：

- 每次运行记录 `run_id`、模型/Prompt/工具版本、token 与成本，接到 Trace 系统。
- 限流按用户/租户 + 全局两层；总并发、单任务步数与预算都设上限。
- 取消要真的能停：worker 监听取消信号，在节点边界检查并退出，同时清理临时资源。

> 和「后端/02 FastAPI 接口开发」对照看：那里讲的是**单个接口**怎么写对；这里讲的是**一次运行**怎么被创建、跟踪、暂停、恢复、取消。

### 长耗时 Agent 任务如何处理？（异步队列、WebSocket/SSE、任务状态轮询、断线重连）

**一句话结论：HTTP 请求不能跟着 Agent 一起跑几十秒到几分钟 —— 把「执行」和「观察」拆开，任务进队列，结果走事件流**。

整体链路：

1. `POST /runs` 校验参数 → 写入任务表（状态 `queued`）→ 投递队列 → **立刻返回 `run_id`**。
2. Worker 取任务，置 `running`，用 `thread_id` 启动图执行；每个节点产出事件，写到事件总线（Redis Stream / Pub-Sub / 数据库表）。
3. 前端订阅 `GET /runs/{id}/events`（SSE），实时渲染增量与工具状态。
4. 需要人工确认时置 `waiting_approval`，推送 `needs_approval` 事件，前端展示确认卡片，用户点确认后调 `/resume`。
5. 结束置 `succeeded / failed / cancelled`，写结果与成本，发 `done` 事件。

断线重连怎么做：

- 事件带**单调递增序号**；SSE 用 `Last-Event-ID`（或查询参数）从断点续传，服务端保留最近一段事件缓冲。
- **不让重连触发重跑**：Agent 状态在 Checkpointer 里，重连只是重新订阅事件流；`run_id` 幂等。
- 轮询兜底：`GET /runs/{id}` 返回当前状态与已产生的事件，网络环境不支持长连接时降级用。
- 心跳与超时：定期发注释帧保活，区分「网络断了」和「任务真的卡住」。

几个真实坑：

- **用户关页面不等于任务该停**：要区分「断开订阅」和「主动取消」；前者继续执行，后者才发取消信号。
- **多实例部署**：事件必须走共享总线（Redis / DB），不能存在某个 worker 的内存里，否则重连到另一台就丢事件。
- **任务卡死检测**：设最长挂钟时间 + 心跳时间戳，超时由看门狗置失败并告警。
- **SSE 反向代理缓冲**要关（第二章已提），否则事件会攒成一坨。

> 一句话概括架构：**队列负责「跑」，事件流负责「看」，Checkpointer 负责「不丢」，幂等键负责「不重」**。

### Python 的 asyncio、协程、await 原理？FastAPI 如何处理并发？

**一句话结论：asyncio 是单线程事件循环 + 协作式调度，`await` 把控制权交还事件循环；FastAPI 用它在等待 IO 时切换去处理别的请求** —— 它解决的是 IO 并发，不是 CPU 并行。

核心机制：

1. **事件循环**：一个线程里维护就绪队列，谁的逻辑等 IO 完成就唤醒谁。
2. **协程**：`async def` 返回的是协程对象，**调用它不会执行**，必须 `await` 或交给 `asyncio.create_task` 调度。
3. **`await` 的含义**：挂起当前协程、把控制权还回事件循环，让循环去跑其他已就绪的任务；IO 完成后再恢复。这叫**协作式** —— 协程不主动让出，别的任务就只能等。
4. **并发 ≠ 并行**：单线程里多个协程交替推进，适合网络/数据库等 IO 等待；CPU 密集计算会一直占着线程，把整个循环卡住。

FastAPI 的并发模型：

- `async def` 路由运行在事件循环里，适合**内部全是异步调用**（`httpx.AsyncClient`、`asyncpg`、Redis asyncio）。
- `def`（同步）路由会被自动放到**线程池**执行，所以同步库不会卡死事件循环 —— 但线程池也有上限。
- 因此最经典的坑：在 `async def` 里用了 `requests`、`time.sleep`、同步数据库驱动，整个进程的所有请求一起被阻塞。

Agent 场景为什么特别重要：

- 一次 Agent 运行里大量时间花在**等模型、等工具、等检索**，天生适合异步。
- 但 LLM 客户端、向量库客户端、数据库驱动要**全部用异步版本**，混一个同步的就把并发优势抵消了。
- CPU 密集步骤（大文件解析、embedding 本地计算）应丢到线程池 / 进程池，别放在事件循环里。
- 用信号量限制对上游的并发，避免高并发下把模型 API 打限流。

> 更细的 `asyncio` / `def` 选型与代码示例在「后端/02 FastAPI」，这里记住一句就够：**`async def` 里不能出现任何阻塞调用**。

### Pydantic 的作用是什么？在 Agent 开发中用在哪些地方？

**一句话结论：Pydantic 用类型注解做运行时数据校验与序列化 —— 在 Agent 里它是「把不可信的模型输出变成可靠程序对象」的关键一层**。

基础作用：

- 定义数据模型（字段类型、必填、默认值、约束）。
- 解析时**校验并转换**（字符串 `"3"` 可按配置转成 int，不合法就抛清晰的 `ValidationError`）。
- 导出 JSON Schema，可直接用作 Structured Output 的 schema。
- 序列化成 dict / JSON，支持别名、自定义校验器。

Agent 开发里的具体落点：

| 位置 | 用途 |
| --- | --- |
| **结构化输出** | 定义模型输出的 schema，交给 `with_structured_output` / 严格模式，解析失败自动重试 |
| **工具入参** | `@tool(args_schema=...)` 校验模型填的参数，挡住编造的 ID 和错误类型 |
| **工具返回值** | 约束返回结构，便于裁剪和回填上下文 |
| **State Schema** | LangGraph 的 State 可用 Pydantic 定义，字段带校验 |
| **API 层** | FastAPI 的请求/响应模型，自动生成 `/docs`；事件协议前后端共用一份定义 |
| **配置管理** | 环境变量、模型参数、租户配置集中校验，启动时就发现配置错误 |

两个版本注意点：

- **Pydantic v1 / v2 不兼容**：`model_validate` / `model_dump`（v2）对应旧版 `parse_obj` / `dict`；`.dict()` 在 v2 已弃用。
- **混用是常见线上事故**：LangChain、FastAPI、LangGraph 各依赖不同版本时容易冲突，锁文件里要显式统一，升级前跑回归。

> 一句话点题：Agent 里模型输出天然是**不可信输入**，Pydantic 就是这道边界上的校验器 —— 它和结构化输出、错误回填重试一起，构成第二章那「四道防线」。

### 数据库选型：关系型、Redis、向量库分别在 Agent 系统中承担什么角色？

**一句话结论：按「数据是否可丢、是否需要查询/事务、访问频率」分工 —— PG 是权威数据源，Redis 是加速与临时状态，向量库负责语义检索**。

| 存储 | 承担什么 | 为什么 |
| --- | --- | --- |
| **PostgreSQL（+ pgvector）** | 用户、会话、消息、长期记忆、Checkpointer、业务数据、向量 | 需要持久、可查询、要事务、要权限隔离；pgvector 让业务数据与向量同库，省一套组件 |
| **Redis** | 限流计数、登录态、短期上下文、热点回答缓存、任务队列/事件总线 | 高频读写、可丢失、可重建、要 TTL |
| **专用向量库** | 大规模向量检索 | 亿级量级或高 QPS 时才需要（选型见第五章） |

一条清晰的判断规则：

> **持久且需要查询/事务/审计的放 PG；高频、可丢、可重建的放 Redis；需要语义相似度检索的放向量索引**。

Agent 特有的几个点：

- **Checkpointer 必须持久化**：`InMemorySaver` 重启就丢，生产用 Postgres；checkpoint 表要有保留/归档策略。
- **多 worker 下别用进程内存存状态**：全局变量在多进程里各持一份，用户刷新到另一实例就「失忆」。这也是第二章那段 AI 示例代码里的经典错误。
- **连接池总量要算**：`实例数 × 池大小` 不能超过 PG 连接上限（后端/03 有展开）。
- **权威来源唯一**：长期对话历史、重要数据以 PG 为准，Redis 只是**加速层**；缓存可以丢，丢了要能从 PG 重建。

> 一个常见的架构错误：把「最近几轮对话」只放 Redis 且当唯一副本，Redis 一重启用户历史就全没了。短期上下文可以放 Redis，但**消息记录要同时落 PG**。

### 如何做 Agent 应用的部署、日志、监控与告警？

**一句话结论：除了常规服务的指标，Agent 还必须监控「质量、轨迹、成本」三类业务指标 —— 只盯 CPU 和 QPS 是完全看不出 Agent 有没有在好好干活的**。

**部署**：

- 容器化（见下一题）+ 多副本；**有状态的部分外置**（Checkpointer → PG，事件 → Redis/DB），让 worker 本身可水平扩缩、可随时重启。
- 长任务用独立 worker 池，和短请求 API 分开部署，避免互相拖垮。
- 配置（模型别名、Prompt 版本、预算上限、限流阈值）走环境变量/配置中心，能不重启就灰度切换。

**日志与 Trace**：

- 结构化日志 + 完整 Trace（第八章）；每次运行记 `run_id` / `thread_id` / 模型与 Prompt 版本 / token / 成本 / 每步耗时。
- 采集时脱敏，日志权限与保留期按数据分级设定。

**监控指标分四层**：

| 层 | 指标 |
| --- | --- |
| **服务** | QPS、错误率、P50/P95 延迟、队列积压、worker 存活、连接池使用率 |
| **上游** | 模型调用成功率、429/5xx 比例、TTFT、各模型 P95、fallback 触发次数 |
| **质量** | 任务成功率、工具调用失败率、拒答率、忠实度抽检、用户负反馈率 |
| **成本** | 单任务 token / 成本、缓存命中率、平均步数、并行调用数 |

**告警要设在这些地方**（比 CPU 更有用）：

- 成功率或忠实度相对基线突然下降 —— 常常意味着模型版本/Prompt/索引变了。
- 平均步数、工具失败率、循环次数上升 —— 死循环或上游故障的早期信号。
- 单任务成本 / 总 token 突增 —— 有人改了上下文或缓存失效。
- 队列积压、任务超时、`waiting_approval` 长时间未处理。
- 上游 429 比例上升、fallback 频繁触发。

> 一个成熟做法：**把线上用户负反馈自动转成一条评估集用例**，并触发一次回归跑批。这样监控和第八章的评估闭环就连起来了。

### 前端侧如何展示 Agent 的思考过程、工具调用状态和流式输出？（这是你的天然优势）

**一句话结论：别把它当「一个聊天框」做 —— 把 Agent 运行建模成一条**可交互的事件时间线**，前端负责把结构化事件渲染成可理解、可干预的过程**。

**1. 先定事件协议（前后端共用一份 schema）**

建议至少定义这些事件类型，每个都带 `run_id`、`seq`（单调递增，用于重连续传）、`ts`：

| 事件 | 前端呈现 |
| --- | --- |
| `plan_updated` | 折叠的步骤清单，标出当前在第几步 |
| `token` / `message_delta` | 打字机式增量文本 |
| `tool_start` / `tool_end` | 工具卡片：图标 + 名称 + 参数摘要 + 运行中/成功/失败 + 耗时 |
| `retrieval` | 「引用了 3 篇文档」可展开看来源片段 |
| `needs_approval` | 醒目的确认卡片，展示**具体参数预览**与批准/拒绝按钮 |
| `error` / `done` | 失败原因与重试入口 / 汇总与成本 |

**2. UI 结构**

- **主区**：对话时间线（用户消息、最终答案、引用）。
- **侧栏 / 可折叠抽屉**：思考过程、计划、工具调用轨迹、token 与耗时 —— 让想看的人能看，不想看的人不被干扰。
- **每个工具卡片可展开**：看参数与返回摘要；失败卡片给「重试」或「换一种做法」入口。

**3. 流式渲染的细节**

- 用 `fetch` + `ReadableStream` 解析 SSE（第二章），**按 `\n\n` 缓冲切帧**，不要把 chunk 当完整事件。
- 增量文本用「追加到当前气泡」，不要每帧重渲染整段；注意中文/emoji 的多字节字符要用 `TextDecoder({ stream: true })`。
- 思考过程与最终答案**分开渲染**，避免把内部推理当成结论展示给用户。
- 断线按 `Last-Event-ID` / `seq` 续传，UI 显示「重连中」而不是清空重来。

**4. 交互与状态机**

- 明确状态：`queued → running → waiting_approval → succeeded / failed / cancelled`。
- 提供**暂停 / 取消 / 重新生成 / 编辑后继续**；审批卡片要用乐观更新 + 幂等提交，防重复点击。
- 长任务允许用户离开页面，回来按 `run_id` 恢复现场（对应第十一章第二节）。

**5. 前端必须守住的边界**

- **模型输出一律当不可信文本**：用安全的 Markdown 渲染、禁用原始 HTML、外链加 `rel="noopener noreferrer"`、防 XSS。
- **不信任事件里的身份与权限字段**：前端只做展示，权限由后端判定。
- 参数预览要脱敏（手机号、密钥、token），别把后端返回的原始对象整坨 `JSON.stringify` 出来。

> 面试里可以直接点出差异化价值：**后端同学容易把 Agent 当成一个返回字符串的接口，而前端能把它设计成「可观察、可打断、可回溯的过程」**。这对建立用户信任、以及做 HITL 审批界面，恰恰是最关键的一环 —— 也是全栈背景最能加分的地方。

### Docker / 容器化部署的基本流程？

**一句话结论：把「代码 + 依赖 + 运行环境」打成一致的镜像，部署就变成拉镜像、注入配置、启动进程；关键是分层缓存、监听地址和非持久化数据的外置**。

一个最小可用的 FastAPI / Agent 服务 Dockerfile：

```dockerfile
FROM python:3.12-slim
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt
COPY . .
CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8000"]
```

三个必须能讲清的点：

1. **先 `COPY requirements.txt` 装依赖，最后才 `COPY . .`** —— 利用镜像层缓存，代码改了不用重装依赖，构建快很多。
2. **`--host 0.0.0.0`** —— 容器里监听 `127.0.0.1` 外部根本访问不到，这是最高频的新手坑。
3. **slim 镜像 + 固定版本号** —— 镜像小、可复现；别用 `latest`，否则回滚时不知道上一版是什么。

Agent 服务额外要注意的：

- **状态外置**：Checkpointer 用 PG、事件用 Redis、上传文件用对象存储 —— 容器文件系统是临时的，重启就丢。
- **密钥走环境变量 / `.env` 运行时注入**，并写 `.dockerignore` 排除 `.env`、`.git`、`venv`、`__pycache__`；**镜像层是累积的**，后面删掉 `.env` 密钥仍在历史层里。
- **多副本**：worker 与 API 可分镜像或同一镜像不同启动命令；`depends_on` 只保证启动顺序，**不保证数据库已就绪**，要配 healthcheck 或应用侧重连重试。
- **容器里的 `localhost` 指容器自己**：连 PG 要用 compose 服务名（`db:5432`），不是 `localhost`。
- **优雅关闭**：`CMD` 用 exec form（JSON 数组）才能正确收到 SIGTERM，让在跑的 Agent 有时间保存 checkpoint。

> 完整的 compose、volume、日志排查、上线与回滚流程在「后端/03 数据与部署」；这里只要记住 Agent 的特殊性：**它是有状态服务，任何放在容器文件系统里的状态都会在下次部署时消失**。

## 十二、框架对比与选型

### LangGraph、AutoGen、CrewAI、OpenAI Agents SDK、Dify/Coze 各自的定位和取舍？

**一句话结论：先按「编排形态」和「要不要自己掌握运行时」分两类 —— 代码框架按控制力/复杂度排序，低代码平台换的是上手速度，交出去的是可控性**。

| 框架 | 心智模型 | 强项 | 主要取舍 |
| --- | --- | --- | --- |
| **LangGraph** | 显式**状态图**：State + Node + Edge | 复杂有状态流程、循环、Checkpointer 持久执行、HITL、Time Travel、可审计 | 学习曲线最陡，简单任务显得啰嗦 |
| **CrewAI** | **角色 + 任务**（role / goal / backstory） | 快速搭出「研究 → 写作 → 审核」这类顺序流水线，代码可读、非工程师也看得懂 | 条件逻辑和循环控制弱于 LangGraph |
| **AutoGen** | Agent 之间**对话**协作 | 研究型、代码生成/自纠错类多 Agent 探索 | **已进入维护模式**（见下方说明），新项目不建议起步 |
| **OpenAI Agents SDK** | 极简：Agents + **handoffs** + guardrails + sessions + tracing | 抽象最薄、上手最快、内置 tracing 与护栏，适合分流/专家移交 | 无内建持久执行与状态机；tracing 与托管工具偏 OpenAI 生态 |
| **Dify / Coze** | 低代码可视化编排 | 非工程人员也能搭、内置知识库/模型接入、最快出原型 | 定制与调试受限、复杂逻辑难表达、平台绑定与数据合规要评估 |

**几个 2026 年的重要现状**（面试时点出来很显时效感）：

1. **LangChain / LangGraph 1.0 于 2025-10-22 GA**。LangChain 收敛到核心抽象，`create_agent` **构建在 LangGraph 之上**；旧的 `AgentExecutor`、`create_react_agent` 已弃用，旧功能移到 `langchain-classic`。所以现在不是「LangChain 还是 LangGraph」二选一，而是**高层起步、需要控制时下潜到图**。
2. **AutoGen 已进入维护模式**，微软把它与 Semantic Kernel 合并为 **Microsoft Agent Framework**（2026 年 4 月 1.0 GA）。新项目应从 MAF 起步，很多网上对比文章还停在旧事实。
3. **MCP 已成为跨框架的工具互操作标准**，主流框架通过适配器接入；选型时不必再把「支持多少工具」当核心差异。
4. **LangGraph 与 LangSmith / Langfuse / OpenTelemetry 组成的可观测链路最完整**，这是生产选型里常被低估的一项。

选型时真正该问的三个问题：

- 工作流**有没有循环、审批门、断点恢复**需求？有 → LangGraph / MAF 这类带持久执行的运行时。
- 是不是**顺序流水线 + 快速验证**？是 → CrewAI 或低代码平台。
- 团队**能否接受平台绑定**、以及后续要不要把 Trace 导到自建监控？决定低代码能不能上生产。

> 一句稳妥的收尾：**框架差异没有「工程纪律」差异大** —— 一个评估集齐全、Trace 完整、权限收得紧的 CrewAI 项目，通常比一个没有评估和终止条件的 LangGraph 项目更容易上线。

### 低代码平台（Dify/Coze）与代码框架如何选择？

**一句话结论：低代码买的是「最快跑通」，付的是「可控性、可调试性、可迁移性」** —— 分界线是这套流程会不会成为长期核心资产。

| 维度 | 低代码平台 | 代码框架 |
| --- | --- | --- |
| 上手速度 | 小时级，可视化拖拽 | 天级，需要工程能力 |
| 谁来做 | 产品/运营也能参与 | 工程师 |
| 定制能力 | 受平台节点与配置限制 | 任意逻辑、任意状态机 |
| 调试 | 平台提供的运行记录，粒度有限 | 完整 Trace、单测、本地复现 |
| 评估与回归 | 通常较弱 | 可接入 CI、评估集、灰度 |
| 数据合规 | 要评估 SaaS 部署与数据留存 | 可完全自托管 |
| 迁移成本 | 高，编排逻辑锁在平台里 | 相对可控（但框架也有绑定） |

**适合低代码**：

- PoC / 内部小工具 / 需求还没验证，先要个能演示的东西。
- 标准 RAG 问答、固定表单流程，逻辑简单且不需要精细控制。
- 主要维护者不是工程师，且没有长期演进计划。

**适合代码框架**：

- 要进生产、要接权限/审计/多租户、要 SLA。
- 有循环、条件分支、人工审批、持久执行、失败恢复。
- 需要评估集回归、灰度、Trace 对接自建监控。
- 数据不能出网 / 要私有化部署。

> 一个常见且合理的路径：**用低代码验证需求 → 跑通后把核心链路用代码框架重写**。别把验证阶段的平台选型当成最终架构；反过来也别为了一个还没验证的想法先搭一整套图编排。

### 什么情况下不用任何框架、直接手写 Agent Loop？

**一句话结论：当你的流程简单到「一个 while 循环 + 一次模型调用 + 几个工具」时，框架带来的抽象成本大于收益**。

手写的核心其实只有几十行：

```python
def agent_loop(question, max_steps=8):
    messages = [{"role": "user", "content": question}]
    for step in range(max_steps):
        resp = client.responses.create(
            model="...", input=messages, tools=TOOLS
        )
        if not resp.tool_calls:          # 没有工具调用 = 给出最终答案
            return resp.output_text
        for call in resp.tool_calls:
            result = run_tool(call)       # 你的代码执行，带超时/校验/幂等
            messages.append(tool_result_message(call, result))
    return "达到最大步数，已停止"       # 兜底，不能无限跑
```

适合手写的场景：

- 工具 3~5 个、无分支、无人工审批、无跨会话恢复。
- 需要**精确控制**每一字节请求、超时、重试、成本归因与日志格式。
- 强合规/强审计，要求调用链完全透明、没有框架隐式行为。
- 依赖必须极简（边缘设备、Serverless 冷启动敏感、嵌入式环境）。

**但要先想清楚你会失去什么** —— 这些正是框架的价值：

| 手写要自己实现 | 框架提供 |
| --- | --- |
| 状态持久化与崩溃恢复 | Checkpointer / 持久执行 |
| 人工审批与暂停恢复 | `interrupt` / HITL |
| 逐步 Trace 与可观测 | LangSmith / OTel 集成 |
| 流式、批量、异步统一接口 | Runnable / stream_mode |
| 并行、重试、fallback | 内建能力 |
| 循环上限、状态合并 | reducer / recursion_limit |

> 判断线很实用：**一旦你开始手写「把状态存进数据库以便崩溃后恢复」，就已经在重新发明 LangGraph 了**。原型可以手写，生产里的长任务尽早换成熟运行时更划算。

> **本章不提供可背诵的答案**。下面 6 题考的是你亲历的事实，编造细节在追问两轮后一定会露馅。这里只给**回答骨架**和**必须提前准备的材料清单** —— 请按你自己「慧办」项目的真实情况填写，写成可直接口述的稿子。

> - 架构：一张图 + 数据流，标出哪些是模型节点、哪些是确定性代码。

### 请完整讲述你参与的 Agent 任务流系统：业务背景、架构、你负责的部分。

**推荐结构**（控制在 2~3 分钟，留下可被追问的接口）：

1. **一句话定位**：这是个给谁用、解决什么问题的系统。
2. **业务背景与痛点**：原流程怎么走、卡在哪、有没有量化。
3. **架构与数据流**：从用户发起 → 接口 → 编排层 → 工具/检索 → 状态存储 → 前端展示，按顺序列一遍。
4. **为什么是 Agent 而不是固定流程**：指出哪一步必须先看到结果才能决定下一步。
5. **你负责的部分**：明确到具体模块，不要说「我参与了」。
6. **结果与数字**：上线效果、稳定性、成本。

**自检**：

- [ ] 听的人能画出你的系统吗？
- [ ] 「你做了什么」和「团队做了什么」分得清吗？
- [ ] 有没有一个数字支撑「这东西有用」？

### Agent 逻辑是如何设计的？为什么这样拆分节点？

**回答要点**：

- 先讲**拆分依据**：是按职责（检索 / 判断 / 执行 / 校验）、按风险等级（只读 vs 副作用）、还是按可复用性。
- 再讲**哪些步骤故意不用模型**：确定性判断交给代码，说清为什么（可复现、省钱、可审计）。
- 讲**State 里放了哪些字段、为什么**，以及消息为什么用累加 reducer。
- 讲一条**条件边**：什么情况走哪条路、什么情况结束、怎么防死循环。
- 讲一件**没这么做而后悔的事**（为下一题「重做会改什么」埋伏笔）。

**自检**：能说清「如果把这个节点合并掉会出什么问题」吗？说不清，说明拆分理由还不扎实。

### Prompt 是如何迭代优化的？有没有量化的前后对比？

**回答要点**（这题最忌讳只说「不断调试」）：

1. 起因：哪类 case 出错、从哪条反馈/日志发现的。
2. 定位：用 Trace 看当时完整输入，确认是 Prompt 问题而不是检索/工具问题。
3. 改动：具体改了什么（分区、few-shot、输出约束、工具描述），**一次只改一处**。
4. 验证：在固定评估集上跑前后对比 —— 成功率、格式合法率、平均步数、成本。
5. 固化：版本化、进回归集、灰度上线，异常能回滚。
6. 数字：给出「从 X% 到 Y%」这类真实对比；**没有精确数字就给量级和样本数，不要编**。

**自检**：改动前后用的评估集是同一份吗？模型版本和索引版本固定了吗？

### 遇到过最棘手的 Agent 问题是什么？怎么排查和解决的？

**推荐按 STAR 讲，重点放在「排查路径」而不是「问题多难」**：

- **现象**：用户看到什么、影响面多大、怎么发现的。
- **定位**：拿到 `run_id` → 看完整 Trace → 找出第一个偏离点 → 分层排除（Prompt / 工具 / 检索 / 模型）。
- **根因**：落到具体一层，说清机制，不要停在「模型不稳定」。
- **解决**：改了什么，以及**为什么这个改法能防止复发**（例如加了校验器、终止条件、幂等键、评估用例）。
- **验证**：回归集 + 线上观察，确认没引入新问题。

**自检**：如果面试官问「你怎么证明是这一层而不是另一层」，你有证据吗？

### 如果重做一次，你会在架构上改进什么？

**回答要点**：给 **1~2 个有代价的改进**，别列一串「会更完善」的口号。可以从这些真实方向里选：

- 一开始就把 Checkpointer 做成持久化、把 `thread_id` 与用户身份绑定（而不是后来补）。
- 更早引入评估集与回归门禁，避免「改一处坏一处」。
- 把高风险动作从主链路里拆出来，前置人工确认与幂等设计。
- 工具结果在工具层就裁剪，而不是等上下文膨胀后到处救火。
- 把多 Agent 合并回一张图 —— 如果当时的拆分其实没带来收益。

每个改进都要补两句：**当初为什么没做**（时间/认知/优先级）+ **现在为什么值得做**（付出的代价换来了什么）。这比单纯「我会做得更好」可信得多。

### 作为前端，你是如何与后端/算法同学协作的？你的独特价值是什么？

**回答要点**（这是你的主场，尽量讲具体交付物）：

- **接口与协议**：谁定义事件协议 / 流式格式 / 错误码，你怎么推动前后端共用一份 schema（Pydantic → TS 类型）。
- **把不可见变可见**：你做的思考过程、工具状态、审批卡片、引用展示，让后端和算法同学能**直接看到 Agent 在干什么** —— 这往往反过来加速了他们的调试。
- **反馈闭环**：前端的点赞/点踩/「没帮上忙」入口，怎么变成评估集用例给算法侧用。
- **体验与信任**：流式首字节、断线重连、取消与重试、失败兜底，这些不是「美化」，是 Agent 能不能被用户接受的前提。
- **边界意识**：模型输出按不可信文本渲染、参数预览脱敏、权限交给后端判定。

**自检**：能不能说出一个「因为前端提了某个需求，后端/算法改了设计」的具体例子？这比罗列技术栈有说服力得多。

> 一句提醒：这一章的价值不在答案写得多漂亮，而在**每个结论都能指向一段你真实做过的代码、一次真实的事故、一个真实的数字**。面试前把上面那页事实材料准备好，比背模板有用得多。

## 十四、开放性 / 系统设计题

### 设计一个「企业内部知识库问答 Agent」，说明架构、数据流、难点。

**一句话结论：核心不是「接个大模型」，而是把权限、版本、引用可核查这三件事做进数据流里** —— 内部知识库答错或越权的代价，远高于答不上来。

**架构分层**：

| 层 | 职责 |
| --- | --- |
| **接入层** | SSO 鉴权、租户/部门身份注入、限流、审计入口 |
| **数据管道** | 多源采集（Confluence / 文档 / 工单 / PDF）→ 解析清洗 → 按结构切分 → embedding → 写 pgvector + BM25 索引；带 `doc_id`、部门、`version`、`updated_at`、权限标签 |
| **检索层** | Query Rewrite → 混合检索 → **按权限硬过滤** → Rerank → top 5~10 |
| **编排层** | 用图建模：判断要不要检索 → 检索 → 评估证据是否充分 → 不够则改写再查（限 2~3 轮）→ 生成 → 自检引用 |
| **生成层** | 强约束「只依据给定片段」，答案**带引用**；无依据时明确说「资料中未找到」 |
| **存储层** | PG：用户、会话、消息、checkpoint、文档元数据；Redis：限流与热点缓存 |
| **展示层** | 流式答案 + 可展开引用原文 + 反馈入口（反馈回流成评估用例） |

**数据流**（一次提问）：

1. 鉴权后从服务端拿到 `user_id` / 部门 / 权限范围，**不采信客户端传的身份**。
2. Query Rewrite 把口语化追问补成独立查询。
3. 混合检索时把权限标签作为**过滤条件**（先过滤再检索，不是召回后再筛）。
4. Rerank 精排，组装上下文并附来源 ID。
5. 生成后校验每条引用是否能在片段中找到；不通过则重生成或降级为「未找到」。
6. 记录 Trace、命中的文档 ID、成本；用户反馈入库。

**四个真正的难点**：

- **权限与多租户**：同一份问题不同部门该看到不同答案，过滤必须贯穿检索、缓存、记忆、日志。
- **文档质量与时效性**：版本冲突、过期政策、扫描件 OCR、表格错位 —— 多数「答不准」根因在这里，不在模型。
- **拒答的边界**：资料里没有时要能体面地说不知道，而不是编一段看起来很像内部口径的话。
- **评估闭环**：必须有带标注的评估集（含「应拒答」用例），每次索引/Prompt/模型变更跑回归。

> 加分的一句：**把「引用」做成一等公民** —— 它同时解决用户信任、答案核查、检索排错三件事，是这类系统性价比最高的设计。

### 设计一个「可自动处理工单/审批的 Agent」，如何保证可控与可审计？

**一句话结论：把「判断」和「执行」彻底分开 —— Agent 只产出结构化的建议动作，真正的写入由一个带规则、权限和审计的确定性执行器完成**。

**架构**：

1. **接入**：工单系统推送 → 校验签名与幂等键 → 入队。
2. **分类与抽取**（小模型 / 规则）：工单类型、金额、申请人、关联单据，输出结构化对象。
3. **检索与研判**：查制度文档、历史同类工单、用户额度；产出「建议动作 + 依据 + 置信度」。
4. **策略引擎（确定性代码）**：金额上限、白名单、黑名单、单日次数、必须由人审批的类型 —— **这一步不经过模型**。
5. **分流**：
   - 低风险 + 高置信 + 规则全过 → 自动执行。
   - 其余 → `interrupt` 生成审批卡片，展示具体参数与依据，等人批准。
6. **执行器**：带幂等键、事务边界、状态回查，调用工单系统写回；失败走重试/补偿。
7. **审计**：每次运行留 `run_id`、完整输入快照、模型版本、Prompt 版本、检索命中文档、建议动作、策略判定、审批人、最终动作与结果。

**可控性怎么保证**：

| 手段 | 作用 |
| --- | --- |
| **动作分级 + 白名单** | Agent 只能产出预定义动作，不能自由调用任意工具 |
| **确定性策略引擎** | 硬规则不交给模型判断 |
| **人工关卡** | 高风险/低置信强制审批，卡片显示参数预览 |
| **最小权限凭证** | 执行器用独立服务账号，只授权本流程所需字段 |
| **幂等 + 状态回查** | 超时/重试/中断恢复不会重复执行 |
| **步数与预算上限** | 防止失控循环 |

**可审计怎么保证**：

- **每次决策可解释**：为什么自动通过 / 为什么转人工，要能追溯到具体规则和引用文档。
- **不可篡改的审计日志 + 可回放**：用 `run_id` 能重放当时的输入与判定（第八章那套记录）。
- **回滚路径**：自动执行错了要能撤销或补偿，并保留原始记录。
- **定期抽检**：抽样人工复核自动通过的工单，统计误通过率，作为是否放宽自动化的依据。

> 收尾一句：这类系统**不该追求自动化率最大化**。上线初期应把自动执行范围收得很窄、全量留审计，用真实数据证明可靠性后再逐级放宽 —— 这正是第一章「按错误代价分级授权」的落地。

### 设计一个「多 Agent 协作的代码审查 / 数据分析系统」。

**一句话结论：多 Agent 的价值在于「视角分离 + 相互制衡」，但必须先设计好共享状态与终止条件，否则就是几个模型互相传话烧钱**。

以代码审查为例（数据分析可换成「取数 → 校验 → 分析 → 复核」同构流程）：

| 角色 | 职责 | 工具权限 |
| --- | --- | --- |
| **Coordinator**（Supervisor） | 拆任务、分派、汇总、决定何时结束 | 只读 + 调度 |
| **Reviewer A：安全/并发** | 查注入、越权、竞态、密钥泄露 | 只读代码 + 规则库 |
| **Reviewer B：正确性/边界** | 逻辑错误、空值、异常分支、边界条件 | 只读代码 + 单测结果 |
| **Reviewer C：性能/可维护性** | N+1、复杂度、重复代码 | 静态分析工具 |
| **Verifier**（确定性优先） | 跑 lint / 单测 / 类型检查，过滤掉模型幻觉 | 执行沙箱 |
| **Writer** | 汇总成带严重级别和文件行号的报告 | 只写报告 |

**关键设计决策**：

1. **并行 fan-out，统一 fan-in**：三个 Reviewer 并行只读，结果各写独立 State 字段（避免并发覆盖），由 Coordinator 合并去重。
2. **用确定性工具做校验器**：模型提的每条问题，尽量让 lint / 单测 / 规则去证实；**证伪的直接丢弃**。这是压住幻觉最有效的一招，也对应第四章 Reflection 那题的结论。
3. **结构化通信**：Reviewer 只返回 `{file, line, severity, category, evidence, suggestion}`，不让它们用自由文本互相转述。
4. **收敛与去重**：同一行多个问题按 category 合并；Coordinator 只做一次汇总，不做多轮互相辩论。
5. **终止条件**：固定一轮 fan-out + 一次校验 + 一次汇总，**最多一轮返工**（针对校验失败的条目）；设 `recursion_limit` 与总预算。
6. **最小权限**：Reviewer 全部只读；只有 Writer 能产出报告，**任何 Agent 都不能直接改代码或推分支**。

**必须警惕的三件事**：

- **不要为了「多 Agent」而多 Agent**：如果三个 Reviewer 用的是同一个模型、同一份上下文，拆开只增加成本，不如一次调用里用结构化 rubric 分三段输出。
- **链式成功率乘法衰减**：每多一次交接就乘一次可靠性，所以层数越少越好。
- **Trace 是前提**：没有逐步 Trace，多 Agent 的调试基本不可行。

> 一个务实的收尾：**先做成「单 Agent + 多 rubric + 确定性校验器」，只有当不同视角确实需要不同工具/上下文时，才拆成多 Agent**。

### 如何设计 Agent 的灰度发布与 A/B 测试？

**一句话结论：实验单元是「一次完整运行（run）」而不是「一个用户请求」，分流要稳定、指标要分层、回滚要能做到秒级切回上一版**。

**分流设计**：

1. **分流键**：按 `user_id`（或 `tenant_id`）哈希分桶，保证同一用户体验稳定；**不要用 `thread_id`**，否则同一用户在不同会话里来回跳版本。
2. **实验对象**：Prompt 版本、模型版本、工具 schema、检索策略、编排图 —— **一次只变一个变量**，多变量要设计正交实验。
3. **版本绑定**：每次运行记录所有版本号（模型/Prompt/索引/图结构），指标才能按版本聚合。
4. **放量节奏**：内部 → 1% → 5% → 20% → 50% → 100%，每档观察足够样本量与至少一个完整业务周期。

**指标分三层，缺一不可**：

| 层 | 指标 |
| --- | --- |
| **质量** | 任务成功率、拒答准确率、忠实度抽检、用户负反馈率、转人工率 |
| **效率** | 平均步数、工具调用失败率、P50/P95 延迟、TTFT |
| **成本与安全** | 单任务 token/成本、缓存命中率、护栏拦截率、越权用例通过率 |

还要看**分组指标**：整体平均分没变但某类任务退化 20% 的情况非常常见，必须按任务类型拆开看。

**工程配套**：

- **离线门禁先行**：新版本先在评估集上跑回归（第八章），不过门槛不允许进灰度。
- **配置化切换 + 秒级回滚**：模型别名、Prompt 版本、开关放配置中心，出问题立刻切回，不需要重新部署。
- **自动止损**：成功率/成本/延迟超阈值自动暂停放量并告警。
- **Trace 对比**：能取出 A/B 两版的完整轨迹做逐条 diff，才知道「好在哪、坏在哪」。
- **统计纪律**：样本量不足时别急着下结论；Agent 输出非确定，同一用例要多跑几次看通过率分布，而不是单次结果。

> 一个容易被忽略的点：**Agent 的 A/B 比普通 Web 功能更贵**，因为每次运行都要消耗 token。灰度前先估算成本，并给实验组设总预算上限，避免一个没止损的实验跑爆账单。

### 你如何看待 Agent 的未来趋势与落地瓶颈？

**一句话结论：瓶颈已经从「模型够不够聪明」转移到「系统够不够可靠、可评估、可治理」** —— 2026 年公开的生产实践与行业调查基本都指向同一个结论：demo 很容易，稳定跑在生产里很难。

**趋势（相对确定的方向）**：

1. **从「更自主」转向「分级授权」**：窄任务 + 明确成功标准 + 关键动作留人工关卡，比全自主助手更容易落地；自主性按风险分级授予（第一章）。
2. **评估与可观测成为一等基础设施**：多份 2026 年行业调查把「评估 / 可观测」列为首要落地障碍；有自动回归评估的团队，回滚率明显更低。指标从 `pass@1` 转向**多次运行的一致性分布**、长任务成功率、故障恢复率。
3. **协议标准化**：MCP 成为工具互操作的事实标准并捐给 Linux 基金会旗下 AAIF，工具生态从「每个应用自己适配」走向「一次实现、到处接入」；同时带来新的供应链与权限风险。
4. **持久执行 / 有状态运行时普及**：Checkpointer、HITL、断点恢复从「高级特性」变成生产默认要求（LangGraph 1.0 的定位正是这个）。
5. **上下文工程取代「堆长上下文」**：焦点从「窗口够不够大」变成「选对放进窗口的内容」；小模型路由、Prompt Caching、压缩成为常规优化。
6. **成本与可靠性驱动架构收敛**：短链、少交接、确定性校验器、可回滚动作 —— 这些「不性感」的工程手段，比换更强的模型更能提高端到端成功率。

**落地瓶颈（讲这些比讲趋势更显成熟）**：

| 瓶颈 | 为什么难 |
| --- | --- |
| **可靠性乘法衰减** | 单步再高，10 步链路的成功率也会显著下降；长任务尤其明显 |
| **非确定性** | 同样输入不同结果，回归测试难写，出问题难复现，用户难建立信任 |
| **故障恢复与副作用** | 公开评测反复显示：Agent 正常完成任务不难，**中途出错后正确恢复**很难；朴素重试还会造成重复副作用（幂等设计必须前置） |
| **评估缺口** | 没有评估集就没有「改好了没有」的判据，优化全靠感觉 |
| **数据与集成** | 很多生产故障的根因是数据质量、上下文缺失、权限与旧系统对接，而不是模型能力 |
| **成本不可预测** | 步数不定导致单任务成本波动大，规模化前必须做预算与归因 |
| **治理与合规** | 注入、越权、数据泄露、审计留痕，往往是项目被叫停的直接原因 |

**给自己的定位**（结合你的转型方向，可以这么收尾）：

> 未来最稀缺的不是「会调某个框架 API」的人，而是能把 Agent **当成一个有状态、会失败、需要被观测和治理的分布式系统**来建设的人。前端转全栈的优势恰好在这里：既懂用户看到的流式过程与审批交互，也懂背后的状态、队列、鉴权与可观测 —— 这正是把 demo 变成可上线产品所缺的那一环。
