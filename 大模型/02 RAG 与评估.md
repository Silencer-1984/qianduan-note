# RAG 与评估

## ⭐⭐ RAG 的完整链路？每一步容易出什么问题？

**考察点**：对检索增强全流程的系统性理解。

**参考答案**：

| 阶段 | 做什么 | 常见问题 |
|---|---|---|
| 摄入 | 加载 → 切分 → embedding → 入库 | 切分破坏语义、表格/图片丢失、元数据缺失 |
| 检索 | 查询改写 → 向量/关键词检索 → 融合 | 召回不全、召回不相关、query 与文档表述不一致 |
| 重排 | cross-encoder 精排 | 成本高、延迟增加 |
| 生成 | 拼上下文 → 生成 → 引用 | 忽略上下文、超出窗口、编造引用 |

**追问**：
- *chunk 大小怎么定？* → 没有标准答案，看文档结构和问题粒度；常见做法是**小 chunk 检索、大 chunk 生成**（或父子块、sentence-window 扩展）。
- *只做向量检索够吗？* → 不够。专有名词、编号、代码这类**精确匹配**场景，关键词检索（BM25）更强；生产上通常**混合检索 + RRF 融合**。
- *为什么要 rerank？* → 向量检索是粗排，只保证"大概相关"；rerank 用 cross-encoder 逐对打分，精度高但慢，放在召回后的 top-k 上最划算。

## ⭐⭐ 怎么评估一个 RAG 系统的效果？

**考察点**：有没有"评测"意识——这是区分工程和玩具的关键。

**参考答案**：拆成两层评，不要只看最终答案好不好。
- **检索层**：召回率、命中率、MRR / nDCG——相关文档有没有被召回到。
- **生成层**：忠实度（faithfulness，答案是否只依据检索内容）、答案相关性、引用正确率。
- **业务层**：人工抽检 + 真实用户反馈（采纳率、修正率）。
- **方法**：建**固定评测集**（问题 + 标准答案 + 相关文档），每次改动跑回归；LLM-as-judge 做初筛，人工校准。

**追问**：
- *没有标注数据怎么办？* → 从线上真实问题抽样，人工标一批（几十到几百条就能起步），再逐步扩。
- *怎么防止"刷分"？* → 留一份**不参与调优的留出集**。

## ⭐ 长上下文越来越强，RAG 还有必要吗？

**参考答案**：有必要，但边界在变。
- 长上下文适合**单次、小规模、强关联**的任务；RAG 适合**大规模、需要更新、要控成本**的场景。
- 长上下文的问题：成本随长度线性上升、中间内容容易被忽略（lost in the middle）、知识更新仍需重新喂。
- 实践上常结合：RAG 先缩小范围，再把相关内容放进长上下文。

**追问**：
- *什么情况下可以不建向量库？* → 数据量小、更新少、一次全量能塞进上下文且成本可接受时。
