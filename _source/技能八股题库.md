# 一、AI / Agent / LLM 应用

## Q1 ⭐⭐ LangChain 的核心抽象有哪些？LCEL 是什么？

**考察点**：是否真的用过，而不是只会调一个 `LLMChain`。

**参考答案**：
- 核心抽象：**Model**（ChatModel / LLM）、**PromptTemplate**、**OutputParser**、**Retriever**、**Tool**、**Memory**、**Chain / Runnable**、**Agent**。
- **LCEL（LangChain Expression Language）** 是基于 `Runnable` 协议的组合方式，用 `|` 把组件串成管道：`prompt | model | parser`。它统一支持同步、异步、流式、批量调用，也支持并行分支。
- 一句话：**LangChain 解决的是"把模型、提示词、工具、检索拼成一条流水线"的问题。**

**追问**：
- *LCEL 管道内部怎么执行？* → 每个 Runnable 实现 `invoke / stream / batch`，管道按顺序传递中间结果；`RunnableParallel` 可以并发分支。
- *LangChain 常被批评过度封装，你怎么看？* → 复杂流程用 LangGraph 更可控；简单链路直接调 SDK 也完全可行。**关键不是用不用框架，而是能不能控制每一步的输入输出和失败处理。**

## Q2 ⭐⭐ LangGraph 和 LangChain 的区别？什么时候用哪个？

**考察点**：对"链"和"状态机"的理解差异。

**参考答案**：
- LangChain 的 Chain 是**有向无环的线性/树形编排**，适合"一次走完"的流程。
- LangGraph 是**图状态机**：显式的 `State`、`Node`（处理函数）、`Edge` / `ConditionalEdge`（条件流转），支持**循环、分支、状态持久化、人工介入（interrupt）**。
- 判断标准：**流程有没有循环和回退**。有"校验不通过要重试""低置信度转人工""多轮工具调用"这类需求，就该用 LangGraph；纯线性 RAG 用 Chain 就够。

**追问**：
- *LangGraph 的状态怎么持久化？* → 通过 **checkpointer**（内存 / SQLite / Postgres 等），按 `thread_id` 保存每一步状态，可实现断点续跑。
- *这和"每阶段落库"有什么区别？* → 落库是业务级检查点，粒度是业务阶段；checkpointer 是框架级执行检查点，粒度是图节点。两者互补。

## Q3 ⭐ ReAct 范式是什么？和 Function Calling 什么关系？

**考察点**：Agent 的基本工作原理。

**参考答案**：
- **ReAct = Reason + Act**：模型循环执行 `Thought → Action → Observation`，根据工具返回结果继续推理，直到给出最终答案。
- 早期靠**提示词**让模型输出固定格式的文本来触发工具；现在主流是 **Function Calling**——模型直接输出结构化的工具调用请求，由宿主代码执行。
- 关系：**Function Calling 是 ReAct 的工程化实现**，把"让模型吐格式文本"换成"模型原生支持结构化调用"，更稳定。

**追问**：
- *Agent 死循环怎么办？* → 最大步数、总超时、重复动作检测（同样的工具 + 参数连续出现就中断）、把状态约束在有限状态内。
- *怎么调试 Agent？* → 全链路 trace，记录每一步的输入、工具调用、返回、token 消耗；按失败类型归类。

## Q4 ⭐⭐ Function Calling 的完整链路是什么？并行调用怎么处理？

**考察点**：是否真的实现过工具调用，而不是只看过文档。

**参考答案**：
1. 把工具定义（名称、描述、JSON Schema 参数）随请求传给模型。
2. 模型返回 `tool_calls`（可能一次多个），**模型本身不执行**。
3. 宿主代码按名称分发执行，拿到结果。
4. 把结果以 `tool` 角色消息回填，再次请求模型。
5. 循环直到模型返回普通文本或达到步数上限。

**并行调用**：模型一次返回多个 `tool_calls` 时，宿主可以并发执行再一起回填——前提是这些工具**相互独立**。

**追问**：
- *工具很多时怎么选？* → 精简工具集（按场景分组）、描述写清适用/不适用条件、必要时先做一次工具路由。
- *模型选错工具怎么办？* → 参数校验 + 执行失败反馈给模型重试 + 限制可选工具范围；不要让它"随便试"。

## Q5 ⭐⭐ RAG 的完整链路？每一步容易出什么问题？

**考察点**：对检索增强全流程的系统性理解。

**参考答案**：

| 阶段 | 做什么 | 常见问题 |
|---|---|---|
| 摄入 | 加载 → 切分 → embedding → 入库 | 切分破坏语义、表格/图片丢失、元数据缺失 |
| 检索 | 查询改写 → 向量/关键词检索 → 融合 | 召回不全、召回不相关、query 与文档表述不一致 |
| 重排 | cross-encoder 精排 | 成本高、延迟增加 |
| 生成 | 拼上下文 → 生成 → 引用 | 忽略上下文、超出窗口、编造引用 |

**追问**：
- *chunk 大小怎么定？* → 没有标准答案，看文档结构和问题粒度；常见做法是**小 chunk 检索、大 chunk 生成**（或父子块、sentence-window 扩展）。
- *只做向量检索够吗？* → 不够。专有名词、编号、代码这类**精确匹配**场景，关键词检索（BM25）更强；生产上通常**混合检索 + RRF 融合**。
- *为什么要 rerank？* → 向量检索是粗排，只保证"大概相关"；rerank 用 cross-encoder 逐对打分，精度高但慢，放在召回后的 top-k 上最划算。

## Q6 ⭐⭐ 怎么评估一个 RAG 系统的效果？

**考察点**：有没有"评测"意识——这是区分工程和玩具的关键。

**参考答案**：拆成两层评，不要只看最终答案好不好。
- **检索层**：召回率、命中率、MRR / nDCG——相关文档有没有被召回到。
- **生成层**：忠实度（faithfulness，答案是否只依据检索内容）、答案相关性、引用正确率。
- **业务层**：人工抽检 + 真实用户反馈（采纳率、修正率）。
- **方法**：建**固定评测集**（问题 + 标准答案 + 相关文档），每次改动跑回归；LLM-as-judge 做初筛，人工校准。

**追问**：
- *没有标注数据怎么办？* → 从线上真实问题抽样，人工标一批（几十到几百条就能起步），再逐步扩。
- *怎么防止"刷分"？* → 留一份**不参与调优的留出集**。

## Q7 ⭐ 如何降低大模型幻觉？

**考察点**：AI 工程的核心能力。

**参考答案**（按有效性排序）：
1. **RAG**：给事实依据，要求答案只基于检索内容，并给出来源。
2. **结构化输出**：约束字段和取值范围，减少自由发挥。
3. **后置校验**：引用是否真实存在、数字是否与原文一致。
4. **允许弃权**：要求"不知道就说不知道"，输出 `unknown` 而不是猜。
5. **降低温度**：事实型任务用低 temperature。
6. **多轮验证 / 交叉检查**：独立再跑一次比对，不一致的标出来。

**追问**：
- *降低温度能根治吗？* → 不能。它只减少随机性，不解决知识缺失。
- *RAG 一定减少幻觉吗？* → 不一定。检索到无关内容时，模型可能"顺着错误上下文编"。所以要加相关性过滤和引用校验。

## Q8 ⭐ 什么是提示词注入？怎么防？

**考察点**：安全意识。现在做 AI 应用基本必问。

**参考答案**：
- **直接注入**：用户输入里写"忽略之前所有指令"。
- **间接注入**：恶意内容藏在**检索到的文档、网页、工具返回结果**里——这类更危险，因为开发者容易只防用户输入。
- 防护：把外部内容明确标记为"数据"而非"指令"；系统提示与用户输入分层；工具调用做白名单和参数校验；输出侧做异常检测；高风险操作必须人工确认。

**追问**：
- *为什么间接注入更难防？* → 内容来自"可信"的数据源，模型无法天然区分"内容"和"指令"。

## Q9 ⭐ 大模型应用怎么优化成本和延迟？

**参考答案**：
- **成本**：结果缓存（key 带 prompt 版本）、模型路由（简单任务用小模型）、输入裁剪（只喂相关片段）、批处理、减少重复调用、限制输出长度。
- **延迟**：流式输出（改善体感）、独立步骤并行、预填充缓存、减少往返轮次、超时降级。
- **用质量换成本**：把复杂 prompt 拆成多步小调用，单步更便宜也更稳。

**追问**：
- *模型路由怎么实现？* → 按任务类型 / 输入长度 / 置信度先分类，再选模型；复杂问题升级到强模型。

## Q10 ⭐ 如何调试一个效果不好的大模型应用？

**考察点**：排查方法是否系统。

**参考答案**：先定位是**检索问题还是生成问题**。
1. 把完整 prompt 和检索内容打出来看——很多时候是检索错了，不是模型笨。
2. 看模型是否忽略了上下文（指令位置、格式、长度）。
3. 按错误类型分类统计，不要只看总准确率。
4. 单点复现：拿失败样本单独跑，一次只改一个变量。
5. 建回归集，防止"修好一个坏掉另一个"。

**追问**：
- *提示词改了很多版怎么管理？* → 像代码一样版本化，每次改动记录原因，配合回归评测。

## Q11 ⭐ LangGraph 里人工介入（human-in-the-loop）怎么实现？

**参考答案**：用 `interrupt` 暂停图执行，把当前状态和待确认内容抛给前端；用户确认后从检查点恢复继续跑。关键是**状态要持久化**，否则进程重启就丢了。

**追问**：
- *和"低置信度转人工"怎么结合？* → 在条件边里判断置信度，低于阈值路由到人工节点。

## Q12 ⭐ 结构化输出怎么保证稳定？

**参考答案**：
- 优先用模型原生的 **JSON mode / structured outputs / schema 约束**。
- 提示词里给字段说明、取值范围、示例。
- 解析失败时**重试 + 把报错信息回填**让模型修正。
- 校验层兜底：Pydantic 校验，失败不静默通过。
- 关键字段用枚举而不是自由文本。

**追问**：
- *重试几次合适？* → 2–3 次足够，再多说明提示词或 schema 设计有问题。

## Q13 ⭐ 长上下文越来越强，RAG 还有必要吗？

**参考答案**：有必要，但边界在变。
- 长上下文适合**单次、小规模、强关联**的任务；RAG 适合**大规模、需要更新、要控成本**的场景。
- 长上下文的问题：成本随长度线性上升、中间内容容易被忽略（lost in the middle）、知识更新仍需重新喂。
- 实践上常结合：RAG 先缩小范围，再把相关内容放进长上下文。

**追问**：
- *什么情况下可以不建向量库？* → 数据量小、更新少、一次全量能塞进上下文且成本可接受时。

## Q14 ⭐ 你怎么理解 Agent 的"可靠性"问题？

**参考答案**：不可靠来自三个地方——**推理链长（误差累积）、工具返回不可控、环境状态变化**。应对：缩短链路、每步做校验、限制工具权限、加最大步数和超时、关键节点人工确认、全链路 trace 便于复盘。

# 二、前端工程化

## Q15 ⭐⭐ 为什么 Hooks 不能写在条件或循环里？

**参考答案**：React 内部用**链表按调用顺序**保存每个 Hook 的状态（fiber 的 memoizedState）。条件或循环会让调用顺序在两次渲染间变化，React 无法把状态和 Hook 对上号，就会错位。规则的本质是：**Hooks 的调用顺序必须在每次渲染中完全一致**。

**追问**：
- *自定义 Hook 也有限制吗？* → 有，自定义 Hook 内部同样要遵守规则，因为它最终展开成顺序调用。
- *为什么不能靠名字匹配？* → 名字在运行时拿不到（压缩后更是），顺序是唯一可靠的标识。

## Q16 ⭐⭐ useEffect 的闭包陷阱是什么？怎么解决？

**参考答案**：effect（或定时器、事件监听）里引用的 state/props 是**创建时的快照**，之后的更新不会反映进去，导致"读到旧值"。
- 解决：正确补全依赖；用函数式更新 `setState(prev => ...)`；把需要的值放进 ref 读最新值；用 cleanup 清理旧订阅。

**追问**：
- *依赖数组放对象/函数会怎样？* → 每次渲染都是新引用，effect 会反复执行。解决：用 `useMemo`/`useCallback` 稳定引用，或把依赖拆成基本类型。
- *为什么不能简单关掉 lint 的依赖检查？* → 会掩盖真正的闭包问题，后续出 bug 很难查。

## Q17 ⭐ useMemo / useCallback 什么时候真的有用？

**参考答案**：只在两种情况有收益：
1. **传给 `memo` 子组件的 props** 需要引用稳定，避免无谓重渲染。
2. **计算开销确实大**（大数据排序、复杂派生状态）。

反例：用 `useMemo` 包一个加法，成本比收益还高。**先测量再优化。**

**追问**：
- *React Compiler 会自动做这些吗？* → 能自动 memo 化，减少手写需要，但理解原理仍然必要。

## Q18 ⭐ React 18 的并发特性解决了什么问题？

**参考答案**：让渲染可中断，避免长任务阻塞输入。`useTransition` 把非紧急更新标记为可中断（如列表筛选）；`useDeferredValue` 延迟渲染旧值以保持输入流畅；自动批处理减少渲染次数。

**追问**：
- *`useTransition` 和 `useDeferredValue` 的区别？* → 前者控制"更新优先级"，后者控制"值的新旧"，前者更常用于触发更新的场景。

## Q19 ⭐ Zustand 的原理？和 Redux 的区别？

**参考答案**：
- Zustand 是**外部 store**，用 `useSyncExternalStore` 订阅。组件只订阅自己用到的切片（selector），切片不变就不重渲染。
- 对比 Redux：更轻、没有 action/reducer 样板代码、不需要 Provider；Redux 的中间件生态和时间旅行调试更成熟。
- 选择：中小型应用用 Zustand 更合适；需要严格可追溯、复杂副作用编排时 Redux 更稳。

**追问**：
- *怎么避免拿整个 store 导致重渲染？* → 用 selector，必要时 `useShallow` 做浅比较。
- *它的更新是不可变的吗？* → 是，必须返回新对象，否则订阅者不会收到通知。

## Q20 ⭐ Immer 的原理？什么时候不该用？

**参考答案**：
- 基于 **Proxy** 生成 draft，读写都记录在 draft 上；提交时按**结构共享**生成新对象（未修改的子树复用原引用）。
- 好处：深层嵌套更新不用手写层层展开，可读性大幅提升；和 React 的不可变更新天然契合。
- 不该用：对象很小（手写 spread 更直接）、超高频更新（Proxy 有开销）、性能敏感热路径。

**追问**：
- *结构共享对 React 有什么意义？* → 未变的子树引用不变，配合 `memo` 可以跳过重渲染。

## Q21 ⭐ App Router 和 Pages Router 的区别？

**参考答案**：
- App Router 默认使用 **React Server Components**，组件在服务端渲染、不打包进客户端；交互部分用 `"use client"` 标记。
- 支持 **Server Actions**（直接在服务端处理表单/变更）、流式渲染、嵌套布局。
- Pages Router 是传统模式，页面级 SSR/SSG。

**追问**：
- *RSC 的好处？* → 减少客户端 bundle、直接访问后端资源、避免把敏感逻辑打到前端。
- *什么必须用 client component？* → 用 state、事件、浏览器 API 的部分。

## Q22 ⭐ SSR / SSG / ISR / CSR 怎么选？

**参考答案**：
- SSR：每次请求服务端渲染，适合个性化、实时数据。
- SSG：构建时生成，适合营销页、文档。
- ISR：静态 + 定时/按需再生成，适合内容更新但不需要实时的页面。
- CSR：客户端渲染，适合后台系统、强交互应用。

**追问**：
- *水合（hydration）是什么？为什么会不匹配？* → 服务端 HTML 与客户端首次渲染结果不一致。常见原因：`Date.now()`、随机数、`window` 判断、浏览器扩展改 DOM。

## Q23 ⭐ Vite 为什么比 webpack 快？

**参考答案**：
- 开发环境**不打包**：利用浏览器原生 ESM 按需加载，启动几乎是秒级。
- 依赖用 **esbuild 预构建**（把 CommonJS 转 ESM、合并大量小文件），速度快一个量级。
- HMR 只更新改动模块。
- 生产构建仍用 Rollup（生态成熟、产物优化好）。

**追问**：
- *依赖预构建解决什么问题？* → 两个：把 CJS 依赖转成 ESM；把几百个小文件合并成一个请求，避免浏览器请求过多。
- *Vite 有什么坑？* → 开发/生产行为差异、某些 CJS 库需配置、monorepo 下的依赖缓存问题。

## Q24 ⭐ TypeScript：interface 和 type 的区别？

**参考答案**：
- interface 可以**声明合并**，更适合描述对象/类的契约；type 可以做**联合、交叉、条件类型、映射类型**等更复杂的类型运算。
- 实际项目里差别不大，团队统一即可；对外 API 类型常用 interface，工具类型用 type。

**追问**：
- *type 能做而 interface 不能的？* → 联合类型、条件类型、`infer`、元组、映射类型。

## Q25 ⭐ unknown 和 any 的区别？

**参考答案**：`any` 关闭类型检查；`unknown` 是"未知但安全"——可以赋值给它，但使用前必须收窄（typeof、instanceof、类型守卫）。**能用 unknown 就不要用 any。**

**追问**：
- *怎么安全处理 unknown？* → 类型守卫函数收窄，配合 zod 之类做运行时校验。

## Q26 ⭐ 怎么用 TS 保证接口类型安全？

**参考答案**：前后端共享类型（monorepo 或生成），运行时用 zod / io-ts 做**校验**（TS 类型在运行时不存在，不能只靠编译期），再用 `z.infer` 从 schema 推导类型，做到"一份定义，编译期 + 运行时都安全"。

# 三、后端与数据

## Q27 ⭐⭐ Python 的 GIL 是什么？影响是什么？

**参考答案**：CPython 的全局解释器锁，同一进程内同一时刻只有一个线程执行 Python 字节码。
- **CPU 密集型**：多线程无法并行，要用**多进程**。
- **IO 密集型**：线程等 IO 时会释放 GIL，多线程仍然有效；异步 IO 更轻量。
- 所以 FastAPI 里调 LLM API 这种 IO 密集任务，**异步收益最大**。

**追问**：
- *GIL 会取消吗？* → Python 3.13 有实验性的 free-threaded 构建，但生态兼容需要时间；短期多进程仍是主流。

## Q28 ⭐ 装饰器原理？

**参考答案**：装饰器是**接收函数、返回函数**的高阶函数，`@decorator` 等价于 `func = decorator(func)`，靠**闭包**保存原函数引用。常见用途：日志、计时、鉴权、缓存（`functools.lru_cache`）。要用 `functools.wraps` 保留元信息。

## Q29 ⭐ FastAPI 的依赖注入（Depends）怎么用？

**参考答案**：`Depends` 声明依赖，FastAPI 在请求时解析并注入。典型用途：数据库 session、当前用户鉴权、分页参数。依赖可以嵌套，也可以带 `yield` 做资源清理（请求结束后自动关闭连接）。

**追问**：
- *`yield` 依赖的清理逻辑什么时候执行？* → 响应完成后执行，适合关连接、回滚事务。

## Q30 ⭐⭐ FastAPI 里 async def 和普通 def 路由有什么区别？

**参考答案**：
- `async def` 路由在**事件循环**里执行；里面若有同步阻塞调用（requests、time.sleep、阻塞式 DB 驱动），会卡住整个 worker。
- 普通 `def` 路由，FastAPI 会丢到**线程池**执行，不会阻塞事件循环——但线程池有上限。
- 结论：**要么全程异步（httpx、asyncpg），要么用普通 def 让框架进线程池；不要 async 里混同步阻塞调用。**

**追问**：
- *怎么发现代码里有阻塞调用？* → 压测看吞吐、监控事件循环延迟、审查 IO 库是否异步版本。

## Q31 ⭐ Pydantic 在 FastAPI 里的作用？

**参考答案**：请求体校验（类型、范围、必填）、`response_model` 控制输出字段（防止敏感字段泄漏）、自动生成 OpenAPI 文档、错误信息结构化。它是"接口契约"的落地方式。

**追问**：
- *response_model 为什么重要？* → 同时做**过滤**和**序列化**：不在模型里的字段会被丢掉，避免把密码哈希、内部字段返回给前端。

## Q32 ⭐ FastAPI 怎么部署？workers 开多少？

**参考答案**：`uvicorn` 直接跑，或 `gunicorn -k uvicorn.workers.UvicornWorker` 做进程管理。每个 worker 是独立进程 + 独立事件循环。
- workers 常见起点是 CPU 核数，IO 密集型可适当多开。
- 配合健康检查、优雅关闭、连接池大小（每个 worker 各持池，别把数据库连接打满）。

**追问**：
- *为什么不建议在容器里开很多 worker？* → 容器 CPU 限额下多进程会争抢；通常用编排横向扩副本，而不是单容器开满 worker。

## Q33 ⭐⭐ Docker 镜像分层和缓存机制？

**参考答案**：每条 Dockerfile 指令生成一层，层有缓存。**只要某层内容和上游不变，就直接复用缓存**。所以把变化频率低的放前面（装依赖），变化频率高的放后面（拷代码）——否则改一行代码就让依赖重新安装。

**追问**：
- *多阶段构建的价值？* → 构建阶段装编译工具和依赖，运行阶段只拷产物，体积和攻击面都大幅下降。
- *alpine 有坑吗？* → 有，musl libc 与 glibc 不兼容，numpy、pandas 这类包可能没有预编译轮子；用 `slim` 更稳。

## Q34 ⭐ Redis 有哪些数据结构？各用在什么场景？

**参考答案**：
- String：缓存、计数器、分布式锁。
- Hash：对象字段（用户信息）。
- List：队列（简单场景）。
- Set：去重、交集/并集。
- ZSet：排行榜、延迟队列（按 score 排序）。
- 其他：Bitmap（签到）、HyperLogLog（UV 估算）、Stream（消息流）。

**追问**：
- *Redis 为什么快？* → 内存操作、单线程避免锁竞争、IO 多路复用、高效数据结构。
- *单线程会不会成为瓶颈？* → 命令执行是单线程，但网络 IO 是多路复用；真正瓶颈常是**大 key / 慢命令**（KEYS、大 range），要避免。

## Q35 ⭐⭐ 缓存穿透、击穿、雪崩分别是什么？

**参考答案**：
- **穿透**：查不存在的数据，缓存不命中，每次都打到 DB。解决：缓存空值（短 TTL）、布隆过滤器、参数校验。
- **击穿**：热点 key 过期瞬间，大量请求同时打到 DB。解决：互斥锁/单飞（只让一个请求重建）、逻辑过期不删 key。
- **雪崩**：大量 key 同时过期，或 Redis 宕机。解决：过期时间加随机抖动、多级缓存、熔断降级。

**追问**：
- *缓存和数据库一致性怎么保证？* → 常用 **Cache Aside**：先更库、再删缓存；延迟双删降低并发窗口；强一致要求高时订阅 binlog 异步删。

## Q36 ⭐ PostgreSQL 索引原理？什么时候会失效？

**参考答案**：默认 B-tree，适合等值、范围、排序。失效常见原因：
- 对列做函数运算或类型转换（`where lower(name)=...`）——可用函数索引或改写。
- 前导模糊匹配 `like '%x'`（走不了 B-tree，可用 trigram 索引）。
- 复合索引不满足**最左前缀**。
- 数据量小或选择性差，优化器判断全表扫描更便宜。
- 统计信息过期，需要 ANALYZE。

**追问**：
- *怎么看查询走了什么索引？* → `EXPLAIN (ANALYZE, BUFFERS)`，看是否 Seq Scan、估算行数和实际行数差多少。

## Q37 ⭐ MVCC 和事务隔离级别？

**参考答案**：PostgreSQL 用 MVCC：每行保留多个版本，读不阻塞写、写不阻塞读，通过 `xmin/xmax` 和快照判断可见性。
- 默认隔离级别是 **Read Committed**：每条语句看到最新已提交快照。
- **Repeatable Read**：整个事务用同一个快照。
- **Serializable**：用 SSI 检测冲突，冲突时回滚重试。

**追问**：
- *长事务有什么问题？* → 阻止 vacuum 回收死元组，导致表膨胀；还会占锁。要监控长事务。

## Q38 ⭐ JSONB 和 JSON 的区别？什么时候用？

**参考答案**：JSONB 存二进制格式，支持索引（GIN）、去重键、查询效率高；JSON 保留原始文本。**存半结构化数据用 JSONB**（比如模型输出），需要保留格式细节才用 JSON。

**追问**：
- *JSONB 能替代关系表吗？* → 不能。频繁更新的字段、需要外键和强约束的数据仍应建表；JSONB 适合**结构不固定、整体读写**的部分。

## Q39 ⭐ 什么是 N+1 查询？怎么解决？

**参考答案**：查列表（1 次）后对每条记录再查关联（N 次），总请求数暴涨。解决：**join 预加载**（joinedload / selectinload）、批量查询 `where id in (...)`、缓存。

**追问**：
- *SQLAlchemy 里怎么发现？* → 开 SQL echo 或性能分析，看日志里是否有大量重复的相似查询。

## Q40 ⭐ 深分页（limit offset 很大）为什么慢？怎么优化？

**参考答案**：`offset 100000` 需要扫描并丢弃前 10 万行。优化：**游标/keyset 分页**（`where id > last_id order by id limit 20`），前提是有序且唯一的排序字段；或用覆盖索引减少回表。
